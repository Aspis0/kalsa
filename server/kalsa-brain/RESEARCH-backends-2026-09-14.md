## 2. CUDA requirements and failure behavior

- **Driver:** CUDA 13.x requires NVIDIA driver `>=580` under minor-version compatibility. CUDA 12.4 GA requires Windows `>=551.61` / Linux `>=550.54.14`; CUDA 12.x’s broader compatibility floor is Windows `>=528.33` / Linux `>=525.60.13`. For a bundled 12.4 runtime, use the 12.4 paired floor (`551.61`/`550.54.14`) as the product requirement, not the looser generic floor. [NVIDIA CUDA 13.4 release notes](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html) (source date: current page, checked 2026-09-14) and [CUDA 12.4 release notes](https://docs.nvidia.com/cuda/archive/12.4.0/cuda-toolkit-release-notes/) (**source date: 2024-02-xx; possibly stale**).
- **Redistributable:** the b10950 Windows CUDA assets explicitly ship separate CUDA 12.4/13.3/13.4 DLL archives; the user does not need the CUDA toolkit, but does need a compatible installed NVIDIA display driver. CUDA 13.4 documentation says the driver is no longer bundled with the toolkit; llama.cpp’s release is bundling runtime DLLs, not a driver. [Release](https://github.com/ggml-org/llama.cpp/releases/tag/b10950) (source date: 2026-09-14) and [NVIDIA notes](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html) (source date: current page, checked 2026-09-14).
- **Compute capability:** current llama.cpp CMake lists CUDA 12’s default virtual targets beginning at `sm_50` and CUDA 13’s target set beginning at `sm_75`; this is a source-level compile-floor inference, not an independently inspected b10950 fatbin. Therefore CUDA 12 builds should be treated as excluding pre-Maxwell CC `<5.0` (Fermi and Kepler, e.g. GTX 400/500/600/700), while CUDA 13 builds exclude Maxwell/Pascal/Volta CC `<7.5` (GTX 750/900, GTX 10-series, P100/P40, Titan V/V100). Verify exact cards against the shipped binary before relying on this. [CUDA CMake](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-cuda/CMakeLists.txt) (source date: unknown; checked 2026-09-14) and [NVIDIA CUDA GPU list](https://developer.nvidia.com/cuda/gpus) (source date: unknown; checked 2026-09-14). **Possibly stale:** the target matrix can change between releases.
- **Failure mode:** CUDA device-count initialization logs `failed to initialize CUDA` and can return no CUDA device, which permits a parent application to select CPU/another backend if the backend is loaded dynamically. Later CUDA error checks call an abort path (`GGML_ABORT`); OOM, unsupported kernels, or driver/runtime faults are therefore not guaranteed to become a clean server error. A missing DLL can also fail process loading before llama-server starts. [CUDA initialization](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-cuda/ggml-cuda.cu) and [CUDA error path](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-cuda/common.cuh) (source dates unknown; checked 2026-09-14).
- A real reported failure is NVIDIA’s “forward compatibility was attempted on non supported HW” during CUDA initialization. Treat CUDA as an isolated child-process probe with a timeout and fallback, not as a clean-error guarantee. [llama.cpp discussion #8459](https://github.com/ggml-org/llama.cpp/discussions/8459) (**source date: 2024-07-12; possibly stale**).

## 3. Vulkan floor on old Intel/AMD integrated graphics

- Current llama.cpp requires Vulkan 1.2 at instance initialization, then requires `storageBuffer16BitAccess`; otherwise it throws “Unsupported device”. This is the real llama.cpp floor, beyond merely having a Vulkan driver. [Vulkan backend source](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-vulkan/ggml-vulkan.cpp) (source date unknown; checked 2026-09-14).
- **Haswell:** an upstream report on Intel HD 4400/Mesa logs “Haswell Vulkan support is incomplete”, `fp16:0`, then “device ... does not support 16-bit storage” and “Unsupported device”. Do not select Vulkan on this class without a real llama probe. [Issue #14805](https://github.com/ggml-org/llama.cpp/issues/14805) (**source date: 2025-07-21; possibly stale**).
- **Broadwell:** **unknown**. I found no current upstream llama.cpp pass/fail report for a Broadwell iGPU. Do not infer support from the GPU name alone; probe Vulkan 1.2 plus 16-bit storage and then run a tiny graph.
- **Skylake:** at least one HD Graphics 530/Mesa report enumerates the device with `fp16:1`; it is evidence that discovery can pass, not evidence of reliable inference or acceptable speed. [Issue #18922](https://github.com/ggml-org/llama.cpp/issues/18922) (**source date: 2026-01-18; possibly stale**).
- **Old AMD APUs:** there is no architecture-generation block in the current Vulkan source; the feature gate is driver-reported. A Renoir `gfx90c` RADV report shows an APU-specific device-lost risk when long compute submissions exceed the Linux GPU lockup timeout; reducing nodes per submit from 100 to 1 avoided the crash in the reporter’s test. This was reported against a sibling ggml consumer, so llama.cpp impact is **unconfirmed**. [Issue #21724](https://github.com/ggml-org/llama.cpp/issues/21724) (source date: 2026-04-xx; checked 2026-09-14).
- Vulkan can be slower than CPU on UMA graphics. On Intel Arc 140T/Arrow Lake UMA, a public llama.cpp report measured Qwen3.6-35B-A3B Q4_K_M at **18.49 decode tok/s full Vulkan, 12.19 CPU, and 5.68 tok/s with a split configuration**; the split was **2.15× slower than CPU** and **3.26× slower than full Vulkan**. The report itself says the cause was not profiled; this is not a Haswell/Broadwell measurement and is not a universal rule. [Issue #26876](https://github.com/ggml-org/llama.cpp/issues/26876) (source date: 2026-08-11; current).
- A Renoir report also measured Vulkan faster than CPU for one workload (17.66 vs 12.95 decode tok/s), demonstrating that UMA alone does not decide the result. [Discussion #10879](https://github.com/ggml-org/llama.cpp/discussions/10879) (source date: 2026-08-07; current).

## 4. Partial offload (`-ngl`)

`-ngl N` is the maximum number of model layers stored in VRAM; `-ngl 0` is CPU-layer placement, and “all/auto” is the default behavior. It is not a promise that the model fits or that every operation stays on the GPU. [CLI options](https://github.com/ggml-org/llama.cpp/blob/master/tools/cli/README.md) (source date unknown; checked 2026-09-14).

When the model does not fit, llama.cpp keeps the remaining layers on CPU. During decode, the activation crosses the CPU/GPU boundary repeatedly, so the curve is workload- and boundary-dependent: a few offloaded layers can be worse than CPU, and a nearly full fit can be much better. There is no defensible universal percentage or monotonic tok/s formula from `-ngl` alone.

The strongest recent public measurement is not a classic `-ngl` sweep but an upstream MoE split (`-ncmoe`): 18.49 tok/s full Vulkan, 12.19 CPU, 5.68 split; split is 69% below full Vulkan and 53% below CPU. It demonstrates the possible shape, not a general prediction model. [Issue #26876](https://github.com/ggml-org/llama.cpp/issues/26876) (source date: 2026-08-11; current).

**Unknown / not found:** a controlled upstream benchmark holding model, context, batch, GPU, driver, and server build constant while sweeping `-ngl=0,1,...,all` with full-fit versus partial-fit decode tok/s. Do not promise speed before download from VRAM capacity and layer count alone; preflight backend support, then benchmark a small representative model in the child process.

## 5. Windows detection without CUDA/vendor SDKs

**Recommendation:** direct DXGI via the Rust `windows` crate (`IDXGIFactory1::EnumAdapters1`, `DXGI_ADAPTER_DESC1`; optionally `IDXGIFactory6::EnumAdapterByGpuPreference`). It is the smallest reliable Windows-only discovery path: enumerate adapters, reject software adapters, inspect `VendorId`/`DeviceId`, and read `DedicatedVideoMemory` plus `SharedSystemMemory`. [EnumAdapters](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgifactory-enumadapters) (**source date: 2021-10-12; possibly stale**), [DXGI adapter description](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ns-dxgi-dxgi_adapter_desc) (**source date: 2024-02-22; possibly stale**), and [Rust Windows DXGI bindings](https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/Graphics/Dxgi/struct.DXGI_ADAPTER_DESC.html) (source date unknown; checked 2026-09-14).

DXGI gets **wrong** if interpreted as usable llama VRAM: `DedicatedVideoMemory` is a capacity classification, not free memory or the current WDDM budget; integrated GPUs commonly report little/no dedicated memory and use shared system RAM. Query `IDXGIAdapter3::QueryVideoMemoryInfo` for the process-local budget/usage, but that budget still changes with Windows and other applications and is not a guarantee that llama’s allocations will fit. [QueryVideoMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo) (**source date: 2024-02-22; possibly stale**) and [memory-info structure](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/ns-dxgi1_4-dxgi_query_video_memory_info) (**source date: 2024-02-22; possibly stale**).

- **WMI `Win32_VideoController`:** useful fallback for names/driver strings, but `AdapterRAM` is a 32-bit field and Microsoft warns it can be inaccurate for WDDM hardware. It is slower and adds COM/provider failure modes. [Win32_VideoController](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-videocontroller) (**source date: not exposed; possibly stale**).
- **`nvidia-smi`:** good NVIDIA-only diagnostic if the executable is installed, but it is not a reliable presence test: it is external, may be absent from OEM/minimal installations, and says nothing about AMD/Intel. Its output is explicitly not guaranteed backward-compatible. [NVIDIA `nvidia-smi`](https://docs.nvidia.com/deploy/nvidia-smi/) (source date unknown; checked 2026-09-14).
- **`ash`:** direct Vulkan enumeration, useful only if the Vulkan loader/driver is present; it tells Vulkan memory heaps/features, not CUDA compute capability or whether llama’s kernels are safe. Dynamic loading is possible, but it is a second backend probe, not the smallest general GPU detector. [ash `Entry`](https://docs.rs/ash/latest/ash/struct.Entry.html) (source date unknown; checked 2026-09-14).
- **`wgpu`:** supports DX12/Vulkan/Metal and exposes adapter identity/backend, but is a larger abstraction and its `AdapterInfo` does not itself provide the DXGI process budget. Use it only if the app already depends on wgpu. [wgpu `AdapterInfo`](https://docs.rs/wgpu/latest/wgpu/struct.AdapterInfo.html) and [wgpu `Adapter`](https://docs.rs/wgpu/latest/target-redirect/x86_64-pc-windows-msvc/wgpu/struct.Adapter.html) (source dates unknown; checked 2026-09-14).

DXGI cannot tell whether llama’s Vulkan gate (Vulkan 1.2 + 16-bit storage), CUDA compute capability, or a particular driver/backend will actually run. Runtime selection should therefore be: DXGI coarse filter → launch the selected llama backend in a disposable child with a tiny model/one-token probe → retain CPU fallback on nonzero exit, timeout, or wrong output.

## 6. macOS

- The build documentation says Metal is enabled by default on macOS; the published arm64 and Intel x64 macOS archives are therefore Metal-capable. “Unconditional” is too strong: the backend is compiled in by default, but runtime flags can disable GPU use, and builds can explicitly pass `-DGGML_METAL=OFF`. [Build documentation](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md) (source date unknown; checked 2026-09-14) and [release assets](https://github.com/ggml-org/llama.cpp/releases/tag/b10950) (source date: 2026-09-14).
- Intel Macs with AMD GPUs are enumerated by Metal, but support is not a safe blanket assumption. A Vega 56 report reproduced command-buffer failures on GCN/wave64 hardware; a separate Intel/AMD report aborts on “device does not support residency sets”; other reports show old AMD hardware falling back much of the work to CPU or running slower. Keep Intel+AMD as a probe/telemetry cohort, not an unconditional Metal choice. [Issue #25866](https://github.com/ggml-org/llama.cpp/issues/25866) (source date: 2026-07-18; current), [Issue #11903](https://github.com/ggml-org/llama.cpp/issues/11903) (**source date: 2025-02-16; possibly stale**), and [Issue #26949](https://github.com/ggml-org/llama.cpp/issues/26949) (source date: 2026-08-12; current, but bug-unconfirmed).
- From Rust, the lightest practical query is Metal itself: call the system Metal device API (or use the small macOS-only `metal` crate), select the device, and read `recommendedMaxWorkingSetSize`; also read `hasUnifiedMemory` and the device name. On Apple Silicon this is a **recommended working-set budget for unified memory**, not dedicated VRAM. The Rust binding exposes `recommended_max_working_set_size()` and `has_unified_memory()`. [Apple Metal property](https://developer.apple.com/documentation/metal/mtldevice/recommendedmaxworkingsetsize?changes=la) (source date unknown; checked 2026-09-14) and [Rust `metal::Device`](https://docs.rs/metal/latest/metal/struct.Device.html) (source date unknown; checked 2026-09-14).

## 7. Crash/hang territory and proposed blocklist

Hard-gate by capability, not by age alone:

- CUDA runtime/driver below the selected CUDA floor; CUDA 12 artifact on CC `<5.0`; CUDA 13 artifact on CC `<7.5`. Use a child-process timeout because later CUDA errors can abort. [CUDA CMake](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-cuda/CMakeLists.txt) (date unknown; checked 2026-09-14), [NVIDIA notes](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html) (current page, checked 2026-09-14), and [CUDA error path](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-cuda/common.cuh) (date unknown; checked 2026-09-14).
- Any Vulkan adapter failing Vulkan 1.2 or `storageBuffer16BitAccess`; this includes the reported Haswell HD 4400/Mesa combination. [Vulkan source](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-vulkan/ggml-vulkan.cpp) (date unknown; checked 2026-09-14) and [Issue #14805](https://github.com/ggml-org/llama.cpp/issues/14805) (**2025-07-21; possibly stale**).
- Intel DG1 Vulkan should use the upstream quirk that disables asynchronous execution; do not override it in a product build without testing. [Vulkan source](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-vulkan/ggml-vulkan.cpp) (date unknown; checked 2026-09-14).

Soft blocklist / fallback rules, not universal hard blocks:

- AMD Renoir `gfx90c` RADV under long submissions: try a lower Vulkan submission-node limit or CPU; device-lost evidence is from a sibling ggml consumer and is unconfirmed for llama.cpp. [Issue #21724](https://github.com/ggml-org/llama.cpp/issues/21724) (2026-04-xx; checked 2026-09-14).
- Intel Arc 140V/Arrow/Lunar/Alder iGPU Vulkan with large context/MoE/KV offload: reports include crashes, garbage, OOM, or watchdog-cancelled work; issues are model/driver-specific and several are bug-unconfirmed. Use a tiny graph probe and conservative fallbacks such as CPU, no KV offload, or no flash attention. [Issue #19327](https://github.com/ggml-org/llama.cpp/issues/19327) (**2025-12-03; possibly stale**), [Issue #18946](https://github.com/ggml-org/llama.cpp/issues/18946) (**2026-01-19; possibly stale**), [Issue #20201](https://github.com/ggml-org/llama.cpp/issues/20201) (**2026-03-07; borderline stale**), and [Issue #27634](https://github.com/ggml-org/llama.cpp/issues/27634) (source date: 2026-08-23; current).
- Intel iMac/iMac Pro + AMD GCN/Vega Metal: exact GPU/OS combinations have reproducible command-buffer failures, CPU fallback, or assertions; do not block every Intel Mac AMD GPU, but maintain exact-model/OS telemetry entries. [Issue #25866](https://github.com/ggml-org/llama.cpp/issues/25866) (2026-07-18; current), [Issue #26949](https://github.com/ggml-org/llama.cpp/issues/26949) (2026-08-12; current), and [Issue #11903](https://github.com/ggml-org/llama.cpp/issues/11903) (**2025-02-16; possibly stale**).
- AMD 680M/Windows Vulkan or related GPU-load paths have a report of black screen/Explorer termination; it is not a cleanly isolated llama.cpp crash, so use as a soft telemetry block only. [Issue #14105](https://github.com/ggml-org/llama.cpp/issues/14105) (**source date: 2025-06-10; possibly stale**).
- Apple Silicon Metal GPU hangs are also documented for particular macOS/model/backend combinations, including `kIOGPUCommandBufferCallbackErrorHang`; do not hard-block all Apple Silicon, but keep child-process watchdog recovery. [Issue #12277](https://github.com/ggml-org/llama.cpp/issues/12277) (**source date: 2025-03-08; possibly stale**).

## Unverified / could not confirm

- Exact b10950 CUDA fatbin compute-capability coverage; the `<5.0` / `<7.5` exclusions above are inferred from current CMake target defaults.
- Broadwell iGPU Vulkan success/failure and any reliable Haswell/Broadwell/Skylake tok/s threshold.
- A controlled `-ngl` full-fit-versus-partial offload benchmark sweep; the cited measurement is an MoE split, not a classic layer-count sweep.
- A universal “usable VRAM” conversion from DXGI `DedicatedVideoMemory`; only the dynamic WDDM budget is observable, and it is not a llama allocation guarantee.
- Whether every listed Intel/AMD issue reproduces on the exact current b10950 binary; several reports are stale, closed, or labeled bug-unconfirmed.
- A universal blocklist for Intel Macs with AMD GPUs, old AMD APUs, or Intel integrated graphics. The evidence supports capability probes, child-process watchdogs, and narrow telemetry-driven entries—not generation-wide bans.
