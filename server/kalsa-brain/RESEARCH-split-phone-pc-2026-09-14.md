# Phone-local conversation + PC-local tools: prior-art report

Research date: 2026-09-14. “C” requires the conversational model to remain on the phone while selected tools—not the whole model—run on the user’s own reachable computer, with no vendor cloud required.

## A. Not it — moving the whole model

- The notable pattern is phone/web UI → a PC running the complete model: [Ollama](https://github.com/ollama/ollama) (accessed 2026-09-14), [LM Studio](https://lmstudio.ai/) (accessed 2026-09-14), [Open WebUI](https://github.com/open-webui/open-webui) (accessed 2026-09-14), and [Enchanted](https://github.com/AugustDev/enchanted) (accessed 2026-09-14). These are A even when the server also exposes RAG, web search, or MCP tools.
- [LMSMOB Chat](https://github.com/mindylab/lmsmob_chat) (accessed 2026-09-14) is a representative open-source phone client: its README describes inference on a PC/LM Studio server and server-side MCP/web tools. A, not C.

## B. Difficulty-based escalation

- **Apple Intelligence / Private Cloud Compute — B.** Apple documents an on-device-first decision: if the device model cannot complete the task and a larger model is needed, relevant data goes to PCC; the documented reason is task complexity/model capability, including larger context and stronger reasoning, not battery. [Apple privacy description](https://www.apple.com/legal/privacy/data/en/intelligence-engine/) (accessed 2026-09-14), [Foundation Models server-side intelligence](https://developer.apple.com/documentation/foundationmodels/adding-server-side-intelligence-with-private-cloud-compute) (accessed 2026-09-14), [PCC announcement](https://security.apple.com/blog/private-cloud-compute/) (2024-06-10; older).
- **Gemini Nano / Firebase Hybrid Inference — B.** Firebase exposes `PREFER_ON_DEVICE`, `PREFER_IN_CLOUD`, and “only” modes, plus the actual inference source; this is a preference/availability mechanism, not a documented battery router. [Firebase Hybrid Inference](https://firebase.google.com/docs/ai-logic/hybrid/android/configuration-options?hl=en) (accessed 2026-09-14). Google’s July 2026 guidance says a custom router may additionally inspect battery status, network, and device model, but its example routes on language—not battery. [Android Developers](https://android-developers.googleblog.com/2026/07/build-intelligent-android-apps-cloud-hybrid-inference.html) (2026-07; older than this report’s cutoff only if superseded).
- **Language Model Cascades — B.** The published criterion is uncertainty/confidence: let a small model answer easy/high-confidence cases and defer uncertain/hard cases to a larger model; the objective is quality versus computational cost, not phone battery. [Google Research: Language Model Cascades](https://research.google/pubs/language-model-cascades-token-level-uncertainty-and-beyond/) (2024; older).
- **CR² — B, serious recent research.** Its query-level gate predicts whether local execution is utility-optimal versus an edge model, using a user-specified cost trade-off; the paper explicitly includes latency, energy, accuracy, and wireless overhead, reporting up to 16.9% normalized deployment-cost reduction at matched accuracy. It is model/location escalation, not remote tool execution. [CR²](https://arxiv.org/abs/2605.12001) (submitted 2026-05-12).
- **TMO/LCIO — B.** A resource-constrained RL policy chooses local versus cloud inference and modality allocation from dialogue/task context, optimizing quality, latency, and usage cost; it does not keep conversation generation on-device while moving only tools. [Local-Cloud Inference Offloading](https://arxiv.org/abs/2502.11007) (2025-02-16).

## C. ⭐ Capability-based split — the actual question

**C is not empty, but the full requested stack is sparse. I found no shipped product or paper that documents all four PC-side functions—ingestion/embeddings, retrieval, web fetch+summarise, and reranking—behind a phone-local conversational model.**

- **Pocket-RAG — C, narrow open-source prototype.** The React Native app runs a small language model on-device, calls a configurable HTTP RAG endpoint, then supplies the returned context to the local model; its troubleshooting explicitly assumes the phone and RAG server can be on the same network. A user-hosted PC can therefore satisfy the private-network/no-vendor-cloud condition. The repository does not document PC-side ingestion, embedding, reranking, or web summarisation as a complete shipped stack. [Pocket-RAG](https://github.com/TzeLun/Pocket-RAG) (README says developed in 2025; accessed 2026-09-14).
- **mobileLLM — C, generic remote-tool substrate.** The project keeps the model, conversation, memory, and agent runtime local; it supports user-configured remote MCP endpoints, so a self-hosted MCP server on a PC can execute selected tools. Its built-in network tools call public services, so the no-vendor-cloud property requires configuring a private MCP/tool server. The repository does not prove a packaged PC RAG-ingestion/embedding/rerank pipeline. [mobileLLM](https://github.com/nanguoyu/mobileLLM) (accessed 2026-09-14).
- **OnDevice-RAG-Android — not C; inverse near miss.** Its document splitter, sentence embeddings, and vector store are on-device; the LLM may be local or remote. It demonstrates the opposite placement for the expensive retrieval preparation. [OnDevice-RAG-Android](https://github.com/shubham0204/OnDevice-RAG-Android) (accessed 2026-09-14).
- **DRAGON — not clean C; distributed-RAG near miss.** The edge device and cloud each perform token generation around distributed retrieval and speculative aggregation. Because the cloud also performs model generation, the conversation does not stay wholly on the phone. [DRAGON](https://arxiv.org/abs/2504.11197) (submitted 2025-04-15; MobiHoc 2025, older).
- **DGRAG — not C; edge/cloud RAG near miss.** It keeps local knowledge at the edge but can defer out-of-scope queries to cloud retrieval/generation; that is escalation of answer generation, not a phone-local conversation with PC-only tools. [DGRAG](https://arxiv.org/abs/2505.19847) (submitted 2025-05-26).

## D. Split inference / layer offload across devices

- **llama.cpp RPC — D.** The official RPC backend exposes remote devices and distributes model weights and KV cache across local and remote devices, with tensor splitting; the README labels it proof-of-concept, fragile, and insecure. This moves pieces of one model, not embeddings/RAG/web/rerank tools. [llama.cpp RPC README](https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md) (accessed 2026-09-14).
- **Petals — D.** Petals partitions large-model blocks across cooperating machines and pipelines inference/fine-tuning over a network. It is a major prior art for distributed model execution, but it is old, Internet-oriented, and not a phone-local conversational model with remote tools. [Petals paper](https://arxiv.org/abs/2209.01188) (2022-09-03; older), [Petals project](https://github.com/bigscience-workshop/petals) (accessed 2026-09-14).
- The related distributed-LLM literature generally optimizes placement, throughput, latency, or reliability of model blocks; it does not answer the capability-based split in C. [Distributed Inference over the Internet](https://arxiv.org/abs/2312.08361) (2023-12-13; older).

## 1. Measured energy cost of on-device phone LLM inference

- **Best absolute phone-level measurement found:** MNN-AECS measured five Android and two iOS devices and five models. For Qwen2.5-1.5B 4-bit over 20 ShareGPT conversations, total phone energy was 6,031 J at 9.9 W on Xiaomi 15 Pro, 10,438 J at 8.7 W on Huawei Mate 40 Pro, and 10,379 J at 7.9 W on iPhone 12; the runs consumed roughly 6–25% of battery in under 15 minutes. [MNN-AECS](https://arxiv.org/abs/2506.19884) (2025-06-24).
- **Prefill versus decode:** the same paper reports decode energy 16–26× higher than prefill for its conversational workloads. On Xiaomi 15 Pro, its phase-separated figure labels prefill at approximately 32–282 J and decode at approximately 498–4,617 J, with phase power roughly 8.8–9.7 W. These are workload totals, not universal J/token values; long-document prefill will change the balance. [MNN-AECS PDF](https://arxiv.org/pdf/2506.19884) (2025-06-24).
- **Prefill-specific optimization:** the llm.npu paper measures prompt lengths 64/256/1024 and reports, on a Redmi K60 Pro at 1,024 prompt tokens, prefill-energy reductions of 35.63–59.52× versus llama.cpp CPU, 35.21–59.25× versus MLC GPU, and 1.85–4.32× versus TFLite GPU. These are relative savings from a prototype, not absolute joules; power was sampled from Android’s power-supply interface at 100 ms intervals over three runs. [llm.npu](https://xumengwei.github.io/files/ASPLOS25-NPU.pdf) (ASPLOS 2025; arXiv 2024-07-08; older).
- **Newest context:** a July 2026 preprint measures energy per generated token across 18 configurations on two smartphones and reports on-device inference averaging 3× less energy-efficient than batched server inference; its abstract does not give phase-separated phone joules. [Battery Price of edge AI](https://arxiv.org/abs/2609.11940) (2026-07-10; under submission).
- A 2026 sustained-load study found thermal management, rather than peak compute, dominates mobile behavior: iPhone 16 Pro throughput nearly halved within two iterations and Galaxy S24 Ultra inference was terminated by an OS GPU-frequency floor. It reports no phone wattage in the abstract, but is relevant evidence that thermal budget is operationally material. [Mobile/NPU/GPU sustained-load study](https://arxiv.org/abs/2603.23640) (2026-03-24; revised 2026-06-07).

## 2. Measured energy cost of WiFi request/response

- **Recent power anchor, not a few-KB transaction trace:** a 2024 smartphone-energy paper’s compiled table reports WiFi infrastructure power of 868 mW connected, 58 mW idle, 26 mW idle power-save, and 1,450 mW while downloading at 4.5 Mbps; its ad-hoc figures are 979 mW transmit and 1,375 mW receive. The table combines that paper’s measurements with literature values, so treat it as an order-of-magnitude anchor, not a current-phone LLM comparison. [Sustainable smartphone energy table](https://doi.org/10.1002/sd.2995) (2024; source lineage partly older).
- **Direct few-KB WiFi measurement, but very old hardware:** Rice/Hay measured Android handsets and found WiFi connection setup around 1.5 J with static addressing and around 6 J with dynamic addressing. Incremental data energy ranged from a best case around 0.005 J/kB to worst cases around 0.13 J/kB on a G1 and 0.04 J/kB on a Nexus One; a few-kilobyte exchange therefore cost roughly 0.015–0.39 J for transfer alone in those tests, before connection/tail costs. [802.11 handset energy study](https://www.cl.cam.ac.uk/~acr31/pubs/rice-80211power.pdf) (2010; stale, but unusually direct).
- The practical comparison is thus: if the phone is already associated and awake, a few KB may be cheap relative to hundreds or thousands of joules of long local inference; if association/setup or radio tail is paid, the fixed 1.5–6 J old-device cost matters. This is an inference from the cited measurements, not a modern phone↔PC experiment.

## 3. When offloading stops paying

- The general mobile-offloading condition is an inequality: radio energy for request + response + waiting/coordination must be below local execution energy; the same paper notes that remote compute can improve response time while communication energy can erase the energy benefit. [Energy-aware computation offloading](https://www.sciencedirect.com/science/article/pii/S0164121215002666) (2015; older).
- **I could not find a published LLM-specific crossover number** such as “offload above N input tokens” or “above N KB” for a phone and a user-owned PC on the same LAN. Recent work uses profiled or learned device/network costs instead: CR² makes a query-level local-versus-edge utility decision and explicitly includes wireless overhead, but reports a policy improvement rather than a universal crossover. [CR²](https://arxiv.org/abs/2605.12001) (2026-05-12).
- For the proposed architecture, offloading ingestion/embedding is most likely to pay when the phone would otherwise prefill a long document and the PC returns a small, compressed evidence set. Returning the raw document to the phone forfeits much of the prefill saving. This is an engineering inference from the MNN-AECS phase measurements and the WiFi measurements above, not a published crossover result. [MNN-AECS](https://arxiv.org/abs/2506.19884) (2025-06-24), [WiFi study](https://www.cl.cam.ac.uk/~acr31/pubs/rice-80211power.pdf) (2010; stale).

## 4. Battery or thermal budget as the routing criterion

- **Production documentation:** Apple’s documented route is model capability/complexity and context size; Firebase’s documented controls are placement preference and availability. I found no Apple or Google documentation saying the default route is selected by battery percentage or thermal headroom. [Apple](https://developer.apple.com/documentation/foundationmodels/adding-server-side-intelligence-with-private-cloud-compute) (accessed 2026-09-14), [Firebase](https://firebase.google.com/docs/ai-logic/hybrid/android/configuration-options?hl=en) (accessed 2026-09-14).
- **Custom routing:** Google’s 2026 hybrid-inference guidance explicitly names battery status as a possible application-defined signal, alongside network and device model, but presents it as custom policy rather than the platform’s default criterion. [Android Developers](https://android-developers.googleblog.com/2026/07/build-intelligent-android-apps-cloud-hybrid-inference.html) (2026-07).
- **Research:** CR² is a clear recent example where energy is an explicit component of the local-versus-edge routing utility, alongside latency and accuracy; it is not specifically a battery-percentage or thermal-sensor policy. [CR²](https://arxiv.org/abs/2605.12001) (2026-05-12).
- Thermal budget is well documented as a constraint on phone inference, but I found measurement and runtime-optimization work rather than a shipped phone↔PC tool router whose primary trigger is temperature. [Sustained-load study](https://arxiv.org/abs/2603.23640) (2026-03-24; revised 2026-06-07), [FUSE](https://arxiv.org/abs/2507.02135) (2025-07-02; older).

## Searched for and did not find

- I could not find a shipped, end-to-end implementation that combines phone-local conversation with a personal-PC LAN service for all of: document ingestion, embeddings, retrieval, web fetching plus summarisation, and reranking. The closest found were [Pocket-RAG](https://github.com/TzeLun/Pocket-RAG) (retrieval endpoint; 2025/2026 access) and [mobileLLM](https://github.com/nanguoyu/mobileLLM) (generic remote MCP; 2026 access).
- I could not find a 2025–2026 measurement of a current phone’s incremental WiFi energy for a few-kilobyte request/response directly paired with an on-device LLM’s joules/token. The available direct per-KB result is the 2010 handset study; the 2024 source is a compiled power table.
- I could not find a published fixed phone↔home-PC LAN offloading crossover point in tokens, bytes, joules, or seconds.
- I could not find evidence that Apple Intelligence or Gemini’s default production routing uses battery or thermal budget; the explicit recent evidence is custom battery-aware policy guidance and research utility functions, not a platform default.
- Search coverage on 2026-09-14 included GitHub projects and documentation for Pocket-RAG, mobileLLM, LMSMOB Chat, Open WebUI, LocalMind, OnDevice-RAG-Android, llama.cpp RPC, and Petals; and papers/preprints for DRAGON, DGRAG, DRAG, TMO/LCIO, Language Model Cascades, CR², MNN-AECS, llm.npu, the Battery Price of edge AI, mobile sustained-load inference, and WiFi/mobile offloading energy.
