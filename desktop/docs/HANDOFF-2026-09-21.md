## 1. The goal, in one line

Each device — the PC and every paired phone — gets **its own conversation and its own cache
namespace** on one engine, so one person's context never becomes another's. Upstream
llama.cpp keeps one cache and cannot separate it per device, which is why this team
maintains an engine fork that reads `X-Kalsa-Slot` and `X-Kalsa-Cache-Salt`.

## 3. What was decided

- **Isolation is per device, not per chat.** A device holds a slot; a chat is what lives in
  it. Two chats on one device share the slot and the namespace.
- **One slot per device, each with its own context window, all resident**, in the
  **non-unified** form (`--parallel N`, pool `N × window`). Unified KV was rejected on
  measured grounds: it gains an idle-slot clearing path whose pressure valve is another
  device's warm slot (2 cold turns of 8 against 0 of 8 in the committed runs), and the memory
  it saves is 33.5 MiB at four slots.
- **The PC is device 1**, enrolled at startup, with no QR; its chat goes through the door
  like a phone's.
- **The disk tier is deferred**, and only for what RAM cannot do: surviving a restart and the
  idle unload, plus headroom beyond the prompt cache. Its preconditions are written in the
  plan's §5.
- **No number reaches the user interface before it is committed in a stripped artifact.**
  This rule exists because two versions of the plan were rejected for printing numbers that
  matched no committed file.

## 5. Where the bodies are buried

- **A local branch name is a footgun.** The app's local branch used to be `main` while
  tracking `origin/brain`; `origin/main` is the **phone** app, and a push there would have
  replaced its contents (3891 files, −486 622 lines). It is renamed `brain` now. Never push
  this repo to `main`.
- **`exe_sha256` is not a version identity.** `kalsa-server` is a thin launcher whose bytes
  are identical in v1.0.0 and v1.1.0. The archive sha256 is the identity. The live module is
  `libllama-server-impl.dylib`.
- **Engine invocation traps**: `--slots` is not the slot count (that is `-np`); the save route
  needs a JSON body (`-d '{"filename":"…"}'`) and answers HTTP 500 without one;
  `--ctx-checkpoints` is rejected spelled with a single dash; its default is **32**, which
  grows one chat's file to roughly 2.7 GB, so the app must pass **1**.
- **`--swa-full` is load-bearing** on sliding-window models: without it a save/restore was
  measured as a no-op for caching (`n_restored=613`, next request `cached=0`).
- **The save file carries no identity** — no device, no salt, no model hash. A
  dimension-compatible foreign file restores silently wrong, so any filename scheme must
  carry the facts the file does not.
- **The engine already has the cache version 1 wanted to invent**: the RAM prompt cache
  (`--cache-ram`) is an LRU of conversation states keyed by `{tokens, checkpoints,
  cache_salt}`. But under door-pinned slots its cross-slot load does not run, so a device's
  *other* chats are not warm today.
- **Agents leave engines running.** One session left four engines holding ~15 GB of RAM, and
  a measurement run was contaminated by an unrelated Android NDK build (8+ `clang` at 50-64 %
  each). Before any measurement, check `ps aux | sort -nrk3 | head` and kill what is idle.
- **A contaminated number is worse than none.** The measurement agent was right to reject
  four attempts, including one whose control arm agreed at 1.0028 while every absolute rate
  was depressed by the build — agreement between two equally-throttled arms proves nothing.
