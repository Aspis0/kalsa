## 2. What the plan got wrong

1. **It re-runs the §7.35 trap and calls it a campaign.** 16 turns + production config ⇒ empty digest corpus ⇒ ciswire ≡ off in every arm (STATE `:121-128`, §7.35 `:2944-2960`). Recall, decay slope, −170 tokens, KV reuse: all null by construction. The plan quotes §7.35 for the VACUOUS banner but doesn't apply its lesson to its own design. This invalidates Part 3 as written, not partially — the headline metrics cannot move.
2. **`computeDnaDeferral` port citation is wrong and the code is not stealable as-is.** Cited L364–429; actual `index.ts:463-521`. Its contract is `- [YYYY-MM-DD]` dated notes; Kalsa's store is 40 undated strings (`MemoryStore.ts:41,367,434,606`). Porting the semantics requires dating the store — unmentioned work.
3. **"A is byte-identical to today" is false.** Today = `anchored`. After S2, all-off = `off`. Either S2 changes the shipping default unmeasured, or arm A measures a config nobody runs. The plan asserts both "no behavior change when all off" (S1) and "remove anchored from user-reachable paths" (S2) — contradictory.
4. **§3.1 is re-armed as THE go/no-go after its own source closed it** (0/96 blanks post-fix, §1.1b `:601`; diagnosis resolved, §3.10 `:1186`). Defensible as a regression watch; indefensible as the primary decision gate given #30's power.
5. **Power arithmetic is absent and the premise rates are wrong-regime.** All speed premises (17.2 / 6.2 tok/s, sub-second prefills) come from the fase4 matrix, which §STATE says is hardcoded `thinking: "off"` — Part 3 mandates `thinking: "default"`. §7.9 measured think-block KV divergence at 295 s → 160 s per turn on the 2.6B's sibling (8B); the 2.6B shares `llm_arch_supports_rs_rollback == false` (KALSA.md §10). The plan uses thinking-off numbers to budget a thinking-on campaign.
6. **The §1.3 effect size is reused on a model its own source says the effect shrinks on.** +0.635 was measured on Qwen3.5-2B. §3.2 (`:933`): "the effect should shrink on the 4B — a stronger model holds more context and needs the crutch less." The 2.6B is the strongest small model measured (37/44). Expected benefit < +0.635; power is not recomputed.
7. **"The gate is already live unconditionally" is used as an argument but its consequence is unaddressed.** The toolhelp arms (D/F/G/H) extend web-tuned thresholds (0.40/0.15, question-mark regex) to calendar/miniapp inputs whose shape (dates, titles, no terminal `?`) has never been measured — §1.1b is a web-search measurement. "Start from measured §1.1b behaviour" overstates what was measured. Jest coverage is not campaign data.
8. **The 0.678 factor citation** points at "KALSA.md §7.38" — the factor is KALSA.md §2.1 row text anchored to HARNESS §7.38. Substance right, pointer wrong — in a doc whose own audit rules demand exact citations.

Per seed (16 turns; decode tokens/turn ≈ 300–350 — consistent with §7.42's implied 348 and §7.38's median 309; prefill from the §7.42 measured table: S23 34 563 ms cold → 240–277 ms → 3 068/6 122 ms at turns 12/16; Jelly 44 159 ms cold → 1.7–3.4 s, never <1661 ms):

**Jelly "≥2 overnight runs" verdict: survives only at face value.** 16 seeds ≈ 6–8 h of wall plus 3–4 physical recharge cycles — two unattended nights cannot do it (unplugged discipline + 30 % floor ⇒ someone must swap chargers mid-night). The budget has zero slack for: thinking-on prefill regression (§2.5 — the one variable that changes everything and is unmeasured), mortality retries, thermal pauses, or any re-run. S23 (~5–6.5 h + recharges) is feasible but has no budget line in the plan at all. **And none of it measures anything** — see finding #27: the corpus is empty in every arm, so all 48 seeds are §7.35 redux. The arithmetic only matters if the design is fixed (winbudget/legacywindow set low, or >40-message conversations).

## 4. What the plan missed

1. **The empty-corpus kill-shot (finding #27)** — the single largest defect; everything else in Part 3 is downstream of the regimes being identical at 16 turns.
2. **KV session restore between arms.** Restored session = 1.8 s prefill vs 120.8 s cold (STATE `:60-62`); disk restore 83.9 s → 1.5 s (§7.25). The plan records "cold-start vs warm state per turn" but never states whether arms start cold, warm-UFS, or restored — and **memory arms generate session files every turn** (`EXTRACT_MEMORY_PRESERVE_CHAT_KV`, `LlamaService.ts:3455-3545`), so turn-1 prefill and reuse metrics are not comparable across arms without an explicit policy.
3. **Extraction's own KV mechanics perturb the metrics it shares.** On memory arms, every turn ends with a snapshot + restore cycle on the engine. "KV reuse fraction on turn-after-tool" on a memory arm is measured *after* an extraction restore — a different mechanism than on a memory-off arm. The plan lists the metric but not the interaction.
4. **Model reload / repack between seeds.** Repack costs ~0.5 GB anon (§7.45); the per-model load policy from §7.52 "has never run on a phone". Part 3 is the first campaign to exercise it — unevenly, since memory arms load the same model but with different engines state paths. Load heat before turn 1 is unaccounted.
5. **Battery normalization.** `battery %/arm` is listed but starting % differs per arm unless the operator enforces full charges between all 48 runs; the §7.42 Jelly row drained 10 pts/16 turns, so a 40 %-start arm and a 95 %-start arm are different experiments.
6. **No multiple-comparison control.** 7 pairwise arm comparisons vs A plus 6 metrics; §1.3's exact p-values were per-pair with no correction, and Part 3 inherits that with 3× the comparisons.
7. **ε is undefined** in "empty-reply rate ≤ A + ε".
8. **The memory go/no-go's negative path is pre-written to a false negative.** "recall moves → keep flag; else park" — with an empty digest corpus nothing moves (finding #27), so organelle A gets parked on the same vacuousness §3.3 called "the empty-digest disaster with a different name". The plan's own §3.3 citation warns against exactly this re-derivation.
9. **New flag key collision.** `kalsa.ciswire.memory` is introduced next to the live `kalsa.memory.enabled` / `kalsa.memory.facts` (`MemoryStore.ts:39-40`) without stating precedence or migration; an enabled `kalsa.memory.enabled` user would silently violate "off must be byte-identical".
10. **Terminology collision (finding #20).** "operative block" means digest/summary in this codebase (`operativeBlock.ts:32`, `AppShell.tsx:4758`). S3's "operative block freeze" will freeze the wrong object unless re-named to the memory-facts block.
11. **State-cache freeze vs extraction.** The "232–553 ms state-cache hits" (turns 2–11, S23) were measured without a per-turn extraction; on memory arms the cache survives a snapshot/restore per turn — the sub-second hit rate transfers only if the restore is truly lossless, which §7.49's attribution defects suggest measuring, not assuming.

Bottom line: the plan's history (Part 1, Part 2 rules) is almost entirely accurate on disk — the verification list in §1 passes 24/32 with only citation-level faults. The engineering design (Part 3) fails at its core: the benchmark cannot run as specified, the control arm is not the shipped config, the decision gates are underpowered by 4–16×, and the tightest budget claim ("≥2 overnight runs on Jelly") holds only if every unmeasured thinking-on premise behaves and nothing goes wrong.
