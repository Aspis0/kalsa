## 1. The goal, in one line

Each device — the PC and every paired phone — gets its own conversation and its own cache namespace
on one engine, and a chat's KV cache **survives being put on disk and comes back warm**. Upstream
llama.cpp keeps one cache and cannot separate it per device, which is why this team maintains an
engine fork that reads `X-Kalsa-Slot` and `X-Kalsa-Cache-Salt`.

## 3. What this session decided

- **The disk tier is built now** (owner's call), and it is its own plan: `docs/PLAN-DISK-TIER.md`,
  version 2, hostile-audited and corrected. Isolation stays per **device**, not per chat.
- **`--swa-full` is not a launch flag of the tier.** Measured, twice, with the harness fixed:
  the flag moves the save file's size and nothing about warmth. The ~1.4 GiB it would have cost on
  one 64k slot is not paid.
- **Identity lives in the file name, built by the door**, and the **salt does not enter the name**:
  the salt is a hash of the credential, so a re-pair would turn a name carrying it into silent data
  loss. The door builds `d<device>-m<hash8>-c<conversation>.bin` and validates the conversation id
  shape; a dot or a slash is a refusal, never a sanitisation.
- **The residency map is the door's own**, keyed by slot. Whoever says which chat was resident
  decides **which file the slot's state is written into**, so the caller never says it.
- **The slot has three states**, `Empty | Unknown | Resident(device, chat)`. On an engine that never
  answered the state is `Unknown`, the sentence says unknown and never "empty", the restore is not
  repaired, and the next activation **does not save** — it will not write out a slot's content it
  cannot name.
- **A save is staged**: it goes to `<name>.staging` and the real file is replaced **only when the
  engine reports `n_saved > 0`**; a reply without that field is unreachable, never a success. This
  is what stops a sleeping engine from writing an empty state over a real chat.
- **The webview waits for the door** before a chat becomes active. Reason: the door serialises
  pagination per slot, but **a completion does not pass that gate**, so an optimistic switch lets the
  activate's deferred erase/restore wipe the state the completion just built — losing exactly the
  warmth the tier exists to give.

## 5. The measurements, and what they proved

- **`dev/results/slot-restore-device-path/`** (`b3ded12`) — the one that matters. With the fixed
  harness, all eight arms come back warm: 1895 of 1900 tokens with a full context, with and without
  the flag, with and without a salt. `cold_arms: []`. The disk footprint measured at ~53 KB per
  token without `--swa-full` and ~30.5 with it (≈ 218 MB against ≈ 125 MB per chat at the 4096-token
  floor).
- **`dev/results/slot-restore-swa/`** (committed earlier) — kept as written. Its `salted` rows are
  **not** the device path (the harness defect below); its conclusion, that the namespace and not the
  flag was the variable, is what pointed at T1.
- **The concurrency figure does not exist.** It is a rate, so it needs an idle machine, and the
  machine was not idle. It gates T6's number only.

## 6. Where the bodies are buried

- **The harness never sent the salt on the slot actions.** `slot_action()` called `post()` without
  `salt_hex`, so `save`/`erase`/`restore` reached the engine with no `X-Kalsa-Cache-Salt`; the
  "salted" arm meant "completion salted, slot actions unsalted", a path no client produces. **The
  door does send it** — `crates/kalsa-door/src/engine.rs:67` calls `request::private_headers`, which
  writes both headers, because the door's own call has to read as the same device.
- **A stale engine satisfies a health check.** A re-run was discarded whole because the fresh engine
  logged `couldn't bind HTTP server socket … port: 19313` and exited, while `wait_health` was
  answered by an engine left alive by an interrupted run, writing into the **previous** work
  directory. `Server.start` now refuses a port that already answers and a child that exited during
  boot. Its first version had a false positive: a port in `TIME_WAIT` is bindable by the engine and
  was not by the probe, so the probe sets `SO_REUSEADDR`.
- **A field that can lie is worse than no field.** The harness hardcoded a `blocking_mechanism`
  string naming the namespace defect; it would have been false in the run that proved the defect
  gone. It is now derived: `cold_arms`.
- **Killing a measurement needs the right pattern.** `pkill -f "llama-server --host 127.0.0.1
  --port 1931"` matches nothing, because `-m <model>` sits between the binary and `--host`. Kill by
  the binary path: `pkill -f "/kalsallama/build/bin/llama-server"`.
- **`brain` is not `main`.** The app's remote (`github.com/Aspis0/kalsa.git`) is the **phone** app's
  and holds two lineages: `origin/brain` (ours) and `origin/main` (the phone app, 911 ahead of the
  merge base). There is no local `main`. Never check it out, never push to it.
- **The app's engine holds port 8130**, and the engine's own test suite gives xdist worker 5 port
  `8080 + 5*10` = 8130 (`tools/server/tests/conftest.py:7-13`). Running that suite in parallel while
  Kalsa Brain runs produces a red that has nothing to do with the code. Serial, or with the app closed.
- **Pins must assert the exact pair, exactly once.** `contains("--ctx-checkpoints 1")` is true of
  `--ctx-checkpoints 12`, and a helper reading the first occurrence lets a duplicated flag through.
  Both were measured: a mutation left 49 plus 151 tests green before, and turns red after.
- **A neutral failure sentence must be declared, not omitted.** `failure.rs:347-360` requires an
  action word; a cause the user cannot act on joins the named `unrecoverable()` list, and the same
  test asserts an exemption does not also give advice.
- **The engine's save catch does not clear the slot; the restore's does** (`server-context.cpp:2812-2819`
  against `:2885-2889`). That is why a refused save keeps its residency and a refused restore rolls
  back.
- **T1 is in no release.** The app pins the `kalsa-server-v1.1.0` archive; `origin/b11010-merge` is
  `5c96b18dd`. A shipped disk tier needs a new engine release carrying `833cde99b`.

## 7. Standing rules

- **Nothing goes upstream.** No PR, issue, comment, review, patch or discussion. Upstream is read,
  never written.
- **No push, tag or release without the owner's explicit OK.**
- **One branch per repo** — the app on `brain`, the engine on `main`. Nobody creates another.
  **A branch is not an artifact: delegate and review by commit hash.**
- **Stage by name** (`git add <file>`), never `-A` and never `.`.
- **Workflow**: Explorer (recon, no sub-agents) → the orchestrator writes the plan → a hostile audit
  → fix → delegate with Coder and Reviewer on **different models**. An errored review is a lead,
  never a pass.
- **No number reaches the user interface before it is committed in a stripped artifact.**
- Files under ~400 lines for anything new; pre-existing excess declared, not refactored. Comments
  only for WHY or a trap. No secret **values** anywhere.
- Paseo: `create_agent` wants `title` first and **`title` ≤ 60 characters**; `zcode-acp` needs an
  explicit `modeId` and never `auto`. Profiles today: Explorer/Coder `pi/CC2/deepseek/deepseek-v4.1-flash`,
  Reviewer `zcode-acp/builtin:zai-coding-plan\GLM-5.3-Flash` (`modeId: edit`, thinking high).
- One coder at a time: two delegates committing on the same branch share the index.
