# The night run: what was asked, what was measured, what is broken

Six things were asked for. Two of them were testable, three are blocked on a half that does
not exist yet, and one turned out to be already covered by tests nobody was running. Every
number below was measured on this machine tonight; nothing here is inferred from reading.

## 0. The blocker that reshapes the list

**The phone cannot pair. There is no pairing on the phone side at all.**

`/Users/marco/Projects/kalsa` has no pairing screen (`src/screens/` holds Account, AiChat,
Documents, Help, Notes, Personas, Pro, Reasoning, Settings), no camera or barcode dependency
in `package.json`, and the words *brain*, *door*, *credential*, *tailscale* appear in exactly
one file — `src/i18n/en.ts:886`, inside an unrelated sentence about privacy. The `kalsa://`
scheme is registered but handles only `share?text=` and `share?file=` (`src/app/shareIntent.ts:2`).

So this computer has a complete, measured, tested pairing ceremony that no phone can complete.
Requests 2, 3, 4 and 6 all stand behind that handshake. They are not bugs waiting to be found;
they are a half waiting to be written.

## 1. A download has no timeout, anywhere, and hangs forever — CONFIRMED

`grep -rn "timeout" crates/kalsa-download/src/*.rs` returns **nothing**. The transport is
`ureq = "2"` (`Cargo.toml:12`), whose agent has no read timeout unless one is set, and the
loop is a bare blocking read:

```rust
        let read = reader.read(&mut chunk)?;      // fetch.rs:72
```

A server that accepts the connection and then stops sending — flaky Wi-Fi, a hotspot that
drops, a CDN edge that stalls without resetting — freezes the download **forever**. The bar
stops at "2.1 of 3.8 GB" and never moves again: no error, no retry, no sentence.

The cruel part: the app already owns the right words for this — *"The connection dropped
partway through. Trying again keeps what was already downloaded."* — but that path is only
reached when the OS reports a reset. A silence is not a reset, so it never arrives.

**The proof is a live process.** A `kalsa-download` test binary has been hung since
**Mon Sep 14 14:13:49** — three days and ten hours — orphaned to launchd, 0% CPU, holding four
listening sockets and a half-written file:

    /tmp/kalsa-download-fetch-overrun-47263/model.gguf.part

Fix: set a read timeout and a connect timeout on the agent. A stalled transfer must become the
dropped-connection message the app already has.

## 2. The same hole makes a test hang forever — CONFIRMED

The process above is a test, not the product. A test that can block with no deadline is a CI
job that never returns, and it leaks four sockets and a temp directory each time. The hang and
the product defect are one bug seen twice.

## 3. The instance guard wakes ten times a second, forever — CONFIRMED

Written tonight, by me. `instance.rs` puts the listener in non-blocking mode and then spins:

```rust
                    Err(error) if error.kind() == io::ErrorKind::WouldBlock => {
                        std::thread::sleep(WATCH_POLL);          // 100 ms
                    }
```

Ten wakeups a second for the whole life of the app, to notice an event that happens when
someone double-clicks the icon twice — perhaps once a week. A blocking `accept` on that thread
costs zero wakeups while idle; stopping it means closing the listener or knocking on it once.

## 4. Every panel polls forever, including while hidden — CONFIRMED, and it is not the cost

    src/pages/status.js:7     POLL_MS = 1000
    src/pages/model.js:8      POLL_MS = 2000
    src/pages/pairing.js:86   POLL_MS = 2000

and the four newly ported surfaces add 1000 ms + three at 2000 ms. `grep -rn
"visibilitychange\|document.hidden" src/ chat/src/` returns **nothing**: minimise the window,
cover it, walk away — it keeps crossing the IPC bridge once a second. That is still worth
fixing; a window nobody can see should not be asking questions.

**But it is not where the battery goes, and neither was the spinning guard.** Both were my
predictions and both were refuted by measuring, so they are recorded here as refuted rather
than quietly dropped.

The first measurements were also wrong in method: they counted only the shell process. On
macOS a Tauri app's web half runs in separate WebKit processes which are not its children, so
they never appeared in the total. Counted properly — the shell plus the three WebKit processes
that appear when it launches:

    WHOLE APP idle, release build, no model:  1.20 CPU-seconds / 60 s = 2.0% of one core
      the shell itself                        0.89 s
      the three WebKit processes              0.31 s combined

Then the two hypotheses, each tested by changing one thing:

    guard spinning at 10 Hz  ->  blocking accept :  1.6%  ->  1.5%   (shell only)
    polls at 1-2 s           ->  polls at 60 s   :  1.5%  ->  1.4%   (shell only)

Both inside the noise. And `sample` on the idle process shows the main thread parked in
`mach_msg2_trap` for 6132 of 6138 samples — it is asleep in the event loop, not spinning.

So roughly two percent of one core is what an idle WebKit window costs on this platform, and
our code is not meaningfully adding to it. The owner's instinct about Tauri apps is half right:
the floor is real, but the floor is the platform's, not ours. The battery villains on this
machine are in section 7, and they are three orders of magnitude larger.

One thing the profile did turn up: five live threads named `kalsa-pairing-worker-0..3` and
`kalsa-pairing`, a pool standing ready for a ceremony that, per section 0, no phone can begin.

## 5. `main.rs` promises a backstop the platform does not have — CONFIRMED

```rust
        // The platform backstop (job object, pdeathsig) covers the exits
        // that run no handler at all.
```

Job objects are Windows, `PR_SET_PDEATHSIG` is Linux. macOS has neither, and this is the
platform the app is developed and demonstrated on. `crates/kalsa-supervisor/src/child.rs:11`
is honest about it — *"macOS has neither; see the README for what that costs"* — and
`tests/orphan.rs` opens by naming the hole. Only `main.rs` implies it is covered, and `main.rs`
is where a reader looks to find out what happens on quit.

## 6. The orphan defence is keyed to a file that can go missing — CONFIRMED, live

The documented macOS mitigation is that *the next start recognises the survivor* from a
recorded state file. Right now:

    pid 53905, started Thu Sep 17 10:12:13, up 14h, parent = 1 (orphaned)
    RSS 3.6 GB
    http 200 on 100.74.116.126:8133  — answering the whole tailnet, unsupervised

and `~/Library/Application Support/kalsa-brain/runtime/` contains **no state file naming it**.
Nothing records that process, so no future start can adopt or kill it. It holds three and a
half gigabytes and an open inference endpoint until the machine reboots.

This is the same shape as the lock bug fixed in `d319390` tonight: a defence that lives in a
file, guarding something that outlives the file. Worth fixing the same way — tie the record to
the thing, not to a name that can be swept away.

## 7. Not ours, but it is where the battery goes

    pid 80356  /usr/bin/caffeinate -s -i   started Sat Aug 29 14:00:15, orphaned
    PreventUserIdleSystemSleep + PreventSystemSleep, held 466 hours

This Mac has not been allowed to sleep for nineteen days. kalsa-brain holds no power assertion
of its own — verified — so this is someone else's forgotten command, but any measurement of
"why does the battery die" has to start here, not with an app burning 1.6% of a core.

So request 2 — *the AI on the PC works* — is true on the computer's side, end to end: it

The whole workspace is green: **508 passed, 0 failed, 10 ignored**, real exit 0. It was red

being run and `cargo test` stops at the first failing crate — so half the workspace was never
reached. `--no-fail-fast` is what showed it.

Those tests also clean up after themselves: no new orphan appeared after running every one of
them. The three leftovers on this machine predate tonight.

## What was not done, and why

- **Driving the desktop UI through all its options.** There is no way to click a Tauri window
  from here. What was reachable — the command layer, the 39-state review harness, the real
  binary launched and observed — was exercised. The rest needs either a hand on the mouse or a
  webdriver the project does not have.
- **Chat history on both devices, with a badge for where it started.** Nothing to test: the
  phone and the PC do not share conversations at all, which `WHAT-IS-MISSING.md` §8 already
  records. The badge is a feature request, not a defect.
- **Tailscale interruptions.** Standing behind the same pairing that does not exist. The one
  piece that could be tested without it — that the road carries HTTP by node id — passes.
