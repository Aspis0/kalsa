## 1. The app runs end to end on Windows, on two machines

passes twice in a row, at `7b77116`, on:

- **the Surface**: Surface Laptop 3, i7-1065G7 (4 cores / 8 threads), 16 GB, Iris Plus (integrated),

- **the Lenovo**: Core Ultra 9 185H (6 P + 8 E + 2 LP-E = 16 cores / 22 threads), 32 GB, NVIDIA RTX 4050

On both machines a stop ends `(stdin, kill): Gone { needed: Kill }; process Reaped; port … — Gone`, and

## 2. Threads: the rule I decided

`--threads` and `--threads-batch` = min(probe plateau, physical cores), in `3d9e45e` and `8e90570`.

The evidence is decode (tg128) in tokens per second, two runs per thread count, from llama-bench on the CPU
with Gemma 4 E4B Q4_K_M:

| Machine | Measured | Plateau | Physical | Under the rule |
| --- | --- | --- | --- | --- |
| Lenovo, session 1 (b10950, `-fa 1`, q8_0 KV) | 6: 8.1 / 8.1 · 12: 10.8 / 9.5 · 16: 11.6 / 11.9 · 22: 7.6 / 9.7 | 22, 16, 16 in three probe runs | 16 | always 16 |
| Surface (b10950, `-fa 1`, q8_0 KV) | 4: 10.2 / 9.9 · 8: 11.2 / 11.2 | 4 | 4 | 4, unchanged |
| M1 Max, CPU only (build 11193, f16 KV, a busy machine) | 8: 24.5 / 27.7 · 10: 9.6 / 17.6 | 8 | 10 | 8, unchanged |

What the rule buys: on the Lenovo the probe once chose 22. In session 1, 22 decoded 26.5 % slower than 16
(n = 2 runs per count; the two 22-thread runs were 29 % apart).

A second, noisier Lenovo session measured 14, 16 and 20 threads, and it separates nothing. Its lowest run
was 20 threads at 6.7.

What the rule leaves: on the Surface, 8 threads decode 10–14 % faster than 4, and the rule still gives 4.
No simple topology rule fits all three machines, so I did not chase one. More PCs would refine the rule,
but one more machine would not settle it.

## 3. The graphics card: what the Lenovo showed

With `-ngl 99` on the Vulkan build, the E4B decodes at 49.1 and 49.8 tok/s and prefills at about 2500
tok/s. That is about 4.2 times the same machine's best CPU decode, 11.8 at 16 threads. These are benchmark
figures, not the app. A second run pinned to the RTX 4050 (`--device Vulkan0`) matched them, and in both
runs the Intel Arc held no buffer.

The app does not use the card. The catalog keeps a margin of `max(3 GiB, 25%)` (`footprint.rs`), which
leaves a 6 GiB card with a 3 GiB budget, and no catalog row fits that. Tonight's fallback therefore runs
the E4B on the CPU instead of refusing the machine.

What the card actually held, from llama-server's own `-v` log at ctx 4096:

| Buffer | Size |
| --- | --- |
| Model weights on Vulkan0 (the 4050) | 2883.51 MiB |
| KV cache | 34.00 + 21.25 MiB |
| Compute | 126.30 MiB |
| Total device allocation | 3065.06 MiB (nvidia-smi: 3079 idle, 3089 during a completion) |
| On the host, as `CPU_Mapped` | 2208.00 MiB |

The host buffer holds `token_embd.weight` and `per_layer_token_embd.weight`. The log says they "cannot be
used with preferred buffer type Vulkan_Host, using CPU instead".

With no server running, nvidia-smi read 0 MiB used on the card. The capture does not say which adapter
drives the screen.

So the catalog sizes the E4B by its pinned file, 4 977 171 584 bytes, while the card's allocation at
ctx 4096 was 3065 MiB. This is one run. It establishes nothing for other contexts, other E-series files or
CUDA.

## 5. Questions for the owner

1. **The card's margin.** 3 GiB of a 6 GiB card is kept back. With no server running the card read 0 MiB
   used, and the E4B's device allocation was 3065 MiB. A sufficiently smaller VRAM margin would put this
   laptop on the GPU, but a small cut would not: the catalog sizes the E4B by its whole file. The
   benchmark ratio is about 4 times, and no app run on the GPU has measured it.
2. **Copy I wrote tonight, which you have not seen:**
   - "No model fits this computer's graphics card's memory, so this model runs on the processor." The
     reviewer notes that it means the *usable* memory, after the margin.
   - "This computer could not use the model file on its own disk. Trying again usually works; if it keeps
     failing, another program may be holding the file." A persistent disk-query error is not helped by
     retrying.
   - "The server that publishes the model did not allow the download just now. Trying again later usually
     works." A permanent 403 or 404 is not helped by trying later.
3. **Old copy that is sometimes false.** "The connection dropped partway through" also covers a DNS failure
   and a refused connection. "Trying again usually works" is not true for a server that always sends too
   much.
4. **The chat's remote-server setting does not work.** Neither CSP admits a remote origin (both allow only
   `'self'`, the IPC channel and loopback), and nothing fetches on the page's behalf. A remote endpoint is
   therefore blocked, in a built binary and in dev. Remove the setting, or make it work.
5. **The four seats on the first screen are still one boolean.** The data exists (the door's presence plus
   the paired list), but drawing them changes what the first screen looks like.
