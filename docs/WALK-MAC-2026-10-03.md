## 1. Bugs, ranked

### P1-1 — Every PDF fails to attach

- **Repro:** paperclip → open panel → pick a PDF. Tried three: a 15 KB `cupsfilter` PDF, a
  677-byte hand-built Type1 text PDF (`BT … (Mini report…) Tj ET`), both from `/tmp`.
- **Expected:** text extracted, file listed under Attached.
- **Observed:** red refusal "Kalsa couldn't read this file. It may be damaged or locked with
  a password." Log: `ui: chat.attach_failed` (10:29:57, 10:30:49). `.txt`, `.md`, `.csv`
  and `.docx` attach and answer correctly in the same session, so the file picker and the
  extractor wiring are fine.
- **Why (unproven):** `lib/attachments.ts:250` is a bare `catch {}` — the real pdf.js error
  is thrown away, so the screen cannot say. Prime suspect: pdf.js's worker loaded by URL
  (`attachments.ts:2,108`) under `tauri://` with a CSP that sets no `worker-src` in either
  `chat/index.html:21-23` or `tauri.conf.json:25`. `docs/WHAT-IS-MISSING.md:775` already
  warns that the CSP guard cannot see `worker-src`. I could not open devtools in the release
  build to confirm.
- **Also:** the copy still advertises it — `i18n/en/files.ts` `unsupportedKind`: "Use a text
  document, **PDF**, Word or PowerPoint file." (shown when I tried the `.png`).
- **Confidence:** failure high (3/3); cause low.

### P1-2 — Stop does not stop the model; the next message waits behind it

- **Repro:** send a long request (e.g. "write 1500 words…"), press Stop mid-answer, watch the
  engine, then send anything.
- **Expected:** generation ends; the next message is answered at once.
- **Observed:** the UI stops ("Stopped early — showing what arrived."), but the engine keeps
  generating the abandoned answer to the end. Door durations, stop → completion logged:
  - turn 3: Stop 10:22:49 → `POST /v1/chat/completions … 79893ms` at 10:23:06 (17 s later);
  - turn 4: Stop 10:24:18 → completion at 10:25:18 (60 s later). `top` on the engine pid, every
    2 s after Stop: `90 105 131 164 127 136 148 143 134 141 136 133 %` CPU for ≥ 26 s. At
    10:24:56 the door's own save of the chat failed:
    `chat idle: slot 0 … code door.engine_unreachable 10000ms` — engine still busy;
  - Stop 10:26:04, then a one-line question at 10:26:12: its request took 18.5 s
    (`18492ms`, logged 10:26:30) — it queued behind the dead answer;
  - whale/heron: Stop 10:55:14 → whale completion 10:55:45; heron (sent 10:55:23) took 72 s.
- **Why:** `crates/kalsa-door/src/stream.rs:78-88` keeps pulling an "answer nobody is
  listening to" until `detached_grace` (2 min, `clocks.rs:41`) so a phone can resume. But the

  engine's slot until the ceiling" — it does. The desktop never resumes, so the grace is pure
  cost there. Mechanism is my reading of the code; the timings are measured.
