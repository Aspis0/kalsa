## Findings

### 1. Numerics of 23178fb24

**1.1 REFUTED (my main suspicion was wrong, and it is worth recording).** The odd fan-out table
looked broken: lane 5's odd control byte is `0x02`, which under a naive `out[i]=in[i^ctrl[i]]` model
selects a *quant* byte instead of the block scale, and lane 31's is `0x02` where `0x12` would be
needed. HVX `vdelta` is not a per-byte XOR, it is the 7-stage butterfly (stages 64,32,…,1); under
that model both tables route every lane's scale correctly and lane 5's junk lands on bytes the
paired multiply never reads. `q4_0-raw-mv-geometry.h:40` (the odd table) is **correct**, and the
in-tree check is real, not a copy of the generator:
`raw-mv-sim.c:52  hvx_vmem(odd)  = Q6_V_vdelta_VV(hvx_vmem(in), hvx_vmem(raw_mv_scale_fanout_odd));`
I re-ran it and controls 9/10 (both EXIT=1). Failure scenario: none.

**1.2 CONFIRMED — bit-identity holds; the last-window/group-end rows cannot diverge.** My worry was
that `raw_mv_load_last(row_end, /*group_end=*/true)` zero-fills bytes 126–127, which are the *odd*
halfword of lane 31 — the very lane whose scale now has to come from the odd table for row b. It
cannot leak: `q4_0-raw-mv-hvx.h:65  const HVX_Vector fanned = Q6_V_vmux_QVV(odd_halves, Q6_V_vdelta_VV(raw_b, fanout_odd), Q6_V_vdelta_VV(raw_a, fanout_even));`
— `vdelta` *overwrites* bytes 126–127 with block 6's scale (source bytes 108–109), whatever the load
put there. Per-row uses the even halfword, paired uses the odd; both get the same scale. The gate
covers this: shapes n_k ∈ {8,9,13,63,64,65,71,336} × rows {1,5,17,31,32} (n_k=9,13,63,65,71 are the
pulled-back/overlapping last window; rows 1/5/17/31 exercise partial groups) — all `bits`.
Also true by construction: the fp accumulation order is unchanged (one `vadd(qf32)` per window per
row, same sequence), the two rows' sources are two *different weight rows* with two independent
`vdelta`s on their own `raw[i]` vectors, so no cross-row contamination is possible.

**1.3 CONFIRMED (weakness in the evidence chain, not in the code).** The in-tree gate proves
`paired == per_row`. It does **not** prove `per_row == df538c50c`; the report's strongest claim —
"120 cases (8 shapes × 5 row counts × random / d=1 / edge-scale data), bit-identical
(`old-vs-new-bits.log`, scratch harness `zz-old-vs-new.c`, **not in the tree**)" (REPORT §4) — is not
reproducible from the repo. The link is a structural argument (per-row consumes only
`Q6_V_lo_W(scales)`, so the new `ascale[l] = scale_bits * 0x10001u` odd halfwords are dead for it),
which I checked by hand and which holds. Failure scenario: someone later makes the per-row path use
the hi half, or the arrangement change is reverted; nothing in the tree fails, and the device arm L
would silently differ from O. Recommendation: keep a copy of the old-header harness in
`tests/hexagon-sim/`.

**1.4 CONFIRMED (unpriced cost, this is the real hostile finding).** The pairing is not free: keeping
`raw[4]` live across the window loop costs registers, and the shipped default dot allocates **0x500
(1280 B) instead of 0x400 (1024 B)** and touches the frame with **29 vs 23 `vmem`** per unrolled
3-window body (+6, i.e. +26 % of its spill traffic). The worker stacks are DDR-backed rpcmem, not
VTCM (`main.c:42 WORK_QUEUE_STACK_SIZE 16384`, `work_queue_init(..., mem_blob, ...)`), so this is
extra stack traffic in the exact loop the S23 ABBA fingered. REPORT §3's two-parameter fit
(Cp ≈ 2.03 G packets/s, Cv ≈ 1.30 G slots/s) has **no term for stack traffic at all**, so the
prediction "if the multiplier is the limiter the prediction is ~17.9 tok/s" silently assumes the new
spill is free. It is the same order as the claimed gain (one multiply slot ≈ 17 %). Failure
scenario: N ≈ L, and the report's causal story ("multiply slots are the limiter") is falsified —
which is a legitimate scientific outcome, but the report should have flagged the spill as a
confound *before* the run, not after. The N-vs-L arm measures the net either way; the arms are the
experiment, the 17.9 is not.

**1.5 REFUTED — F16 vs F32 activations are not a live case.** `matmul-ops.h:102-104`
`static inline bool htp_mm_raw_act_admitted(bool is_f32, uint64_t nb0) { return is_f32 && nb0 == sizeof(float); }`
and the op-level check `ggml-hexagon.cpp:2251` refuses anything else, so the raw-row kernel never
sees F16 or strided activations. (The "F16/strided" work in `ceb89bedc` was the *admission* check.)

**1.6 REFUTED — K < 256 is not a case.** `matmul-ops.h:27
#define HTP_MM_RAW_MV_MIN_K ((HTP_MM_RAW_MV_WINDOW_BLOCKS + 1) * 32)` = 256, enforced in
`htp_mm_raw_kernel_admitted`; n_k=8 is the smallest gate shape, i.e. the minimum admitted K is the
first one tested.

**1.7 PLAUSIBLE — probe 16's outputs are NaN-bearing, probe 1's were not.** In `RAW_MV_INT_ONLY`
the accumulator holds int lane sums and is finally reinterpreted as float
(`Q6_Vsf_equals_Vqf32(hvx_vec_reduce_sum_qf32(acc[i]))`). Any small negative sum (e.g. −1 →
`0xFFFFFFFF`) is an fp32 qNaN, so arm I's logits will contain NaNs where the ABBA's P1 arm had
zeros. No abort is expected (llama-bench samples an argmax; the tiled prefill path is untouched), but
the report's "output garbage by design" understates it, and no gate distinguishes "ran and produced
NaNs" from "ran and produced the real thing".

**1.8 No rounding/lane-order hazard found.** `Wqf32_vmpy_VhfVhf` is a lane-wise fp16 multiply whose
lo/hi halves are the even/odd halfword lanes (the convention the baseline already relied on at
`Q6_V_lo_W(scales)`); `Vqf32_vmpy_VsfVsf` is lane-wise fp32. Both halves go through the same
pipeline, so rounding/denormal behaviour cannot differ between row a and row b. `scale_bits *
0x10001u` (`q4_0-raw-mv-act.h:34`) is exact for any `uint16_t`. The new `uint32_t *` store needs
4-byte alignment at `win+384+4l`; `win = act + w*512` and the buffer is already vector-aligned (the
pre-existing `hvx_vmem(win + 3 * VLEN)` store demands it), so no new alignment requirement.

### 2. Host chunk sizing (6a6ec8678)

**2.1 CONFIRMED — the host is now exactly the DSP's requirement at every row count, not just 32.**
`matmul-ops.h:330  static inline bool htp_mm_hmx_pipeline(uint32_t m, bool raw_weight) { return raw_weight || m > 32; }`
against the DSP's unconditional `matmul-ops.c:2690  if (raw_q4_0) { pipeline = 1; }`. There is one
solver call site (`ggml_hexagon_precompute_hmx_mm_params`, two callers: `:4773`, `:5029`), the DSP's
layout builder is called with identical arguments on both sides (`matmul-ops.c:2738` vs
`matmul-ops.h:704`), and both use the same budget (`vtcm_budget = sess->vtcm_size` vs
`ctx->vtcm_size` — v73 8 MiB, which the overflow log in the ABBA corroborates). `is_matmul_id` is
excluded at the call site and is unreachable for raw weights anyway (`ggml-hexagon.cpp:2251`), and no
fused kernel admits raw weights (`:5983`).

**2.2 CONFIRMED — the new host test is not vacuous, and it does reproduce the old failure.** I built
and ran it: `EXIT=0 / ALL PASS / 8 solves overflowed under the old rule`. It carries its own
premise guard (`tests/test-hexagon-hmx-raw-fit.c:57  if (old_overflows == 0) { printf("FAIL premise: ...`),
so it cannot pass after the defect stops existing, and substituting the old predicate makes the
`now` column overflow and the run fail.

**2.3 CONFIRMED (process gap) — the test is invisible to CI.** Its own header says so:
`tests/test-hexagon-hmx-raw-fit.c:8  // Not registered with CTest (HTP headers)`. Nothing in any
automated run re-checks the host/DSP VTCM contract, so a later edit to `htp_mm_hmx_pipeline` or to
`if (raw_q4_0) pipeline = 1` silently reinstates the `dsp-rsp INTERNAL-ERROR` abort — the very bug
this commit fixes. Fixing it is cheap: the test compiles with plain `cc` and the two htp headers
(I did it in 3 s); add it to `tests/CMakeLists.txt` guarded by nothing special.

**2.4 PLAUSIBLE — the fix re-derives a DSP-side fact on the host, and nothing tests the equality.**
Host: `ggml_hexagon_is_raw_weight` (`ggml-hexagon.cpp:2178`) = hexagon buffer + WEIGHTS usage +
`extra->flags & GGML_HEXAGON_TENSOR_REPACK == 0`. DSP: `htp_mm_has_raw_weight`
(`matmul-ops.c:371`) = `quant && !(w->flags & HTP_TENSOR_REPACK)`. The type lists match
(`ggml-hexagon_is_repack_type` covers exactly the 7 DSP quant types), so they agree today; if a
placement bug ever gives the DSP a non-REPACK quantized weight the host does not classify as raw, the
host solves single-buffer and the abort comes back, with nothing failing until a device run.
Failure scenario is far away, but it is the same class of bug as the one being fixed.

**2.5 CONFIRMED (coverage, benign) — the test's row list is {32,33,128,512}.** `m < 32` is untested,
which is harmless: the solver aligns `m_chunk` to 32-row tiles, so every m ≤ 32 produces the m=32
layout. Only one model's K/N set is tested; other models are uncovered, but a solver failure would
now *fall back* (host picks another kernel) rather than abort.

**2.6 REFUTED — forcing `pipeline = 1` cannot make anything worse.** It only shrinks the solved
chunks; if the solver cannot fit, `htp_mm_hmx_solve_2d_params` returns false and the host takes
another path. Pre-fix, "solver succeeded" meant the DSP rebuilt the same chunks double-buffered and
returned −1 (`matmul-ops.c:2742 return -1;` → `HMX matmul failed` → `HTP_STATUS_INTERNAL_ERR`).

### 3. Diagnostic dots (7e4945582)

**3.1 CONFIRMED — the strict parser accepts 8/16/32 and combinations with 1/2/4, and refuses two
dots.** `ggml-hexagon.cpp:7494-7498` gates on `(probe & ~probe_bits) == 0 && (dot_bits & (dot_bits-1)) == 0`,
so 1|8, 2|16, 4|32, 5, 7 are accepted and 24/40/48/56 are refused with the WARN (`check.sh` step 4
exercises 24). Bit 3 (value 8's neighbour) is not a defined bit and is refused ✓.

**3.2 CONFIRMED — isolated from the default path, on the host and in the DSP.** The probe is written
only for the raw-row kernel: `ggml-hexagon.cpp:4604  kparams->pipeline = raw_row ? opt_rawrow_probe : 0;`
and `raw_row` requires `src1_nrows == 1` (decode). The HMX path always overwrites the field
(`ggml-hexagon.cpp:4510 kparams->pipeline = pipeline ? 1 : 0;`) so prefill cannot see a probe; the
flat fallback resets it (`ggml-hexagon.cpp:4648 // the probe bits set above are the raw-row kernel's; none may ride into another kernel`).
On the DSP the field is read in exactly two raw-row places (`matmul-ops.c:793`, `:1695`), both inside
`HTP_MM_KERNEL_HVX_RAW_ROW`. pp512 invariance is therefore structural, and §8's 856–862 gate should
hold.

**3.3 CONFIRMED — never memory-unsafe.** `raw-mv-overread.c` and the output-tail check now run all
four kernels, and I re-ran both: `ALL LOADS IN PAYLOAD`, canaries intact for int-only/fp-only at rows
{1,5,17,31,32} × n_k {9,64}. The loads are byte-identical across modes (`vmemu = 26` in all four),
so the two new dots have exactly the baseline's access pattern; their writes are the same guarded
`if (r0 + i < valid_rows)`.

**3.4 PLAUSIBLE — nothing on the device proves probe 16/32 selects a different dot.** The sim gate
has `check_diagnostics_differ` for exactly this ("a probe bit that silently selected the default
would make its device arm meaningless"), but `check.sh` only tests the *refused* combination. If the
DSP wiring were wrong, arms I and F would run the default dot, produce **valid** text, and land
inside the N–L band while being read as half-costs — the most expensive possible misreading of a
12-arm session. Cheap device gate (≈2 min): run `GGML_HEXAGON_RAWROW_PROBE=16` and `=32` at
`-p 0 -n 8` and require the generated text to differ from probe 0's (and I's to differ from F's);
or add the two probe arms to `check.sh` before the timed run.

**3.5 Minor.** `check_diagnostics_differ` runs at one shape (`raw-mv-edge-sim.c:197 … check_diagnostics_differ(64)`),
and its failure text is misleading: controls 9/10 trip it as
`FAIL diagnostic dots n_k 64: a diagnostic dot computes what another one does` when the real cause is
`paired != per-row`. A message naming the (a,b) pair would have saved me a minute.

### 4. Device scripts

**4.1 CONFIRMED — an arm cannot measure the wrong binary or config.** `env.sh` sets
`export ADSP_LIBRARY_PATH="$bin/dsp;$R/lib"` *per arm* inside `runarm`, and the bench binary comes
from the same `$bin`; skel and host binary can never come from different directories. The new
per-arm `ONE`/`TWO` argument style removes the old `$EXTRA` global (`EXTRA=""` reset) that was the
one way an env var could leak into the next arm. The recipes are effect-identical to the ABBA's
(verified against `s23-onecopy-abba-df538c50c/REPORT.md:24-35`: `OPFUSION=0`, `RAW_HMX=1`,
`HOSTBUF=1`, everything else at defaults, `RAW_LOCAL` default 0 ✓ "dropped per the coordinator"),
the bench line is byte-identical, the model path and the new device dir (`onecopy-pair`, so the
`O` arm's binaries are not clobbered) are right, and the three commits touch nothing outside
`ggml/src/ggml-hexagon` + `tests/`, so `$R/lib` on the phone stays valid for the pushed binaries.
Artifact hashes: 4/4 match the report and nothing is newer than the skel → the binaries really are
the tree of 7e4945582.

**4.2 CONFIRMED — the +256 B dot frame is safe on silicon.** `allocframe(#0x500)` vs `#0x400`, both
constant in K; worker stack `main.c:42 #define WORK_QUEUE_STACK_SIZE 16384`; the previous report
measured the chain at ≤ 6919 B → ≤ 7175 B, ~44 % of the stack. The delta is exactly the frame delta
because nothing else in the chain changed. (The 6919 B figure is inherited from the earlier report,
as the writer says.)

**4.3 FINDING — the thermal gate is advisory, not enforcing.** `env.sh`
`waitcool() { i=0; while [ $i -lt 20 ]; do ... [ "${t:-999}" -le 330 ] && return; sleep 30; i=$((i+1)); done; }`
falls through after 10 minutes and **runs the arm anyway**, while REPORT §8 says "battery temp
≤ 33.0 °C at each arm start — `waitcool` enforces it". The ABBA had to rerun three arms that
overshot 33.0 °C. The start temperature is recorded (`st` → `batT=`), so a violation is
reconstructable, but nothing stops or flags a hot arm. Fix: return non-zero on give-up and have
`runarm` write `GATE-FAIL` into `speed.txt`.

**4.4 FINDING — no gate on the result.** `runarm` records `exit=`, the `pp512|tg128` grep, and an
error count, but never fails and never checks that a `tg128` line exists at all. The report's own
gate "pp512 must stay 856–862 in every one-copy arm" (§8) is not implemented anywhere. An arm that
crashed early, or that ran a config which fell back to the flat kernel, produces a short
`speed.txt` that still looks like data. Minimum: fail the arm if the log has no `tg128` line or
`errors=` is non-zero, and print pp512 explicitly (it already greps `pp512`).

**4.5 FINDING — the inputs that decide pass/fail are never hashed.** Neither script verifies
`$M` (`/data/local/tmp/heat3way/ship.gguf`), `$R/input/kld_english_fixture.txt` or
`$R/input/cause-cpu-base.logits` (a directory shared with other experiments), and the sha256 check
for the pushed binaries *and* for the `O` arm's binaries exists only as prose in REPORT §8. If
anything in `/data/local/tmp/govhtp/input/` was rewritten, the KLD gate "must EQUAL to every digit"
fails for a reason that has nothing to do with this change, and a tired coordinator at 02:00 is
exactly the person who waves it off as noise. Put both sha256 steps in `check.sh`.

**4.6 FINDING (minor) — re-running `run-arms.sh` destroys the previous run**: `rm -f $D/speed.txt`
at the top plus fixed log names, no `set -e`, no resume, all evidence in the same directory as the
binaries. And REPORT §8's "~35 min" is optimistic: 12 arms × (tg128+pp512 with `-r 3` ≈ 2.5 min)
+ 12 × 90 s gaps ≈ 40–50 min.

### 5. Clean code

**5.1 CONFIRMED.** 342/−75 over 14 files; responsibility per file is respected (geometry tables /
activation arrangement / HVX kernels / probe bits / dispatch), the `RAW_MV_DOT(NAME, MODE)` macro
keeps four one-line instantiations, and every comment I could falsify is true: the geometry comment
("`out[i] = in[i ^ o]` when ctrl[i] has bit o", the odd control, "the other halfword lanes are
don't-cares"), `ascale` ("halfword lanes 2l and 2l + 1 … both"), the mode list, the probe-bit
meanings, the frame table, "The halving of the half × half multiplies is in the binary".

**5.2 FINDING (misleading comment).** `run-raw-mv.sh:22`
`#     9  two entries of the odd-halfword fan-out table corrupted (the second row of every pair)`
— the `sed` corrupts **one** adjacent byte pair (bytes 50–51 = the odd-halfword control of lane 12).
"the second row of every pair" describes nothing in the code and will mislead the next person
maintaining the controls.

**5.3 FINDING (hygiene).** `run-raw-mv.sh:32-40` (control 8) writes `tests/hexagon-sim/.prefix/`
**into the worktree** and cleans it only via an `EXIT` trap; a killed run leaves generated headers
inside the repo (they are also untracked, so `git status` noise). Use `mktemp -d`.

**5.4 FINDING (fragile by construction).** `raw_mv_add_window(..., enum raw_mv_mode mode)` branches
*inside* an unrolled loop and only works because each of the four callers passes a compile-time
constant through `always_inline`. I verified the specialisation happened (`int_only` has 0 hf/0
sf/0 vdelta; `fp_only` has 0 vrmpy — otherwise the diagnostic arms would be meaningless), but the
next person who calls `raw_mv_32x1_impl` from a non-inlined wrapper silently gets all three paths.
A `switch (mode)` dispatching to four small always-inlined helpers would make the property local.

**5.5 FINDING (overload, inherited but widened).** `kparams->pipeline` now carries three meanings
(bool pipeline for HMX, probe bitfield for the raw-row HVX kernel, and both are written from
different branches of the same host function). Safe today because every consumer sits in a distinct
`kernel_type` branch; nothing enforces that. The two new bits widen a field that was already a
lie. Worth a comment or a dedicated field next time.

## Terse summary

The dot is right. I tried hard to break the pairing and could not: the odd fan-out table is correct
once you model `vdelta` as the 7-stage butterfly it is, the last-window zero-fill cannot leak into
the odd halfword, F16/K<256 are not reachable cases, and re-running the in-tree gate myself gives
`paired == per-row bits` on every case with controls 9/10 failing for their own reason. The shipped
skel carries exactly the four dots and the instruction counts and frames the report claims, and the
host test really does reproduce the 32-row abort and really would fail if the defect disappeared.
The problems are all around the experiment, not in it: the pairing silently adds 256 B of stack
frame and 26 % more spill traffic that the speed model does not price; the strongest numerics claim
(120 cases vs `df538c50c`) lives in an untracked scratch harness; the host test is not in CTest; the
new host predicate re-derives a DSP invariant nothing checks; `waitcool` does not enforce what the
report says it enforces; nothing on device proves probe 16/32 do anything different from probe 0;
and the sha256s and input hashes that decide pass/fail live in prose. Run it — with items 1–3 above
fixed first.
