Reviewer: gpt-5.6-luna  
Writer under review: grok-4.6  
Scope: claimed P1 fixes in `LlamaService.ts` / `AppShell.tsx`. Read-only audit; no G2 or device claim.

## Verdict: FIX

The lock-order claim is narrowly correct. The prewarm fix is not. It still permits a stale native completion after disposal has invalidated the module context. The test evidence is pure-helper coverage, not proof of the wiring or race behavior.

## Findings

### F1 — P1: post-governor prewarm guard is bypassable — CONFIRMED

The prewarm captures an engine and checks `disposing` only before an async yield:

> `src/engine/LlamaService.ts:L822-L842`
> ```ts
>       if (disposing || !context) {
>         logPrewarm({ op: "skip", reason: !context ? "no_context" : "disposing" });
>         return;
>       }
>       const engine = context;
>       ...
>       await refreshGovernorBeforeCompletion(engine);
>       if (shouldSkipPrewarmWhenKvHoldsChat(kvHoldsChatSession)) {
>         logPrewarm({ op: "skip", reason: "kv_holds_chat" });
>         return;
>       }
>       const result = await trackCompletion(
>         engine.completion({
> ```

`refreshGovernorBeforeCompletion` itself awaits at `L1059` and may await native work at `L1063`. During that window, disposal does this synchronously:

> `src/engine/LlamaService.ts:L1996-L2002, L2026-L2037`
> ```ts
>     disposing = true;
>     const current = context;
>     context = null;
>     ...
>     kvHoldsChatSession = false;
>     ...
>     resetPrewarmState();
> ```

The resumed prewarm sees `kvHoldsChatSession === false` and calls `engine.completion()` on the old captured context. Disposal has already called `current.stopCompletion()` at `L2046` and is waiting for the job at `L2050-L2056`; this is an unsynchronized completion/stop race. The post-await guard must recheck at least `gen === prewarmGeneration`, `!disposing`, and `context === engine` before any native call. A generation check only after completion is too late.

### F2 — P1 liveness hazard: lifecycle lock can hostage disposal — CONFIRMED (conditional on a hung job/native call)

The planner samples engine-job state before acquiring either lock:

> `src/engine/LlamaService.ts:L943-L949`
> ```ts
>     const plan = planPrefixInputChange({
>       ...
>       busy: engineJobPendingCount > 0,
>     });
> ```

The wipe then holds the lifecycle chain while waiting for an unbounded engine job / `clearCache`:

> `src/engine/LlamaService.ts:L965-L980`
> ```ts
>         void withLifecycleLock(() =>
>           withEngineJob(async () => {
>             ...
>             await context.clearCache();
>             ...
>           }),
>         );
> ```

`withEngineJob` has no timeout (`L710-L726`). If a job starts after the planner sampled `busy: false`, or `clearCache` itself hangs, this wipe owns lifecycle and waits forever. `disposeEngine()` queues behind lifecycle at `L1988-L1989`, so it cannot reach its documented 60-second engine-job safety timeout / `stopCompletion` path at `L2050-L2056`. The outer-lifecycle order avoids the classic dispose-held-lifecycle cycle, but it does not make the wait safe. Recheck `engineJobPendingCount` inside the lifecycle callback before enqueueing, and give the wipe/native call a bounded recovery path or a lock protocol that lets disposal interrupt it.

### F3 — “recheck-to-clearCache is still TOCTOU” — REFUTED for the original KV-flag race

Once the wipe callback owns lifecycle and the engine FIFO, there is no `await` between the flag recheck and invocation of `clearCache`:

> `src/engine/LlamaService.ts:L967-L978`
> ```ts
>             if (!context || disposing) return;
>             if (!shouldApplyQueuedPrefixWipe(kvHoldsChatSession)) {
>               ...
>               return;
>             }
>             try {
>               await context.clearCache();
>             } catch {
>               return;
>             }
>             markChatKvCleared();
> ```

The lifecycle lock excludes init/restore/dispose, and the engine job excludes completion/utility jobs. The original “restore sets the hold after the planner” race is therefore closed on this path. This does not cure F1: ordinary prewarm does not hold lifecycle.

### F4 — dispose gate terms are present, but the claim is broader than the gate — CONFIRMED / PLAUSIBLE

The requested OR is present in the deferred-dispose check and idle predicate:

> `src/app/AppShell.tsx:L2902-L2909`

That is **CONFIRMED** as source text. It is not a universal disposal barrier: `skipDisposeWhileInFlight` deliberately allows background/trim disposal while `inFlight` is true (`src/app/backgroundDiscardPlan.ts:L46-L54`), and the thermal path’s wait at `src/app/AppShell.tsx:L3482-L3487` includes `nativeEngineWorkInFlight()` but not the download/model-switch refs. Treat “all dispose paths are gated” as **REFUTED**; treat the operational impact of those intentional force-dispose paths as **PLAUSIBLE**, not proven safe by this patch.
