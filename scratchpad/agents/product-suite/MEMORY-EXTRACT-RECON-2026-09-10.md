# RECON — accessory jobs vs chat state (Plan §3, LFM2.5-2.6B hybrid)
Single native context; all accessory completions serialize through withEngineJob (FIFO).

## (1) Memory extraction after a turn — CONFIRMED
- Trigger + delay: armMemoryExtract at onDone (AppShell.tsx:4799); the job waits on a saveGate released by afterSessionSave (AiChatPage's saveEngineSession settle, AppShell.tsx:4888-4898 "1) armMemoryExtract at onDone … 2) AiChatPage awaits saveEngineSession (FIFO) 3) afterSessionSave releases the save-gate → extractMemory runs"), with a 10 s safety valve (:4849-4853 "stranded gate keeps memoryExtractRef set and DEADLOCKS the next send") and abort-release.
- API + thinking: extractMemory (LlamaService.ts:4000) → withEngineJob → engine.completion with `enable_thinking: false, thinking_budget_tokens: 0, reasoning_format: "none"` (:406不具有-4066), n_predict 256, temp 0.1, EXTRACT_MEMORY_TIMEOUT_MS = 20_000 (:443) with real stopCompletion on expiry (:4068-4072).
- Blocks next send: YES, by design. Next send's handleSendStream does `if (memoryExtractRef.current) { await memoryExtractRef.current; }` (AppShell.tsx:4931-4936) BEFORE ensureEngineForModel — the user's send WAITS for extraction (bounded 20 s + snapshot/restore time). It does not abort or bypass it.
- KV state: EXTRACT_MEMORY_PRESERVE_CHAT_KV default-on (:3989-3993). Isolation = restore-from-disk (.kvs if chatKvDiskCurrent) else temp checkpoint `sessionFilePath(modelId).extract-ckpt` via snapshotNativeSession (saveSession, :4036-4042); if snapshot fails → SKIP: "Cannot isolate extract without destroying chat KV — skip" (:4044-4046). finally restores via restoreNativeSession and resets kvHoldsChatSession/lastChatNPast/chatKvDiskCurrent on failure (:4106-4121). On LFM2.5 hybrid the restore is a full state reload, not seq surgery — prefix intact after restore. Also relevant: saveSession REFUSES to overwrite live KV after tool turns ("Never save the live KV after tools… no guaranteed checkpoint at the pre-divergence boundary", :2192-2200) — markSessionDivergesAtLastExchange keeps the previous good prefix.

## (2) Translation / title / other accessory completions — CONFIRMED
- translateText (LlamaService.ts:4126+, TRANSLATE_TIMEOUT_MS 30 s) — UI-only trigger from the message menu (AiChatPage.tsx:3278-3283): refuses outright when `sendingRef.current || translationInFlightRef.current` — never races a send, never triggered automatically. ## (3) Background embedding vs send — CONFIRMED never blocks the chat gate while user waits
- Embedding uses the SEPARATE embedder (EmbeddingService/tryAcquireEmbed gate state embed_active), not the chat context. Co-residency: "On totalMemoryBytes > 6e9 AND a 2B-class chat model, tryAcquireEmbed is allowed while state is chat_ready" and "During chat_loading, embed is ALWAYS refused" (llamaContextGate.ts:8-14) — chat init calls releaseEmbedderBounded FIRST (AppShell.tsx:472-505, EMBEDDER_RELEASE_TIMEOUT_MS bound, timeout ⇒ hung ⇒ chat refused with restart message, never deadlocks the send). The embed JOB is aborted, not awaited, when ownership changes: bumpEmbedJobGeneration aborts embedJobAbortRef (:1050-1056) — called on unmount (:1163), library save (:1205), model load (:1955 area).

## (4) What the user sees while extract holds the engine — CONFIRMED nothing
- The extract runs AFTER the turn UI completes; sending/sendingInFlight are already false (job runs post-save). The composer is fully enabled; nothing shows. If the user sends during extraction, handleSend silently awaits memoryExtractRef (no status label, no spinner) — from the user's perspective the send just takes up to ~20+snapshot/restore seconds longer before "thinking" appears. No UI surface exists for accessory work.

## (5) Jelly cost math + prefix proof
- CONFIRMED cost model: extract prompt = extractPrompt + 2×2000-char slices (≈1k-1.2k tokens) + 256 n_predict. On LFM2.5-2.6B at ~3 tok/s decode (KALSA.md:661 "2.8-3.7 tok/s"): 256 tokens ≈ 75-90 s decode ALONE — but EXTRACT_MEMORY_TIMEOUT_MS = 20_000 caps it: the timer fires at 20 s, stopCompletion kills the native call, result is discarded as empty (parseOutcome 0). Plus snapshot (saveSession, seconds) + restore (loadSession) around it. So every enabled-memory turn on the Jelly: up to ~25-30 s of engine hold, and the extraction USUALLY TIMED OUT to zero facts (20 s ≪ 85 s needed) — "attività di memoria spariscono silenziosamente" is literally what happens today on the Jelly; only the telemetry line (KALSA_MEMORY_EXTRACT with extractStopReason 0 + parseOutcome) records it.
- Next-send prefix: n_common proof — there is NO KALSA_KVPREFIX/n_common telemetry in the repo (grep: zero hits; only KALSA_SESSION op:save/load/init + kv_prefix_unavailable/kv_not_chat reasons at :2136, :2389). The strongest available proof: restoreNativeSession→KALSA_SESSION {op:"load", ok, tokens…} (:2389) after the extract's finally restore, plus chatKvDiskCurrent=true afterwards. The intended n_common metric does not exist — the §3 "provable" criterion is currently unmeasurable. PLAUSIBLE that prefix reuse works (restore is exact-state), but unproven by telemetry.

## Ranked smallest changes
1. CHEAPEST + biggest: right-size extraction for LFM2.5 — raise EXTRACT_MEMORY_TIMEOUT_MS (20 s) to ~120 s OR cut the prompt (drop the 2000-char assistant slice to ~600) and n_predict 256→160; today it burns 20 s of engine AND returns nothing on the Jelly. Alternatively gate extraction on decode EMA (decodeSpeed.ts) like the thinking budget.
2. Make the next send not WAIT: keep the await (correctness), but only when the engine is warm; if extract is running when the user sends, let the send proceed after the CURRENT native op settles instead of awaiting the full job — or abort extract via a timeout-scoped signal when a send arrives (the engine job FIFO already serializes; an abort hook would cut the 20 s wait to ~0).
3. Add the missing prefix-proof telemetry: log n_common (restored-vs-live tokens or prefix match length) in KALSA_SESSION {op:"load"} and a KALSA_MEMORY_EXTRACT duration + skipped_reason field (snapshot_unavailable today is silent parseOutcome 0) — makes "non spariscono silenziosamente" verifiable.
4. Surface accessory work in UI: a tiny " memoria…" status chip while memoryExtractRef is set (composer stays enabled) — addresses "quando l'utente invia il messaggio successivo" perception.
5. Translation: already refuses during send; no change needed. Embed: already bounded + generation-aborted; no change needed.
