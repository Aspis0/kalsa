## Findings

### CONFIRMED — P1: the wipe recheck is not synchronization

`notifyStaticPrefixInputs` snapshots only `busy: engineJobPendingCount > 0` (`LlamaService.ts:938-944`), then queues:

> `void withEngineJob(async () => {` (`LlamaService.ts:954-956`)  
> `if (!shouldApplyQueuedPrefixWipe(kvHoldsChatSession))` (`LlamaService.ts:959`)  
> `await context.clearCache();` (`LlamaService.ts:963-964`)

The init restore is in a separate lifecycle/native path:

> `return withLifecycleLock(async () => {` (`LlamaService.ts:1443`)  
> `await tryLoadEngineSession(modelId, {` (`LlamaService.ts:1892`)  
> `const result = await context.loadSession(...)` (`LlamaService.ts:2730`)  
> `kvHoldsChatSession = true;` (`LlamaService.ts:2740`)

`withLifecycleLock` (`LlamaService.ts:1116-1122`) does not serialize with `withEngineJob`; the wipe also does not enter `runNativeOp`. The wipe can read `false`, then `loadSession` can set the hold while `clearCache()` is already executing. `restoreEngineSession` uses the engine-job FIFO (`LlamaService.ts:2837-2842`), but that does not fix the `initEngine` restore path. This is still a native race and a P1 ship blocker.

### CONFIRMED — P1: prewarm has the same hold TOCTOU race

The hold check occurs before enqueue:

> `if (shouldSkipPrewarmWhenKvHoldsChat(kvHoldsChatSession))` (`LlamaService.ts:798-800`)  
> `void withEngineJob(async () => {` (`LlamaService.ts:816`)

The queued body checks generation/disposal/context, but never rechecks `kvHoldsChatSession` (`LlamaService.ts:818-826`). `ensureEngineForModel` fires it without awaiting (`AppShell.tsx:3675-3677`), while a chat completion later sets:

> `kvHoldsChatSession = true;` (`LlamaService.ts:4183-4185`)

A prewarm can therefore observe empty KV, enqueue behind the send, then run its system-only `completion()` (`LlamaService.ts:836-849`) over live chat KV. The wipe-job recheck does not protect this separate path.

### CONFIRMED — P2: clear failure is still reported as a successful wipe

The code swallows `clearCache()` failure and unconditionally advances state:

> `} catch {` (`LlamaService.ts:965`)  
> `markChatKvCleared();` (`LlamaService.ts:968`)  
> `void queueStaticPrefixPrewarm(...)` (`LlamaService.ts:969`)

A rejected clear is thus treated as “KV gone,” followed by prewarm. There is no retry, failure state, or proof that the native cache was cleared.

### CONFIRMED / PLAUSIBLE — P2: final deferred-dispose gate drops model/download state

The initial idle predicate includes both flags (`AppShell.tsx:3095-3102`), but the final gate after async preparation checks only stream/send flags plus `nativeEngineWorkInFlight()` (`AppShell.tsx:2902-2907`). `modelSwitchInFlightRef.current` is set before awaits (`AppShell.tsx:4016-4018`) and cleared only in `finally` (`AppShell.tsx:4091-4093`).

CONFIRMED: the second gate is weaker than the first. PLAUSIBLE: a model switch or download can begin during preparation and disposal can be approved before its native phase is submitted.

### CONFIRMED — test evidence does not cover the fix

`prefixPrewarm.test.ts` imports only the pure helper module (`L1-6`) and tests the boolean inversion (`L52-71`). The harness likewise compiles/tests pure `prefixPrewarm.ts` logic. There is no `LlamaService` wiring test for restore-vs-wipe ordering, execution-time prewarm hold checks, or clear failure. Green helpers cannot establish the claimed safety.

### PLAUSIBLE — busy input changes are dropped

The planner logs and returns on `skip_inflight` (`LlamaService.ts:951-953`) with no dirty bit or retry. A prefix-input flip during an engine job can therefore miss its only prewarm opportunity and force a later cold/mismatch turn.

### REFUTED — “skip means stale prefix forever”

The app-level marker is reset (`LlamaService.ts:751-754`), the next turn logs a hash miss (`LlamaService.ts:3408-3416`), and a successful turn records its current hash (`LlamaService.ts:4183-4189`). So the marker does not remain stale forever; the native reconciliation behavior is simply untested.
