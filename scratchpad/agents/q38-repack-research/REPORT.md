# Q2_K/Q3_K ARM NEON repack research

**Verdict — GO-shaped, but only as a bounded, measurement-led kernel project.** The strongest prior art says that row-interleaving can transform standard Q2_K/Q3_K on ARM, and the pinned upstream code already supplies the reusable Q8_K activation and Q4_K–Q6_K ARM micro-kernel patterns. The project is not a trivial port: Q2_K/Q3_K have different metadata/dequantization paths, repack doubles memory pressure if the source mapping is retained, and the current repack integration has a real 3-D `MUL_MAT_ID` assertion trap. Start with an **8-column-by-4-activation-row dotprod path** for A76-class coverage; add an **8-column-by-8-row i8mm path** after correctness and residency behavior are proven. This is an **experienced SIMD-kernel project**, roughly several engineer-weeks for a production-quality first pass and longer if upstream-quality shape, fallback, memory, and cross-device coverage is required. The conclusion is an inference from the evidence below, not an upstream promise. [ik_llama.cpp IQ2_K_R4 PR](https://github.com/ikawrakow/ik_llama.cpp/pull/146), [ik_llama.cpp IQ3_K_R4 PR](https://github.com/ikawrakow/ik_llama.cpp/pull/145), [upstream Q2_K interleave PR](https://github.com/ggml-org/llama.cpp/pull/14373), [upstream 3-D repack crash](https://github.com/ggml-org/llama.cpp/issues/26537)

## 1. Prior art

### Upstream llama.cpp

The upstream Q2_K interleaving contribution is PR #14373, merged on 2025-08-01. It introduced an x86/x64 AVX2/AVX-512 implementation, with a `block_q2_Kx8` representation built from eight Q2_K blocks, sequential eight-byte quant extraction/interleaving, and per-column scale/min metadata. The author reported approximately 5.5% AVX2 and 25.5% AVX-512 gains in one set of tests, with larger Clang prefill numbers on a Phi3 3B Q2_K test. [PR #14373](https://github.com/ggml-org/llama.cpp/pull/14373)

The same PR’s maintainer testing on a 13900K found many cases close to parity, and the maintainer explicitly called out repacking cost, loss of mmap behavior, and weak AVX2 justification; the PR was subsequently limited to AVX-512. That is direct evidence for an upstream Q2_K repack, not evidence of a NEON implementation. [PR #14373 discussion and test tables](https://github.com/ggml-org/llama.cpp/pull/14373), [the merged Q2_K interleave commit](https://github.com/ggml-org/llama.cpp/commit/baad94885df512bb24ab01e2b22d1998fce4d00e)

### ik_llama.cpp: the strongest direct precedent

ikawrakow’s `ik_llama.cpp` has the most relevant public ARM precedent: it adds row-interleaved IQ2_K_R4 and IQ3_K_R4 types, with four interleaved rows and NEON matrix-vector/matrix-matrix paths. The IQ2_K_R4 PR reports ARM NEON prompt-processing speed of 107.93 versus 59.71 for its non-interleaved IQ2_K reference on the cited LLaMA 3.1 8B PP512 test, approximately 1.81x; the IQ3_K_R4 PR reports 93.83 versus 54.94, approximately 1.71x, on the corresponding ARM NEON test. [IQ2_K_R4 PR #146](https://github.com/ikawrakow/ik_llama.cpp/pull/146), [IQ3_K_R4 PR #145](https://github.com/ikawrakow/ik_llama.cpp/pull/145)

The same PRs report more modest but still positive ARM decode gains: approximately 1.15–1.21x for IQ2_K_R4 and approximately 1.12–1.15x for IQ3_K_R4 over the cited thread-count range. These are fork-specific benchmarks, not a promise for upstream GGML_TYPE_Q2_K/Q3_K, but they are strong evidence that the two-bit/three-bit decode patterns can benefit from row interleaving on NEON. [IQ2_K_R4 ARM measurements](https://github.com/ikawrakow/ik_llama.cpp/pull/146), [IQ3_K_R4 ARM measurements](https://github.com/ikawrakow/ik_llama.cpp/pull/145)

The important qualification is format identity: `_R4` is an ik_llama.cpp row-interleaved storage type, not a drop-in implementation of upstream llama.cpp’s `tensor_traits<block_q2_K,...>` or a proof that upstream should copy the exact layout. ik_llama.cpp’s README also says runtime repacking disables mmap and needs enough RAM, while offline row-interleaving creates a different stored type. [ik_llama.cpp README](https://github.com/ikawrakow/ik_llama.cpp), [ik_llama.cpp runtime-repack discussion](https://github.com/ikawrakow/ik_llama.cpp/discussions/258)

The direct public Q2/Q3 ARM precedents found here are the four-row `_R4` variants; I found no equally direct Q2_K_R8 or Q3_K_R8 NEON result in the examined PRs. That makes `_R4` the better prior-art starting point, while upstream’s existing 8-column ARM kernels provide the rationale for testing an 8-column/four-row upstream layout. [IQ2_K_R4 PR](https://github.com/ikawrakow/ik_llama.cpp/pull/146), [IQ3_K_R4 PR](https://github.com/ikawrakow/ik_llama.cpp/pull/145), [ik_llama.cpp README](https://github.com/ikawrakow/ik_llama.cpp)

The fork’s published ARM comparisons show large prompt-processing deltas for standard Q2_K and Q3_K model families when compared with its row-interleaved path; its January 2025 comparison reports approximately 3.26x for Q2_K and 4.33x for Q3_K in one M2 Max PP512 table. Those numbers include the fork’s broader implementation and should be treated as motivation, not as an apples-to-apples forecast for the pinned upstream code. [ik_llama.cpp January 2025 comparison](https://github.com/ikawrakow/ik_llama.cpp/wiki/Jan-2025%3A-prompt-processing-performance-comparison)

### Arm KleidiAI and other public work

KleidiAI is relevant as a micro-kernel and packing reference, but it does not appear to provide a drop-in GGML Q2_K or Q3_K implementation. Its release notes describe Advanced SIMD QAI8DXP-by-QSU2CXP matrix multiply with RHS packing, where QSU2CXP is KleidiAI’s own two-bit RHS format; the examined releases and source naming do not list GGML Q2_K metadata or a Q3_K equivalent. [KleidiAI repository and micro-kernel model](https://github.com/ARM-software/kleidiai), [KleidiAI releases](https://github.com/ARM-software/kleidiai/releases), [Arm KleidiAI format/packing explainer](https://learn.arm.com/learning-paths/cross-platform/kleidiai-explainer/page3/)

KleidiAI’s useful transferable ideas are feature-specialized micro-kernels, explicit RHS packing, no hidden dynamic allocation inside the kernel, and separate Advanced SIMD/SVE/SME implementations. Its repository describes packing and quantization micro-kernels as ARM-specific and organized by ISA feature, which is a good model for keeping a Q2/Q3 packer and the dotprod/i8mm kernels separately testable. [KleidiAI repository](https://github.com/ARM-software/kleidiai)

Arm’s “LLM Inference on Arm CPUs” paper is additional evidence for group-wise layout transformation: it describes optimized narrower-bit layouts, amortizing load/unpack work across output rows, and separate GEMV/GEMM strategies. The paper explicitly evaluates Q2_K and reports that its optimized Q2_K path improves throughput particularly at lower thread counts, but it is not an upstream GGML patch and does not supply the exact Q3_K implementation requested here. [Arm LLM inference paper](https://arxiv.org/abs/2501.00032)

Arm’s public LLM Runner example documents KleidiAI acceleration for Q4_0 models, not Q2_K or Q3_K. That is a useful ecosystem signal: sub-4-bit acceleration exists, but the public Arm integration surface is not evidence that Q2_K/Q3_K are already solved in a reusable upstream-compatible package. [Arm-Examples LLM Runner](https://github.com/Arm-Examples/LLM-Runner)

## 2. Why the upstream gap exists

The recorded upstream reason for limiting Q2_K repack is economic rather than a claim that the format cannot be accelerated. In #14373, maintainer testing found many small or inconsistent gains, while repacking adds startup/load work and can prevent mmap-style use; the author then changed the policy to enable repacking only on AVX-512 after review feedback. [PR #14373](https://github.com/ggml-org/llama.cpp/pull/14373), [Q2_K interleave commit](https://github.com/ggml-org/llama.cpp/commit/baad94885df512bb24ab01e2b22d1998fce4d00e)

The named participants matter for the historical record: the PR was authored by Srihari-mcw/Manogna-Sree, slaren supplied the 13900K performance and mmap objections, and ggerganov approved the merged change; the merge date shown by the PR is 2025-08-01. The author’s later update says repacking was enabled only on AVX-512. [PR #14373](https://github.com/ggml-org/llama.cpp/pull/14373)

I found no upstream comment showing that NEON Q2_K was attempted and rejected. The defensible conclusion is narrower: upstream accepted an x86 Q2_K implementation after AVX-512-specific evidence, and later ARM work concentrated on Q4_K–Q6_K; there is no recorded NEON experiment in the examined Q2_K PR that would settle the Android/MoE residency case. [PR #14373](https://github.com/ggml-org/llama.cpp/pull/14373), [upstream ARM Q4_K PR](https://github.com/ggml-org/llama.cpp/pull/16739), [upstream ARM Q6_K PR](https://github.com/ggml-org/llama.cpp/pull/19360)

There is a technical reason the Q2/Q3 case needs its own measurement: Q2_K and Q3_K spend more of the hot loop on bit-plane extraction and metadata reconstruction than Q4_K–Q6_K. A repack can make those loads regular and amortize unpacking across rows, but it can also make the stored format larger in practice, add a one-time transform, and lose the file-backed property that matters to large MoE models. This is an inference supported by the format definitions, the Arm paper’s layout rationale, upstream’s Q2_K review, and the documented mmap failures. [GGML tensor encoding schemes](https://github.com/ggml-org/llama.cpp/wiki/Tensor-Encoding-Schemes), [Arm LLM inference paper](https://arxiv.org/abs/2501.00032), [PR #14373](https://github.com/ggml-org/llama.cpp/pull/14373), [upstream mmap/repack issue](https://github.com/ggml-org/llama.cpp/issues/16761)

## 3. Design inputs from the pinned code

### Source formats

The GGML encoding reference describes Q2_K as 2.5625 bits per weight with sixteen 16-value sub-blocks, each using a four-bit scale and four-bit minimum; it describes Q3_K as 3.4375 bits per weight with sixteen 16-value sub-blocks and six-bit scales. [GGML tensor encoding schemes](https://github.com/ggml-org/llama.cpp/wiki/Tensor-Encoding-Schemes)

At the pinned source level, `block_q2_K` contains two half-precision super-block parameters, 16 bytes of packed scale/min metadata, and `QK_K/4` bytes of packed two-bit quants; its static size assertion is at `ggml-common.h:308-309`. `block_q3_K` contains one half parameter, `QK_K/4` low two-bit bytes, `QK_K/8` high-bit-mask bytes, and 12 bytes of packed six-bit scales; its static assertion is at `ggml-common.h:320-321`. This is the exact low-plane/high-plane shape a Q3 repacker must preserve. [pinned `ggml-common.h:308-321`](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-common.h:308)

### What the existing Q2_K repack transfers

The pinned Q2_K transform groups eight source blocks into one `block_q2_Kx8`: it copies the eight super-block `d` and `dmin` values, lays out 128 bytes of scale/min metadata for the eight columns, and interleaves the two-bit quants by taking eight-byte chunks. The transform and its comments are at `repack.cpp:2965-3050`; the public destination layout is at `repack.h:59-73`. [pinned Q2_K transform](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.cpp:2965), [pinned repack layouts](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.h:59)

The transferable design is not the exact x86 instruction sequence; it is the division of labor. The packer puts the same bit planes and scale/min records for several columns adjacent, while the kernel consumes a regular block and applies the original quantization equation after integer dot products. Q2_K’s existing x8 layout already has the right granularity for an ARM 8-column RHS kernel; the missing work is an ARM-compatible q2 unpack/dequant micro-kernel and its q8_K row contract. [pinned Q2_K repack transform](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.cpp:2965), [upstream Q2_K PR](https://github.com/ggml-org/llama.cpp/pull/14373)

The pinned Q2 GEMV/GEMM traits pair `block_q2_Kx8` with Q8_K activations for the 8x8 path and `block_q2_Kx16` with Q8_K for the 1x16 path; the trait declarations and selection are at `repack.cpp:4547-4570` and `4629-4637`, while the generic q2 kernels are at `repack.cpp:1029-1055` and `1986-2014`. [pinned Q2 traits and selection](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.cpp:4547), [pinned Q2 generic kernels](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.cpp:1029)

### Q8_K activations and the scale/min correction

The generic repack code provides Q8_K activation quantization paths for four-row and eight-row work. The `block_q8_Kx4` public layout contains four floating-point row scales, interleaved Q8 values, and per-16-value int16 block sums; the declaration and size assertion are at `repack.h:96-102`. [pinned Q8_Kx4 layout](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.h:96)

The K-quant dot product is not just `dot(qw, qa) * d`. For Q4_K/Q5_K, the ARM code loads the Q8_K row scale, combines it with each weight block’s `d` and `dmin`, accumulates integer dot products, and uses Q8_K block sums to subtract the contribution from the quantized minimum. The Q4_K 8x4 GEMV code is around `arch/arm/repack.cpp:576-704`, and the Q4_K 8x4 GEMM code is around `:3323-3511`; corresponding Q5_K/Q6_K paths follow the same scale/bias pattern with their respective bit extraction. [pinned ARM Q4_K GEMV](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/arch/arm/repack.cpp:576), [pinned ARM Q4_K GEMM](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/arch/arm/repack.cpp:3323), [pinned ARM Q5_K/Q6_K paths](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/arch/arm/repack.cpp:863)

For Q2_K, the new kernel must preserve the same separation: decode four two-bit values per source byte into signed/unsigned int8 lanes, use the eight-column packed scale/min metadata, accumulate against Q8_K activations, apply the per-sub-block scale, and subtract the min term using the activation block sums. For Q3_K, the low two-bit plane and `hmask` high bit must be reconstructed before the scale is applied; a kernel that only interleaves `qs` will silently produce numerically plausible but wrong output. The format layouts are at the pinned `ggml-common.h:308-321`, and the existing q4–q6 correction pattern is in the ARM file cited above. [pinned Q2_K/Q3_K structures](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-common.h:308), [pinned ARM K-quant correction code](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/arch/arm/repack.cpp:576)

### 8x4 dotprod versus 8x8 i8mm

The pinned ARM implementation has 8-column interleaved Q4_K/Q5_K/Q6_K kernels with four activation rows and eight activation rows. The 8x4 GEMM families use `block_q8_Kx4` and dot-product instructions; the 8x8 families use eight-row activation packing and, under the appropriate feature guard, `vmmlaq_s32`/i8mm operations. The 8-column guards and assertions are visible at `arch/arm/repack.cpp:3323-3335`, `:3762-3770`, `:4083-4152`, `:4282-4306`, `:4731-4755`. [pinned ARM repack.cpp](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/arch/arm/repack.cpp:3323)

Arm Cortex-A76 implements Armv8.4-A dot product instructions, making dotprod the safer baseline for A76-class devices. Cortex-X3 supports `FEAT_I8MM`; Arm’s X3 optimization guide gives throughput information for SDOT/UDOT and SMMLA/UMMLA/USMMLA, so i8mm is the higher-throughput option when the runtime feature is present. [Cortex-A76 technical reference](https://documentation-service.arm.com/static/5f562083235b3560a01e03bc), [Cortex-X3 technical reference](https://documentation-service.arm.com/static/62bb289431ea212bb6625392), [Cortex-X3 software optimization guide](https://documentation-service.arm.com/static/63a029881d698c4dc521ca3f)

The recommendation is therefore **8x4 dotprod first**, with runtime feature gating and a scalar/generic fallback for shapes that do not fit. It maximizes A76-era coverage and reuses the simpler four-row Q8_K contract. Add 8x8 i8mm as a second kernel for X3/S23-class cores if measurements show that the eight-row path pays back its more complex activation packing and tail handling. This is an engineering recommendation inferred from the ARM feature split and the pinned kernel structure; a Snapdragon SKU must still be measured because the system may schedule work across heterogeneous cores. [Arm AArch64 extension documentation](https://sourceware.org/binutils/docs-2.34/gas/AArch64-Extensions.html), [pinned ARM 8x4/8x8 implementations](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/arch/arm/repack.cpp:3323)

## 4. Risks and traps

### 1. Correctness is the first gate, not an afterthought

Upstream issue #19561 reports that Q4_K ARM repack PR #17494 caused stack smashing on aarch64, while `--no-repack` avoided the failure. That is a directly relevant precedent for buffer-size, temporary-layout, and tail mistakes in this exact subsystem. [Q4_K ARM repack stack-smashing issue](https://github.com/ggml-org/llama.cpp/issues/19561)

Upstream issue #16942 reports garbled output in a high-thread x86 repack configuration, again with `--no-repack` as the workaround. The lesson for Q2/Q3 is to test bit-exactness over thread counts, not just a single-thread numerical comparison. [high-thread repack correctness issue](https://github.com/ggml-org/llama.cpp/issues/16942)

The Q3-specific trap is plane reconstruction: the 2-bit low plane, high-bit mask, six-bit packed scales, and super-block scale must be independently checked against the reference dequantizer. The structural evidence is the Q3_K definition at `ggml-common.h:320-321`; the correct test should compare dequantized values and GEMM/GEMV outputs, not only final model perplexity. [pinned Q3_K structure](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-common.h:320)

### 2. Extra-buffer initialization and lifetime

The repack subsystem stores a tensor trait pointer in `tensor->extra`; the pinned initialization and use are at `repack.cpp:4727-4739`. The trait must be selected only when the operation, type, dimensions, ISA, and buffer size all agree, and the extra pointer must not survive a reset/reuse path with stale layout metadata. Upstream discussion explains that extra buffers have lifecycle implications and that repack metadata is attached during tensor initialization. [pinned extra initialization](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.cpp:4727), [upstream repack extra-buffer discussion](https://github.com/ggml-org/llama.cpp/discussions/7911), [upstream supports_op discussion](https://github.com/ggml-org/llama.cpp/discussions/5277)

The `block_q2_Kx8` and `block_q2_Kx16` structs have static size assertions, but that does not prove that a temporary array, destination stride, or extra allocation is correctly initialized. The Q2 transform uses local arrays of source blocks and copies metadata into a destination block, so the project should add explicit zero/init behavior where padding or all fields are not written, then exercise repeated repack/reset cycles. [pinned Q2 layouts](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.h:59), [pinned Q2 transform](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.cpp:3292)

### 3. Shape, tail, and alignment assumptions

The existing ARM kernels assert that the number of columns is divisible by their interleave width, and the pinned selection logic checks `ne[1] % 8` or `% 16`. The ARM Q4/Q5/Q6 code also assumes 8-column groups in the optimized families. These are logical tile/alignment constraints, not merely pointer-alignment constraints. [pinned ARM divisibility assertions](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/arch/arm/repack.cpp:3323), [pinned Q2 selection checks](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.cpp:4629), [pinned repack transform shape guards](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.cpp:3213)

The design must define a safe fallback for `ne[1] % 8 != 0`, `ne[0] % 8 != 0`, K dimensions that are not whole QK_K blocks, and GEMV batches that do not fill four or eight activation rows. It must also confirm that the repack’s `nb[]` strides and tensor offsets are compatible with expert slices rather than assuming a contiguous 2-D matrix. The upstream supports-op discussion explicitly recommends declining unsupported shapes, and the current ARM code demonstrates the cost of relying on assertions. [upstream supports-op discussion](https://github.com/ggml-org/llama.cpp/discussions/5277), [pinned ARM shape assertions](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/arch/arm/repack.cpp:580)

### 4. 3-D MoE experts and `MUL_MAT_ID`

This is the highest-risk integration trap for the stated use case. In the pinned checkout, `supports_op` permits `GGML_OP_MUL_MAT_ID` with a 3-D weight source at `repack.cpp:4774-4795`, but `compute_forward` asserts `ggml_n_dims(op->src[0]) == 2` at `repack.cpp:4282`. Upstream issue #26537 reports the corresponding aarch64 DeepSeek-V4-FLASH crash, and issue #25837 reports garbled output in another 3-D/repack interaction. ### 5. Residency and the anonymous-RAM trade

Repacking materializes a new tensor buffer. For a roughly 6 GB expert set, repacking every expert should be budgeted as roughly another 6 GB of weight-shaped storage at peak, plus temporary source/destination and working buffers, unless the original mapping is safely unmapped or only a selected subset is transformed. The exact multiplier depends on the type and allocator, but the order-of-magnitude consequence follows from storing a second full representation. ik_llama.cpp explicitly warns that runtime repacking disables mmap and needs enough RAM. [ik_llama.cpp README](https://github.com/ikawrakow/ik_llama.cpp), [upstream mmap/repack memory issue](https://github.com/ggml-org/llama.cpp/issues/16761)

That extra memory is the point for this workload only if it is selective: an anonymous repacked hot-expert buffer can avoid repeatedly faulting the original file-backed pages after the OS evicts them. It is not a guarantee against all anonymous-memory pressure, and repacking the complete expert set can make the device fail earlier. Upstream issue #16761 documents retained/repacked memory and major-fault differences, while #23603 documents large MoE CPU_REPACK allocation failures at approximately three times total RAM and the `--no-repack` workaround. [upstream mmap fault/memory issue](https://github.com/ggml-org/llama.cpp/issues/16761), [large MoE repack allocation issue](https://github.com/ggml-org/llama.cpp/issues/23603)

The design should therefore measure at least three modes: baseline mmap, repack-all, and repack-selected-experts. The success criterion is not just kernel throughput; it is end-to-end time, major faults, peak RSS/anonymous memory, energy, and whether the selected experts remain useful across the full conversation plan. The rationale is an inference from the reported workload and upstream memory behavior. [upstream mmap fault/memory issue](https://github.com/ggml-org/llama.cpp/issues/16761), [upstream large-MoE issue](https://github.com/ggml-org/llama.cpp/issues/23603)

## 5. Upstream strategy

Upstream has accepted architecture-specific repack work when it is self-contained, benchmarked, and integrated with the generic repack traits, as shown by Q2_K x86 and the Q4_K–Q6_K ARM PRs. That history favors a contribution with a small, explicit storage layout, reference fallback, feature guards, shape checks, and reproducible ARM benchmarks. [Q2_K x86 PR](https://github.com/ggml-org/llama.cpp/pull/14373), [Q4_K dotprod PR](https://github.com/ggml-org/llama.cpp/pull/17494), [Q6_K dotprod PR](https://github.com/ggml-org/llama.cpp/pull/19360)

The recent upstream discussion does not promise a broad repack roadmap. Maintainers describe repacking as hardware-related and emphasize testing, while users point out that extra-buffer propagation and operation selection need to be coherent across backends and RPC-like configurations. The contribution should therefore make the ARM scope explicit and avoid claiming that a new storage type is universally beneficial. [upstream repack discussion](https://github.com/ggml-org/llama.cpp/discussions/21130)

The practical upstream sequence should be: first land or locally validate a reference repack/layout and exhaustive correctness tests; then add dotprod; then add i8mm; then submit residency/benchmark evidence and a narrowly scoped `MUL_MAT_ID` policy. This reduces the chance that a novel Q3 layout, an ARM kernel, and a 3-D routing change become one unreviewable patch. This is a recommended review strategy based on the upstream PR history and bug record. [upstream Q2_K PR](https://github.com/ggml-org/llama.cpp/pull/14373), [upstream ARM repack bug](https://github.com/ggml-org/llama.cpp/issues/19561), [upstream 3-D repack bug](https://github.com/ggml-org/llama.cpp/issues/26537)

As of the research date, I found no open upstream Q2_K/Q3_K ARM repack PR in the examined GitHub searches. The already merged ARM Q4_K–Q6_K work is the main code-area collision, and the 3-D MoE repack issues are the main integration collision. Recheck the searches and issue tracker immediately before opening the project or PR. [Q2_K repack search](https://github.com/ggml-org/llama.cpp/pulls?q=is%3Apr+Q2_K+repack), [Q3_K repack search](https://github.com/ggml-org/llama.cpp/pulls?q=is%3Apr+Q3_K+repack), [aarch64 repack search](https://github.com/ggml-org/llama.cpp/pulls?q=is%3Apr+aarch64+repack), [current 3-D repack issue](https://github.com/ggml-org/llama.cpp/issues/26537)

## One-page verdict for the design document

**Project shape: GO, conditionally.** The project has enough prior art to justify a focused implementation: ik_llama.cpp demonstrates meaningful NEON gains from four-row interleaving for IQ2_K and IQ3_K, Arm’s paper supports amortizing narrow-bit unpacking across rows, and upstream already has Q8_K plus ARM Q4_K–Q6_K patterns. The key novelty is making those ideas work for upstream GGML Q2_K/Q3_K while solving residency and MoE shape handling. [IQ2_K_R4 PR](https://github.com/ikawrakow/ik_llama.cpp/pull/146), [IQ3_K_R4 PR](https://github.com/ikawrakow/ik_llama.cpp/pull/145), [Arm LLM inference paper](https://arxiv.org/abs/2501.00032), [pinned ARM repack code](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/arch/arm/repack.cpp:3323)

**Start layout: 8x4 dotprod.** Use eight interleaved weight columns and four Q8_K activation rows, matching the pinned ARM Q4_K/Q5_K/Q6_K GEMM family. This is the broad A76-class compatibility path and the simpler first proof of Q2/Q3 bit-plane correctness. Add 8x8 i8mm second for devices with `FEAT_I8MM`, especially X3/S23-class targets, after measuring whether the extra activation packing and eight-row scheduling improve end-to-end expert matmul. [pinned ARM 8x4/8x8 families](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/arch/arm/repack.cpp:3323), [Cortex-A76 technical reference](https://documentation-service.arm.com/static/5f562083235b3560a01e03bc), [Cortex-X3 technical reference](https://documentation-service.arm.com/static/62bb289431ea212bb6625392)

**Honest effort class: experienced kernel work.** A minimal proof-of-concept is not large, but production quality requires two new format-specific pack/decode paths, reference equivalence tests, GEMV and GEMM, dotprod and i8mm feature selection, tails, 3-D policy, allocator/extra-buffer lifecycle, and residency benchmarks. Upstream’s stack-smashing, garbled-output, mmap, and 3-D failures show that the integration surface is as important as the SIMD loop. [upstream ARM correctness issue](https://github.com/ggml-org/llama.cpp/issues/19561), [upstream high-thread correctness issue](https://github.com/ggml-org/llama.cpp/issues/16942), [upstream mmap issue](https://github.com/ggml-org/llama.cpp/issues/16761), [upstream 3-D issue](https://github.com/ggml-org/llama.cpp/issues/26537)

**Top five traps to put in the design doc:**

1. **Q3 plane/scale corruption:** preserve `qs`, `hmask`, packed six-bit scales, and super-block `d`; validate dequantized blocks before throughput. [pinned Q3_K structure](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-common.h:320)
2. **Extra-buffer and temporary initialization:** static size assertions do not cover stale `tensor->extra`, padding, destination strides, or repeated repack/reset. [pinned extra lifecycle](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.cpp:4727), [upstream extra-buffer discussion](https://github.com/ggml-org/llama.cpp/discussions/7911)
3. **Shape/tail mismatch:** never dispatch an 8-column or four/eight-row kernel unless `ne[]`, K blocks, strides, and activation batches satisfy the contract; otherwise fall back. [pinned ARM assertions](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/arch/arm/repack.cpp:3323)
4. **3-D `MUL_MAT_ID`:** resolve the current `supports_op`/compute assertion mismatch before claiming MoE support. [pinned mismatch](C:/Users/gualt/Desktop/Kalsa/moe-experiments/BigMoeOnEdge/third_party/llama.cpp/ggml/src/ggml-cpu/repack.cpp:4282), [upstream crash](https://github.com/ggml-org/llama.cpp/issues/26537)
5. **Memory versus residency:** repack only selected hot experts unless the device budget explicitly covers an additional weight-shaped allocation; report peak anon/RSS and faults, not only kernel speed. [upstream mmap issue](https://github.com/ggml-org/llama.cpp/issues/16761), [large-MoE allocation issue](https://github.com/ggml-org/llama.cpp/issues/23603)

**Decision gate:** proceed to implementation only if the team can define the 3-D policy, reserve the selective-residency memory budget, and commit to reference-versus-repacked numerical tests plus end-to-end Android measurements. If those conditions hold, the research supports opening the kernel project. [upstream supports-op discussion](https://github.com/ggml-org/llama.cpp/discussions/5277), [ik_llama.cpp runtime repack discussion](https://github.com/ikawrakow/ik_llama.cpp/discussions/258)
