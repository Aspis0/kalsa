# iOS performance and resilience recon

Scope: read-only inspection of `/Users/marco/Projects/kalsa-ios`, branch `phone/room-v1`, as checked out on 2026-10-04. No build, install, Metro, Simulator, or phone run was performed. Findings are source-confirmed unless marked PLAUSIBLE; runtime impact needs the measurements listed.

## Ranked findings by user impact

1. **P1 visible lag — CONFIRMED: transcript is not virtualized.** `src/ui/shell/Transcript.tsx:195,239-242` — “`<ScrollView`” and “`: messages.map((message, index) => {`”. Every message mounts into one ScrollView, so scroll/layout and memory costs rise with full conversation length; memoized rows avoid some child rendering but do not virtualize or avoid the parent map/wrappers. Replace with a virtualized list (FlatList/FlashList), stable key extraction, tuned windowing, and measured row sizing where practical. **Measure:** Instruments Time Profiler + Core Animation/FPS while scrolling 100/500/1,000-message conversations; compare mounted row count and JS/UI frame hitches.

2. **P1 visible lag — CONFIRMED: the 33 ms stream coalescer does not coalesce normal token rates.** `src/host/sendHost.ts:246-249` — “`~30 fps UI flush`”; `src/engine/streamCoalescer.ts:49-60` — “`if (lastFlushAt === 0 || elapsed >= intervalMs) {`”. At the stated 5–15 tokens/s, token gaps exceed 33 ms, so each token takes the immediate leading-edge `setMessages` path. Each flush also replaces the assistant message object and traverses the full transcript; memoization protects settled row internals but the list work remains. Use a real frame scheduler/leading cadence (e.g. one flush per display frame or 50–100 ms), keep latest text in a ref, and validate perceived latency. **Measure:** instrument `setMessages` flush count versus native token count; Hermes sampling profile and Core Animation FPS during long streamed markdown answers at 60/120 Hz.

3. **P1 likely jetsam — CONFIRMED: iOS memory warnings do not reach the model owner.** `node_modules/react-native/Libraries/AppState/AppState.js:32-40` — “`memoryWarning - This event is used in the need of throwing memory warning or releasing it.`”; `modules/kalsa-lifecycle/ios/KalsaLifecycleModule.swift:1-6` — “`UIKit's coarse memory warning is not on the Android trim-level scale`”; `src/host/iosBackgroundGuard.ts:51-54` — “`AppState.addEventListener("change"`”. RN 0.86 exposes the event, but the app only subscribes to `change`; the iOS module only samples headroom. Add a memory-warning path that stops or safely drains active generation, disposes the local model/context when safe, clears reclaimable JS/image caches, and records warning/headroom/model/context. **Measure:** trigger memory pressure on a device; verify warning log, falling resident footprint, prompt recovery/reload, and absence of jetsam reports.

4. **P1 likely jetsam — PLAUSIBLE: the largest shipped vision bundle is about 3.5 GB on disk before runtime allocations.** `src/engine/ModelRegistry.ts:217,223-228` — “`sizeBytes: 2_834_975_040`” and “`sizeBytes: 672_423_616`”; `src/engine/LlamaService.ts:2615-2628` — “`use_mlock: true`” and “`n_ctx: effectiveNCtx`”. The code does account for mmproj in load estimates (`src/engine/modelGateRAM.ts:70-85`), and current catalog context is 8,192 tokens, but the model weights, vision projector/encoder, KV, compute buffers, Metal allocations, and React Native compete under the actual per-process jetsam limit. No iPhone 15 Pro or 6 GB device measurements are in this checkout evidence. Gate vision on observed iOS headroom, offer a smaller/no-vision model on low-headroom phones, and stress-test concurrent chat/history/image workloads. **Measure:** physical-device `os_proc_available_memory`, Xcode Memory Gauge/Allocations/VM Tracker, Metal allocations, and device jetsam reports at cold load, image prompt, and long generation.

5. **P1 possible jetsam — PLAUSIBLE: every native model load requests `mlock` while weights are mmap-backed.** `src/engine/LlamaService.ts:2615-2624` — “`use_mlock: true`” / “`use_mmap: load.useMmap`”; `src/engine/loadPolicy.ts:22-25` — “`page-cache backed, reclaimable by the kernel under pressure`”. Pinning mapped weights, if honored on iOS, could undermine reclaimability and raise pressure; the tree contains no iOS measurement proving whether mlock succeeds, how much it pins, or whether it is ignored. Make the policy platform-aware unless a device measurement supports mlock. **Measure:** compare signed Release device runs with mlock on/off; inspect native `mlock` warnings, VM Tracker resident/file-backed pages, available-memory headroom, and jetsam outcome.

6. **P1 launch / P2 — PLAUSIBLE: first React content waits for several async readiness gates.** `App.tsx:156-158` — “`if (!themeLoaded || !fontScaleLoaded || !localeReady) return null;`”; `App.tsx:207` — “`return ready ? <HostRoot /> : null;`”. Theme/font preferences, locale, fonts, and then model-catalog configuration all precede the chat UI. This is asynchronous (not evidence of a blocked main thread or watchdog kill), but can prolong the launch splash/blank interval on cold storage. Render a lightweight shell promptly and hydrate preferences without gating first paint where visual consistency permits. **Measure:** Instruments App Launch/Time Profiler from process start to first interactive frame; cold and warm launches with signposts around each readiness gate.

7. **P2 crash containment — CONFIRMED: no React error boundary at the app root.** `App.tsx:210-230` — “`<GestureHandlerRootView style={{ flex: 1 }}>`” wrapping providers and `<AppContent />`; the root composition has no ErrorBoundary. The global `ErrorUtils` handler in `src/logReport/collector.ts:89-114` records and chains fatal JS errors; that is diagnostics, not render-tree recovery. Add a root boundary with a recoverable fallback/restart path for render errors and preserve the fatal report. **Measure:** inject a render exception in a non-production harness; confirm fallback rendering, error report, and unaffected relaunch.

8. **P2 memory/latency — PLAUSIBLE: PDF extraction temporarily keeps a base64 PDF and an HTML string containing it.** `src/components/PdfToImages.tsx:271-284` — “`FileSystem.readAsStringAsync(pdfUri, { encoding: FileSystem.EncodingType.Base64 })`” followed by “`setHtml(buildPdfHtml(pdfSrc, workerSrc, pdfB64, pages));`”; default PDF cap is 5 MiB (`:144`). The WebView then parses/decodes its embedded copy, so peak usage can exceed the file cap even though the bound is finite. Prefer a file URL/streaming bridge to WebView and release the JS base64 reference immediately. **Measure:** Allocations + VM Tracker during repeated max-size PDF import/rasterization; note JS heap, WebContent/WebView, and peak footprint.

9. **P2 model fit — CONFIRMED configuration / PLAUSIBLE user impact: hybrid context can rise to 16,384 tokens on high-RAM devices and is not silently reduced by the context profile.** `src/engine/contextProfile.ts:154-160` — “`Catalog n_ctx is never silently downgraded`”; `:196-203` — “`RAM gate only UPGRADES hybrids`”. `LlamaService` later applies an available-memory tuning clamp with an 8,192 floor (`:2434-2438`), but the default catalog context remains authoritative if memory is unknown or estimated to fit. Consider a device-class iOS ceiling/headroom-based policy, especially for a vision model; preserve the fast iOS q8_0/q8_0 KV choice. **Measure:** compare actual KV/Metal/compute allocations at 8k and 16k on iPhone 15 Pro and the smallest supported RAM class; record available headroom and jetsam margin.

10. **P2 entitlement assumptions — CONFIRMED: neither memory entitlement is in the checked-in entitlements.** `ios/KalsaAIChat/KalsaAIChat.entitlements:1-4` — “`<dict/>`”. Do not assume increased-memory-limit is active. Extended Virtual Addressing expands address space, not physical RAM; Apple describes increased-memory-limit as a higher limit on supported devices, while capabilities/profiles authorize claimed entitlements. Apple says capability availability depends on program membership, so a free Personal Team should not be assumed to provision either entitlement; confirm an authorized profile/signature before relying on it. These entitlements would not make a 3.5 GB model safe by themselves. Fix only after confirming Apple authorization and testing on-device. **Measure:** inspect final signed entitlements and embedded provisioning profile, then capture device `os_proc_available_memory` and jetsam behavior with/without the authorized entitlement. Sources: [increased memory limit](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.kernel.increased-memory-limit), [extended virtual addressing](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.developer.kernel.extended-virtual-addressing), [capabilities and membership](https://developer.apple.com/help/account/capabilities/capabilities-overview/).

11. **P2 possible image memory — PLAUSIBLE but mitigated: visible 72 px thumbnails load the original URI.** `src/ui/shell/UserImages.tsx:13-14,34-45` — “`const THUMB_SIZE = 72;`” and “`source={{ uri: image.uri }}`”. The view is tiny but native image decoding may still decode a larger source; attachment intake does resize to 1,280 px (`src/host/useAttachments.ts:177-182`), reducing the worst case. Generate/store a small thumbnail separately and pass that URI to the transcript. **Measure:** Instruments Allocations/VM Tracker while opening histories with many 12 MP photos; compare decoded image footprint and scrolling hitches.

12. **P2 JS stall — PLAUSIBLE on very long chats: prompt-deadline estimation serializes the complete message array on the JS thread.** `src/engine/LlamaService.ts:4513-4524` — “`JSON.stringify(currentMessages).length / 4`”. This runs at turn setup rather than per token, but creates a temporary transcript-sized string and synchronous CPU/GC work before generation; image/base64 must stay out of history (the current attachment code does). Use bounded/incremental character accounting or precomputed prompt estimates. **Measure:** Hermes sampling profile and JS frame timing with 1k-message/large-transcript history; inspect GC and send-to-first-token latency.

13. **P3 battery/idle work — CONFIRMED, scoped: a periodic battery sampler runs while the local model is resident, even when idle.** `src/host/useModelBar.ts:34-39` — “`enabled: modelHost.modelState === "ready" && resident`”; `src/hooks/useBatteryEta.ts:244-248` — “`timer = setInterval(() => void tick(), intervalMs);`”. This is intentional ETA sampling and stops on background (`:254-260`), so it is not evidence of an idle crash or major performance issue. Consider pausing while the app is idle or thermal/low-power constrained. **Measure:** Energy Log and Time Profiler with an idle loaded model; verify timer stops in background and quantify wakeups per hour.

## Audited areas with no source-confirmed issue

- **Virtual address/memory policy:** no increased-memory-limit or extended-virtual-addressing key is present; `modules/kalsa-lifecycle/ios/KalsaLifecycleModule.swift:27-42` samples `os_proc_available_memory()` on hardware and maps simulator/Mac zero to unknown. Current estimator includes optional mmproj; this is better than comparing only GGUF disk size, but it is not yet proof of safe runtime peak.
- **mmap/KV:** `LlamaService.ts:2617-2628` uses mmap according to per-model policy and passes the resolved context/KV; `kvCacheProfile.ts:21-25,57-62` resolves iOS q8_0/q8_0. The open question is `use_mlock`, not a blanket absence of mmap/KV handling.
- **Streaming markdown and row memoization:** streaming answer is rendered as plain `<Text>` until settled (`src/ui/shell/TranscriptTurns.tsx:203-219`); settled Markdown uses `useMemo` (`src/ui/shell/TranscriptMarkdown.tsx:63-67`), and rows are `memo` (`src/ui/shell/TranscriptRow.tsx:27-41`). These help but cannot compensate for the unvirtualized parent ScrollView or ineffective 33 ms cadence.
- **Native modules / main thread:** searched custom iOS Swift modules for force unwraps, `try!`, `as!`, and fatal unwrap patterns; none found. `KalsaIrohModule.swift:7-12,61-115` exposes async functions and parks blocking I/O on worker threads. No source evidence found of synchronous custom JSI work on the JS thread during token generation. This does not audit the pinned llama.rn C++/ObjC internals.
- **Background GPU/heavy work:** the existing iOS background guard stops local generation and releases the poisoned context on lifecycle transitions (`src/host/iosBackgroundGuard.ts:51-85`); Llama prewarm explicitly skips unless `AppState.currentState === "active"` (`src/engine/LlamaService.ts:1112-1117`). No additional confirmed background GPU work surfaced in the checked paths.
- **iOS build/config:** Release has `USE_HERMES = true` (`ios/KalsaAIChat.xcodeproj/project.pbxproj:587`), `COPY_PHASE_STRIP = YES` and `ENABLE_NS_ASSERTIONS = NO` (`:556-558`); bitcode is disabled in Debug (`:380`) and irrelevant to modern iOS distribution. `CADisableMinimumFrameDurationOnPhone` is true in `ios/KalsaAIChat/Info.plist:5-6` and `app.config.js:33-35`; scene lifecycle is configured (`Info.plist:72-87`). No `UIBackgroundModes` key is present, which avoids claiming continuous background execution. Launch storyboard exists; privacy manifest declares accessed API reasons and no collected data (`ios/KalsaAIChat/PrivacyInfo.xcprivacy:4-35`).
- **Unhandled promise coverage:** no app-level `unhandledrejection`/promise-rejection tracking setup was found. `ErrorUtils` captures fatal JS exceptions but is not evidence that every rejected async operation is caught; individual paths need continued `.catch` handling. No specific uncaught-rejection kill path was established by this read-only pass.
