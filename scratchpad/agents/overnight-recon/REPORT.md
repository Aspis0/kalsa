## 1) iroh netmon / Jelly Star AVCs

**Finding / confidence: CONFIRMED for version, netmon behavior, and endpoint retention; PLAUSIBLE that this explains the reported AVC cadence.** Android build lock resolves `iroh 1.2.0` and `netwatch 0.19.3` (`native/kalsa-iroh-mobile/Cargo.lock:1353-1355`: `name = "iroh"`, `version = "1.2.0"`; `:1941-1943`: `name = "netwatch"`, `version = "0.19.3"`). The wrapper directly pins Android `iroh = "=1.2.0"` (`native/kalsa-iroh-mobile/Cargo.toml:23-25`: `iroh = "=1.2.0"`).

- `netwatch::interfaces::State::new()` calls platform `get_state()` (`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/netwatch-0.19.3/src/interfaces.rs:294-300`: “Returns the state of all the current machine's network interfaces.” / “platform::get_state().await”). Android selects the Linux interface implementation (`interfaces.rs:28-40`: `#[cfg(any(target_os = "linux", target_os = "android"))]` / `use self::linux as platform;`); that implementation delegates interface enumeration to `netdev_impl` (`interfaces/linux.rs:9-10`: `pub(super) use super::netdev_impl::{get_state, home_router};`; `netdev_impl.rs:76`: `let raw = netdev::interface::get_interfaces();`).
- The Android `RouteMonitor` is a no-op: `netmon/android.rs:14-18`: `pub(super) fn new(_sender: mpsc::Sender<NetworkMessage>)` / “Android doesn't allow us to do this”. The actor's only Android timer is wall-time checking once per hour: `netmon/actor.rs:33-36`: “Set background polling time to 1h” / `Duration::from_secs(60 * 60)`; timer is installed at `:91`: `time::interval(POLL_WALL_TIME_INTERVAL)`. A network-change snapshot runs only after a monitor message or explicit actor hint (`:137-140`: `let mut new_state = State::new().await`). Thus this is not a 22-second interface polling loop. The reported AVCs are consistent with denied netdev interface enumeration, but the observed ~22-second cadence is not explained by Android netmon's configured timer (PLAUSIBLE attribution).
- The built endpoint is dial-only but alive: `native/kalsa-iroh-mobile/src/bridge.rs:39-42`: “bind a dial-only endpoint”; `:77-79`: `Bridge::start(...)`. JS starts it once per process session (`src/remote/irohBridge.ts:39-48`: “runs exactly once per session”). Android retains it in `bridge` (`KalsaIrohModule.kt:47-48`: `private var bridge: MobileBridge? = null`); only native `OnDestroy` drops it (`:109-121`: `OnDestroy { ... bridge = null ... dropBridge(current) }`). No AppState/background close path was found. **So yes, the endpoint/netwatch actor survives backgrounding while the process/module survives.**
- Knobs: easiest targeted fix is native Android `ConnectivityManager.NetworkCallback` → iroh network-change hint, while retaining netwatch's no-op monitor; or add explicit `stopBridge` on background and restart on active. The iroh endpoint builder exposes `net_report_config` and says “Some non-essential features ... can be disabled” (`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/iroh-1.2.0/src/endpoint.rs:798-806`), but the app's `BridgeConfig` does not currently expose that config. `netwatch 0.19.3` has no Android route watch and no short interval to lengthen. Newer upstream check: **iroh 1.3.0 still locks `netwatch 0.19.3`** (`iroh 1.3.0 Cargo.lock`, `[[package]] name = "netwatch"` / `version = "0.19.3"`), so no dependency-level Android fix is evident in that release ([iroh 1.3.0 Cargo.lock](https://docs.rs/crate/iroh/1.3.0/source/Cargo.lock); [netwatch Android source](https://docs.rs/crate/netwatch/0.19.3/source/src/netmon/android.rs); [actor source](https://docs.rs/crate/netwatch/0.19.3/source/src/netmon/actor.rs)).
- Severity: **log-noise high; battery/perf low-to-moderate from netmon itself, potentially higher from the retained endpoint.** Smallest fix: close the bridge on Android background, if background remote connectivity is not a requirement; otherwise native callback hints plus inspect which other endpoint subsystem is producing the ~22-second enumeration attempts. Do not claim netmon is the cadence root cause without that trace.

## 2) Android model download keep-awake

**Finding / confidence: CONFIRMED.** Downloads activate tagged Expo keep-awake before transfer (`src/host/useModelDownload.ts:208-210`: `await activateKeepAwakeAsync(DOWNLOAD_KEEP_AWAKE_TAG)...`). Android Expo implements this with the Activity screen flag, not a partial CPU wakelock (`node_modules/expo-keep-awake/android/src/main/java/expo/modules/keepawake/ExpoKeepAwakeManager.kt:19-26`: `activity.window.addFlags(WindowManager.LayoutParams.FLAG_KEEP_SCREEN_ON)`). No download foreground-service start appears in the path; the notification helper schedules notifications (`src/host/downloadNotifications.ts:90-115`: `Notifications.scheduleNotificationAsync(...)`).

- The transfer's `try/finally` covers normal success, caught download/load errors, abort returns, and thermal/current-generation early returns inside the try (`useModelDownload.ts:215-235`, `:260-281`: `finally` / `await deactivateKeepAwake(DOWNLOAD_KEEP_AWAKE_TAG)`). Unmount aborts the controller (`:128-135`: `downloadAbortRef.current?.abort()`). `notifications.begin()` is before the `try` (`:208-215`), but its implementation catches setup failures (`downloadNotifications.ts:129-142`), so that does not bypass cleanup. Abrupt process kill cannot execute JS `finally`; the screen flag is Activity-owned, so no app-created service/CPU lock remains to keep a dead process awake (lifecycle inference).
- Severity: **battery/perf moderate while a large download keeps the display on; background CPU battery low from this mechanism.** Smallest fix: keep current tagged acquire/finally; if the owner wants downloads to continue with screen off, replace this with a resumable OS-managed transfer/foreground service rather than a CPU wakelock. (Do not treat current code as one.)

## 3) Whole-history JSON.stringify on send

**Finding / confidence: CONFIRMED.** It is not per keystroke or per generated token. Local inference serializes the assembled `currentMessages` for prefill sizing (`src/engine/LlamaService.ts:4525-4534`: `armPrefillDeadline()` / `JSON.stringify(currentMessages).length / 4`). That prompt is bounded by the context-derived window: `src/context/windowProfile.ts:90-95`: `WINDOW_MAX_MESSAGES = 40`, image window `8`; `:345-351`: char budget is derived from `nCtx` and returned with that message cap. It runs when the send arms/re-arms prefill (`LlamaService.ts:5158`, `:5321`, `:5701`), not per keystroke/token; tool rounds also stringify for their ceiling check (`:5172-5175`).

- Remote PC chat stringifies the mapped message array for the request (`src/engine/remote/openaiTransport.ts:363-371`: `xhr.send(remoteChatBodyJson(...))`; `src/engine/remote/openaiMessages.ts:239-245`: body uses `JSON.stringify({ ... messages: args.messages ... })`). **When image planning needs a wire-size budget**, it also builds the same whole body first (`src/engine/remote/RemoteEngine.ts:700-705`: `bodyBytes` calls `remoteChatBodyJson(...)`). The remote message body can reach the configured 12 MiB budget (`src/engine/remote/wireBudget.ts:8-11`: “whole JSON body's ceiling” / `12 * 1024 * 1024`). This is per send, on the RN JS request path, and again only on an additional remote resend/tool round if one occurs—not token cadence.
- Room send serializes its request body (`src/room/roomApi.ts:171-175`: `encodedBody = JSON.stringify(body)`); the send body is a message object, not room transcript. Room history fetches pages of 200 (`src/room/useRoom.ts:35-36`: “newest 200”; `:286-288`: fetch limit). No full room-history stringify on each send found.
- Severity: **perf moderate for a large remote prompt (two synchronous serializations, up to the 12 MiB budget); local bounded and occasional.** Smallest fix: build the remote JSON once, measure that same string, then pass it into transport. Keep serialization on send, never move it into composer updates.

## 4) Remote PC stream while backgrounded

**Finding / confidence: CONFIRMED for lifecycle wiring and retry behavior; PLAUSIBLE for how much Android runs it while suspended.** Direct PC turns use event-driven XHR/SSE; transport has one 120-second inactivity timeout (`src/engine/remote/openaiTransport.ts:135-167`: `idleTimer` / `setTimeout(... inactivity ...)`) and clearable completion timers (`:141-153`). There is no direct-turn reconnect/poll loop in that transport. iOS has an AppState guard, but it explicitly no-ops off iOS (`src/app/iosBackgroundPlan.ts:47-54`: `if (args.platform !== "ios") return noAction();`; remote turns have `stop = ... && !args.remote`). So direct Android PC streaming is not explicitly aborted on background; if Android suspends the app, delivery waits until execution resumes, otherwise XHR callbacks may continue. No background CPU polling loop was found for direct PC turns.

- Room PC event streams are separate and explicitly paused: `src/room/roomAppState.ts:23-28`: background calls `pauseRoomStreams()`, active calls `resumeRoomStreams()`; `roomSubscriptions.ts:73-80`: pause/resume every wire; `roomStream.ts:365-376`: pause calls `halt()`, resume starts idle watch and dials once. While foregrounded, room stream uses a 5-second health check / 30-second ping timeout (`roomStream.ts:37-42`, `:345-359`) and capped reconnect backoff 0.5–30 seconds (`roomBackoff.ts:2-14`). Those room timers/wires are halted on background.
- A queued room post may retain one capped-backoff retry timer while backgrounded (`roomQueue.ts:361-369`: `setTimeout` → `runAttempt`; `:483-484`: scheduled only for retry verdicts). It is not a streaming-reply loop; foreground stream reconnect flushes the queue (`roomStream.ts:273-277`). Whether that one timer wakes Android while backgrounded depends on RN/OS suspension; severity **low, PLAUSIBLE**.
- Severity: **battery low for direct PC stream (network activity only if OS lets it run); correctness/reliability moderate because Android does not explicitly abort/pause a turn.** Smallest fix: add Android background handling for remote streams (abort and mark partial interrupted, or explicitly opt into a supported background transfer); keep room stream pause. If policy is “no background battery,” aborting the direct stream on background is the smaller change.
