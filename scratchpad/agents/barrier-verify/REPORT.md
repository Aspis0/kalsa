## Step 5 — q4 ILA residual

Resolved. The dispatched q4 GEMM path is the **source-compiled** `kernel_gemm_moe_q4_k_f32_ns`, not the prebuilt `_ila` binary.

Evidence:

1. **Compile-time.** `GGML_OPENCL_USE_ADRENO_BIN_KERNELS` is not in CMakeCache and has no default-ON `option()`. `use_adreno_bin_kernels()` is a compile-time `return false` (`ggml-opencl.cpp:1548-1550`). The `#ifdef` around the `dl_load_library(KERNEL_LIB_NAME)` block (`:6106-6125`) is therefore inactive: no attempt to load a binary-kernel library.
2. **Runtime logs.** None of `mmid.err` / `mmid_m96.err` / `dense.err` contain `loaded bin kernel library`, `failed to load`, or any `*_ila` kernel name. The ILA facility did not even print a fallback line, which is what compiled-out looks like (vs a runtime miss, which would log `failed to load %s, will use builtin kernels`).
3. **Dispatch.** Isolated m=96 GEMM (`n=4`) logged `GGML_OPENCL_LOG_KERNELS: kernel_gemm_moe_q4_k_f32_ns` (source name). The ILA kernel's OpenCL function name is `kernel_gemm_moe_q4_k_f32_ns_ila`.
4. **Host guard.** Because `kernel_gemm_moe_q4_k_f32_ns_bin` stays `nullptr`, the mask-arg block at `ggml-opencl.cpp:23203-23209` runs and pairs the **new** 16-arg source signature with the barrier-safe kernel. The old 13-arg ILA signature is not selected. The guard is the mechanism that would protect a BIN_KERNELS build; this tree never takes that branch.

K2 notes (`PLAN.md:84-85`): the `_ila` binary keeps the old signature; the guard plus compiling the path out is what prevents pairing it with the new source. Device confirms the ILA path is **not taken**.

## `ne01==0` residual (not device-testable)

The clamp uses `ne01 - 1u`. At `ne01==0` that wraps to `UINT_MAX`; the host GEMV x size is also zero, so a launch would be invalid before kernel execution. `supports_op` only checks `ne01 % 32` and does not itself reject zero. GGML has an empty-tensor concept. Whether an empty MUL_MAT_ID can reach this dispatch is an integration precondition, identical to the q2/q3 reference clamp. This session does not claim it is unreachable; it is **not exercisable** with the admitted `%32` device tests (`ne01=1/32/64/96` are all positive). Left **open / noted**.
