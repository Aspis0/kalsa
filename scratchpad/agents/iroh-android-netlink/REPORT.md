# iroh 1.2.0 on Android: netlink denials and Kalsa dial failure

Read-only source/research report for the Kalsa coordinator. Checked the app manifest in `/Users/marco/Projects/kalsa/android` and the current iroh worktree `/Users/marco/Projects/kalsa-wt-iroh`. The requested `native/kalsa-iroh-mobile/src/transport.rs` does not exist: that crate has the UniFFI wrapper in `src/bridge.rs`; the actual iroh transport is `/Users/marco/Projects/kalsa-brain/crates/kalsa-iroh/src/transport.rs`, matching the pinned `kalsa-iroh` dependency revision.

## Findings

### Android untrusted-app restrictions and fatality

Android policy explicitly forbids untrusted apps from binding route netlink sockets and from sending `RTM_GETLINK`: AOSP's policy says `neverallow all_untrusted_apps domain:netlink_route_socket { bind nlmsg_readpriv };` and `neverallowxperm all_untrusted_apps domain:netlink_route_socket nlmsg RTM_GETLINK;` ([AOSP SELinux policy](https://android.googlesource.com/platform/system/sepolicy/+/android16-qpr2-release/private/app_neverallows.te)). RTM_GETADDR dumps can also be denied by device policy; this is interface/address enumeration, not a denial of ordinary UDP/TCP sockets. Android 11/API 30 introduced the route-netlink restrictions for apps; the older bind restriction and the newer `nlmsg_readpriv`/RTM_GETLINK policy are related but distinct ([Android 11 change report and Go issue context](https://github.com/golang/go/issues/40569)). These SELinux denials cannot be fixed by adding an Android manifest permission.

The exact locked `netwatch 0.19.3` has Android-specific handling:

- `netwatch/src/netmon/android.rs`: `RouteMonitor::new` returns `Ok(...)` with the comment “Android doesn't allow us to do this.” So route-change monitoring is deliberately absent, but monitor construction succeeds.
- Its Android-selected `interfaces/linux.rs` uses `/proc/net/route`, then invokes `/system/bin/ip route show table 0`; it does not make netlink dump a required Android startup operation.
- `netwatch` calls `netdev::interface::get_interfaces()`. Locked `netdev 0.45.1` Android code first attempts `RTM_GETLINK`/`RTM_GETADDR`; on error, `os/android/interface.rs` explicitly falls back to `unix_interfaces()` (`getifaddrs`). Subsequent reads under `/sys/class/net/...` are best-effort: `read_to_string(...).ok()?` returns `None` on denial. In other words, they can produce log noise or missing optional interface metadata, not a propagated endpoint error.
- In iroh 1.2.0, `EndpointInner::bind` does await `netmon::Monitor::new()` and maps a real monitor-construction error to `BindError::CreateNetmonMonitor`; on Android the stub returns success. Socket binding is separately mapped to `BindError::Sockets`. Thus the reported interface-enumeration denials are not, on this dependency set, a fatal bind/dial condition.

The `/sys/class/net` `search` AVC corresponds to netdev's optional Android interface metadata/statistics reads (speed, interface type, byte counters, MTU). It is not used to open iroh's QUIC socket. The iroh 1.2 builder defaults to unspecified IPv4 `0.0.0.0` and IPv6 `[::]`; Kalsa does not bind to a selected interface or read `/sys/class/net` itself.

### Real Android use and integration patterns

- **Delta Chat / Chatmail Android** ships the Rust core, which documents “Peer-to-Peer networking using Iroh” and is used by Android frontends ([Chatmail core README](https://github.com/chatmail/core), [Delta Chat Android](https://github.com/deltachat/deltachat-android)). Important version caveat: current core Cargo.toml uses `iroh = { version = "0.35", default-features = false }`, not iroh 1.2.0 ([core Cargo.toml](https://github.com/chatmail/core/blob/main/Cargo.toml)). This proves production Android use of iroh, but is not direct evidence for 1.x Android compatibility.
- **iroh-live Android demo** documents end-to-end testing on a real Android device to Linux and builds `iroh-live` with `default-features = false`; its Kotlin app talks to a Rust JNI bridge, built with cargo-ndk ([demo README](https://github.com/n0-computer/iroh-live/blob/main/demos/android/README.md)). This is direct Android/i​​roh integration evidence, though the demo's precise transitive iroh version should be checked against its lockfile before treating it as a 1.2.0 test.
- **iroh-ssh-android** is a Flutter app with Rust core through flutter_rust_bridge; it describes real iroh P2P connections and configurable/default relays ([project README](https://github.com/futpib/iroh-ssh-android)). **dsh-tether** ships an Android APK with a Rust iroh sidecar ([project README](https://github.com/zexadev/dsh-tether)). These demonstrate viable packaging and app architectures, but their README claims alone do not establish exact Android netwatch behavior for iroh 1.2.

For iroh 1.2 specifically, the bundled `iroh-dns 1.3.0` Android documentation says the app *may* install JNI context: `iroh::dns::install_android_jni_context(JavaVM, application_context)`. That enables fetching Android's configured DNS nameservers. Its documented fallback is public nameservers if context is not initialized; the same docs warn that missing context can panic when the app uses `panic = "abort"` ([iroh-dns source/docs](https://docs.rs/crate/iroh-dns/1.3.0/source/src/dns.rs)). This is separate from SELinux/netlink. Kalsa's Kotlin module currently gets `applicationContext` for `filesDir`, but has no visible `install_android_jni_context` call or `JNI_OnLoad` initializer (`modules/kalsa-iroh/android/.../KalsaIrohModule.kt`). Add initialization before constructing the endpoint, using JNI_OnLoad or an equivalent host startup hook; verify that it runs before `MobileBridge.new` binds/builds address lookups. If adding JNI plumbing is undesirable, explicitly configure a reliable Android DNS resolver and ensure the panic strategy permits iroh's documented fallback.

Permissions are not substitutes for SELinux access. `INTERNET` permits ordinary network sockets. Android's connectivity guidance lists `ACCESS_NETWORK_STATE` for network-state APIs ([Android networking guide](https://developer.android.com/develop/connectivity/network-ops/connecting)); it is not a grant for route-netlink dumps and is not needed for a UDP socket to exist. `CHANGE_WIFI_MULTICAST_STATE` permits Wi-Fi multicast lock usage; it is relevant only if the app needs to receive Wi-Fi multicast, e.g. SSDP discovery for UPnP port mapping ([Android permission reference](https://developer.android.com/reference/android/Manifest.permission#CHANGE_WIFI_MULTICAST_STATE)). Neither permission enables `nlmsg_readpriv`.

### Kalsa transport and deadline

`native/kalsa-iroh-mobile/src/bridge.rs::MobileBridge::new` calls `BridgeConfig::dial_only().with_relay(RelayChoice::N0Public)`. In `crates/kalsa-iroh/src/transport.rs`, the dial-only N0 builder clears the N0 publisher, then adds `PkarrResolver::n0_dns()` and `DnsAddressLookup::n0_dns()`; it keeps the N0 relay mode. No explicit socket address is configured; iroh binds the default wildcard IP sockets. The phone has no inbound ALPN and does not publish its own id; that does not prevent dialing the desktop. The desktop's serving endpoint must publish/resolve under its stable node id and offer the matching lane ALPN (`kalsa/door-tunnel/1` or `kalsa/pair-desk/1`).

`BridgeConfig::dial_only()` sets 10 seconds. `Transport::dial` creates one absolute deadline before `endpoint.connect`, and applies that same deadline to `connect` (address lookup, path establishment, QUIC handshake) and `open_bi`. It does **not** include endpoint startup/bind; nor does it cover stream reads/writes. A reported failure in 1–2 s is therefore not the configured timeout: log the UniFFI error variant. `Deadline` should normally occur near 10 s; a fast `Transport` error points to immediate resolution/connection/ALPN/peer errors, and a fast `Io` during `startBridge` points to key-file or endpoint startup.

The locked iroh 1.2 feature defaults include `portmapper` and `tls-ring` (and metrics). `PortmapperConfig::default()` is enabled; this makes UPnP/PCP/NAT-PMP probing available. iroh net-report is an internal module in this release, not a separate Cargo crate; its reporting/probes are separate from binding and are not what the reported netlink denial blocks. Android's no-op netwatch route monitor also means no automatic route-change events are delivered by that path.

## Ranked causes for the fast phone failure and fixes

1. **Address lookup / Android DNS initialization or reachability (highest).** Dial by bare node ID requires n0 address lookup. Kalsa has no JNI DNS-context initializer. Without it, iroh-dns uses public fallback nameservers; a carrier/private-DNS/Wi-Fi policy may make those unusable, producing fast resolution failure. On Rust builds using `panic = "abort"`, missing JNI context may panic instead of falling back. **Fix:** initialize iroh's Android JNI context before `MobileBridge.new`, or configure a resolver that works on-device; verify both N0 HTTPS/Pkarr and DNS paths in logs. No Cargo feature or manifest permission fixes an unavailable resolver. Add `ACCESS_NETWORK_STATE` if the app will use Android connectivity APIs to select/retry on network changes.
2. **Remote identity, ALPN, or remote service lifecycle mismatch.** The phone's `connect` requests one fixed ALPN, and the desktop must be running the corresponding serving version under the scanned node id. A stale node id, desktop endpoint not currently publishing, desktop bridge stopped, or incompatible ALPN can return before 10 seconds. **Fix:** confirm desktop publication and target node id; align Kalsa transport pin and lane ALPN. No manifest permission fixes protocol mismatch.
3. **Relay/discovery blocked on the current network.** The phone relies on n0 DNS and N0 public relays, then direct path discovery/hole punching. Captive portal, DNS filtering, UDP restrictions or blocked relay HTTPS/TLS can fail quickly or exhaust the 10 s budget. **Fix:** test N0 DNS and relay reachability on the same phone/network; use a custom reachable relay if the network blocks N0. Do not infer failure from SELinux AVCs alone.
4. **Android portmapper multicast side work.** Iroh's default enables portmapper, which can probe local routers; restricted multicast can degrade direct-address discovery but the N0 relay remains the fallback. **Fix:** for the phone, set `.portmapper_config(PortmapperConfig::Disabled)` (or use `iroh` with `default-features = false` and re-enable required features such as `tls-ring`; ensure Cargo feature unification does not turn portmapper back on). If retaining SSDP receive, add `CHANGE_WIFI_MULTICAST_STATE` and acquire a Wi-Fi multicast lock. This is not a fix for a fast hard error unless logs specifically show portmapper failure.
5. **Missing `ACCESS_NETWORK_STATE` in app manifest (secondary, not socket permission).** `/Users/marco/Projects/kalsa/android/app/src/main/AndroidManifest.xml` declares `INTERNET` but not `ACCESS_NETWORK_STATE`; in the current iroh worktree, `app.config.js` likewise has no such permission and `modules/kalsa-iroh/android/src/main/AndroidManifest.xml` is empty. **Fix:** add `android.permission.ACCESS_NETWORK_STATE` in Expo `android.permissions` if the app or its Android networking glue queries `ConnectivityManager` / network state. Keep `INTERNET` (already present). This cannot authorize netlink nor cure address lookup/ALPN failures by itself.

## Decision

The observed `{ nlmsg_readpriv }` and `/sys/class/net` AVCs are expected Android restriction/fallback noise for this dependency graph, not evidence that iroh endpoint bind or dial is denied. The strongest Android-specific actionable gap is missing explicit JNI context for iroh-dns, especially if system DNS is needed or release panic behavior is abort; next inspect the actual error variant and iroh resolver/relay logs. Add `ACCESS_NETWORK_STATE` for Android connectivity state monitoring, not as a netlink workaround. `CHANGE_WIFI_MULTICAST_STATE` is only for keeping multicast reception enabled if portmapper SSDP is intentionally used.
