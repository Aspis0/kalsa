This is a fixed workload for comparing prefill and decode behavior on one phone. Treat every paragraph as ordinary source text. Do not browse, call tools, infer measurements, or continue an earlier conversation. The text is deliberately self-contained so it can be pasted unchanged into a new chat for every arm. Do not summarize it during prefill and do not answer the factual content before reaching the final instruction.

The study concerns how a mobile device handles a long input followed by a small, bounded response. A request can place most of its work before the first generated token, during prompt evaluation, or after that point, during token generation. Those phases may use different compute backends. A useful comparison therefore records the prompt evaluation time and the generation rate separately, while holding model, input bytes, output request, application state, and device conditions constant. The observed route must be checked from runtime evidence; a requested route alone does not prove where work executed.

A repeatable procedure begins by checking that the device is disconnected from every charger and that its screen remains awake. The operator records charge level, battery temperature, platform thermal status, and any exposed skin sensor. The device is left idle with the application visible until the specified start point is reached. A run begins only after all start conditions are satisfied. During the run, the sampler records the same fields at a short, regular interval, along with current and voltage when readable. Missing or implausible readings invalidate the arm instead of being silently replaced by estimates.

Each repetition starts in a genuinely empty conversation. Earlier messages can remain in the model context even when they are not visible in the composer, so simply replacing the text field is insufficient. Before sending the workload, the operator creates a new chat through the application’s own conversation action and verifies that no previous user or assistant messages appear in its transcript. The benchmark text is then inserted as the exact same UTF-8 bytes. No manual editing, automatic rewriting, or additional instruction is allowed between repetitions.

The prefill request should remain identical across the GPU and CPU arms. A route setting is a request to the engine and must be paired with evidence identifying the backend that performed the prompt evaluation. Decode should remain on the same intended processor in every arm. If a setting only takes effect during engine initialization, the app must be restarted consistently before every arm, followed by the same load and warm-up procedure. If that setting applies per turn, it should be set and acknowledged immediately before sending the prompt.

For each arm, preserve the complete timestamped log from before input delivery until generation stops. Record the requested route, actual prefill backend, prompt token count, prefill duration, number of generated tokens, and decode rate. Also record the temperature and platform status at the start and their peaks. The battery energy estimate should use the time series of current and voltage, with a stated integration method and units. An arm that crosses a stop threshold is stopped immediately and marked stopped; its partial observations are not treated as a completed comparison.

Results should be interpreted narrowly. A faster prompt evaluation does not by itself establish that the whole response is faster. A lower final battery temperature can reflect a shorter workload, an earlier stop, or recovery between repetitions. Pairwise comparisons are valid only when the input token count and generated-token count match and when both arms begin at the prescribed thermal point. If any of these conditions differ, report the mismatch and do not claim a backend or thread-count effect.

The workload text itself has no dependency on chat history, files, tools, or live facts. It describes a hypothetical measurement protocol rather than asking for advice about a real person or device. Keep the answer compact and deterministic in shape: return a JSON object with keys "phase", "controls", "evidence", and "caveat". Give one short sentence for each value, do not add a preamble or markdown fence, and keep the complete JSON answer to at most 64 whitespace-separated words. This requested answer shape is only a prompt-level bound; it is not an engine-enforced generation-token limit.

Before comparing two rows, verify that both use the same saved prompt file and report its checksum. A fresh conversation removes prior transcript text, but it does not erase global application instructions or model-specific prompt wrappers. The recorded prompt token count should therefore distinguish user-text tokens from the full runtime prompt count when the engine exposes both. Preserve both values rather than assuming they are interchangeable. Do not alter the model, sampling settings, system prompt, or context limit between arms. If the app cannot guarantee an exact response length, record the generated token count and stop method explicitly; do not label a natural end-of-answer as a fixed decode length.
