- Desktop shows a QR containing v3 JSON (`reachable`, one-shot `code`, `nonce`, optional `node`, optional `tailnet`), not merely a URL. `~/Projects/kalsa/src/pairing/pairingQr.ts:49-54` — “desktop's v3 pairing square (one QR = one JSON object)”; `:75-94` parses those fields. The QR scanner is `src/screens/PairingQrScanner.tsx:52` (calls `parsePairingQr`).
- Paste/deep-link is also supported: `~/Projects/kalsa/src/pairing/pairingInvite.ts:54-71` accepts JSON or `https://kalsa.io/pair#<base64url>` and `kalsa://pair#...`. Android intent filters are in `app.config.js:37-47`; JS listens for initial and incoming URLs in `src/host/HostOverlays.tsx:153-169`. iOS already has scheme `kalsa` (`app.config.js:8`) but no iOS Associated Domains / universal-link config is present. QR scan works without any deep-link association.
- Pairing desk and chat/door have separate lanes. When QR has a node and native module exists, claim/complete use iroh (`src/screens/PairingScreen.tsx:279-293`); otherwise pairing uses `fetch` to the configured desk URL. Door requests use the selected road (`src/remote/doorRoad.ts:62-100, 115-143`).

### Tailscale / HTTPS road

- A v3 QR can carry a validated `https://<tailnet-host>` (`pairingQr.ts:29-44`). Scanning it derives door URL plus desk URL on port 8443 (`src/screens/PairingScreen.tsx:363-366`; `src/pairing/pairingUrls.ts:16-32`). It is HTTPS over ordinary RN fetch/XHR, routed by the OS; Kalsa has no embedded Tailscale SDK.
- App URL policy accepts HTTPS, or HTTP only for loopback (`src/pairing/pairingUrls.ts:3-13`). Authorization is sent for HTTPS or loopback HTTP only (`src/engine/remote/remoteUrl.ts:73-79`). Thus the intended tailnet road is TLS HTTPS; plain `http://100.x` cannot safely carry the bearer today even if the OS allows it.
- Android cleartext is globally off: `app.config.js:69-70` — `usesCleartextTraffic: false`. `plugins/withLoopbackCleartext.js:11-19` allows only `127.0.0.1`, `localhost`, `::1`; `:33-37` attaches this network security config. There is no checked-in Android project; Expo prebuild generates it. Search of the app manifest/config/module sources found no `FOREGROUND_SERVICE`, `startForeground`, or foreground service declaration. Iroh has an empty module manifest (`modules/kalsa-iroh/android/src/main/AndroidManifest.xml:1`). The app's explicit Android special case is loopback cleartext, not a Tailscale exception.

### iroh road

- JS native facade: `~/Projects/kalsa/modules/kalsa-iroh/src/index.ts:8-19` exposes `startBridge`, `nodeId`, `openTunnel`, byte read/write/shutdown; `:43-47` currently says “KalsaIroh native module unavailable (Android only)”. Expo module config registers only Android (`modules/kalsa-iroh/expo-module.config.json:1-5`). JS adaptation is `src/remote/irohBridge.ts`; byte HTTP/1.1 rides the native QUIC stream in `src/remote/irohHttp.ts`; `src/remote/irohChatXhr.ts` adapts streaming SSE to XHR; `src/pairing/pairingDeskFetch.ts` dials the `desk` lane.
- Rust crate: `native/kalsa-iroh-mobile/` (`Cargo.toml:1-8`) wraps the pinned `kalsa-iroh` desktop protocol and Tokio (`:15-27`). UniFFI exports `MobileBridge`/`Tunnel` in `src/bridge.rs`; Android-specific JNI context is isolated in `src/android_context.rs`, and `src/lib.rs:13-18` gates that module on `target_os="android"`.
- Build: `.github/workflows/apk.yml:228-260, 286-313` installs Rust + `cargo-ndk`, builds `libkalsa_iroh_mobile.so` from `native/kalsa-iroh-mobile`, validates 16 KB ELF alignment, and copies it to `modules/kalsa-iroh/android/src/main/jniLibs/$ABI/`. Generated Kotlin UniFFI bindings live under that module and JNA is its runtime (`modules/kalsa-iroh/README.md:16-22, 41-45`). No iOS library, Swift binding, or Swift Expo module exists.
- Crate README records Android `opt-level="z"` release size at **11.16 MB** vs **11.55 MB** for `"s"` (`native/kalsa-iroh-mobile/README.md:28-36`). This is not an iOS size estimate; measure the Apple device/simulator xcframework and app archive before deciding whether to ship both slices.

## 2. Tailscale on iOS: required changes and limits

1. Keep the desktop's QR-provided tailnet endpoint HTTPS. Give Brain a certificate trusted by iOS for its MagicDNS hostname (or route through a trusted HTTPS proxy). ATS requires HTTPS by default for URL Loading System traffic: [Apple ATS](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSAppTransportSecurity).
2. If plain HTTP remains a supported configuration, make the exception as narrow as possible in `app.config.js` `ios.infoPlist.NSAppTransportSecurity`. For MagicDNS use an exact DNS entry in `NSExceptionDomains` with `NSExceptionAllowsInsecureHTTPLoads: true`; Apple requires App Store Connect justification and may do additional review for this exception. For literal 100.x IP, iOS 17+ allows exact IP/CIDR entries in `NSExceptionDomains`; that IP exception does not apply when the request uses its hostname, or vice versa. iOS 16 (the app's current 16.4 deployment target) cannot target an IP there; a global `NSAllowsArbitraryLoads` workaround is broad and needs justification. Do not use global arbitrary loads for a supported feature if HTTPS is feasible. `NSAllowsLocalNetworking` is not the correct MagicDNS exception: it covers unqualified names, `.local`, and IP literals as an ATS local-networking setting, with OS-version differences, not arbitrary fully-qualified `*.ts.net` names. Sources: [NSExceptionDomains](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSAppTransportSecurity/NSExceptionDomains), [NSAllowsLocalNetworking](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking), [Apple ATS exception review guidance](https://developer.apple.com/documentation/security/preventing-insecure-network-connections).
3. Tailscale's iOS app installs a Network Extension VPN; its documentation says the VPN gives **all apps** access to the tailnet. Kalsa can use ordinary HTTPS/fetch to the desktop after the owner signs into the correct tailnet and has Tailscale connected. No Kalsa-specific VPN entitlement or Tailscale SDK is indicated. [Tailscale remote-server access](https://tailscale.com/docs/use-cases/personal-or-at-home-use/access-nas-media-file-servers?tab=ios+%2F+ipados), [iOS VPN configuration](https://tailscale.com/docs/integrations/mdm/ios).
4. Add `NSLocalNetworkUsageDescription` only if Kalsa performs local-LAN operations (e.g. a future direct LAN address or service discovery); Apple's key covers direct connections to local hosts as well as Bonjour. QR entry itself needs no Bonjour. If Bonjour discovery is added, list its service types in `NSBonjourServices`. Do not treat this permission as a tailnet/ATS bypass. Apple says simulator does not support Local Network privacy prompts, so prompt/denial requires a physical device. [NSLocalNetworkUsageDescription](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSLocalNetworkUsageDescription), [TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
5. Foreground operation is the supported baseline. iOS normally suspends apps shortly after backgrounding; existing sockets/QUIC tasks cannot be promised to remain alive. Reconnect or fail clearly on foreground. A short UIKit background task only grants bounded finishing time, not an always-on service. [Apple background execution modes](https://developer.apple.com/documentation/Xcode/configuring-background-execution-modes), [UIKit background time](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time).

## 3. iroh on iOS: bridge work, upstream evidence, constraints

- Port the existing crate rather than rewriting the road: separate Android-only `iroh`/JNI/`ndk-context` setup from cross-platform Rust, verify the pinned `kalsa-iroh` and iroh dependency graph compiles for Apple, then build Rust device `aarch64-apple-ios` and simulator `aarch64-apple-ios-sim` (plus x86_64 simulator only if the app supports it). Package static libraries and headers in an XCFramework. Generate UniFFI Swift bindings from the Apple library and add `modules/kalsa-iroh/ios/KalsaIrohModule.swift` + podspec; register `"apple"` in `expo-module.config.json`; resolve the key path with iOS `FileManager` and preserve JS method names. Swift wrapper must expose asynchronous Expo methods and keep blocking FFI off the JS/main thread.
- Existing Android build pipeline is Linux/NDK-only (above). There is no app CI job for Apple or iroh artifact. Mac build recipe should use Xcode toolchain and `xcodebuild -create-xcframework`; `uniffi-bindgen generate --language swift` (with the generated C header/module map) supplies Swift glue. Check whether the dependency graph needs Apple `SystemConfiguration` / `CoreWLAN`/Network frameworks before linking. Relevant upstream example: [n0-computer/hello-iroh-ffi Swift README](https://github.com/n0-computer/hello-iroh-ffi/blob/main/swift/README.md) demonstrates iOS + macOS, simulator run, SwiftPM XCFramework consumption and manual endpoint-ID entry. [n0-computer/iroh-ffi Swift build docs](https://github.com/n0-computer/iroh-ffi/blob/main/README.swift.md) and [Makefile](https://github.com/n0-computer/iroh-ffi/blob/main/Makefile.toml) document its Apple XCFramework pipeline and simulator consumer checks. This is evidence upstream iroh has an Apple path, not proof this pinned Kalsa fork builds unchanged.
- Current crate is `cdylib` + `lib` (`Cargo.toml:7-8`), and Android JNI context is already cfg-isolated, but dependencies/platform resolver and Swift FFI still need explicit Apple validation. Rust targets are necessary, not sufficient. Apple's iOS networking permissions are not Bonjour requirements for QUIC unicast; no Bonjour browse is part of this design.
- iroh-on-iOS is in real use, but not issue-free: [iroh issue #4319](https://github.com/n0-computer/iroh/issues/4319) documents iOS 16 UniFFI dialing and a ~30s relay failover outage; [#4424](https://github.com/n0-computer/iroh/issues/4424) reports iOS/iPhone CGNAT UDP mapping churn and relay fallback delays. Test both relay and direct paths and expect foreground reconnection. The phone is dial-only (`native/kalsa-iroh-mobile/src/bridge.rs:37-49`); no background accept service is needed.
