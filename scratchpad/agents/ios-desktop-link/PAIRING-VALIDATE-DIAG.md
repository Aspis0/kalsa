## Finding

The reported failure is the **PairingScreen door-address preflight**, before `PairingSession.begin()` and before any claim. It is not evidence of a malformed code/nonce, an iOS random-source failure, or an APNs/push-token problem.

The invite parser accepts v3 with a node and no tailnet (`~/Projects/kalsa-ios/src/pairing/pairingQr.ts:47-55, 67-94`; `~/Projects/kalsa-ios/src/pairing/pairingInvite.ts:40-45`). With no tailnet, `acceptScannedSquare` falls back to the phone's configured URL prefill and immediately calls `run` (`~/Projects/kalsa-ios/src/screens/PairingScreen.tsx:360-375`). That prefill comes from `initialDoorUrl`, which Settings obtains from `getRemoteBrainUrl()` (`~/Projects/kalsa-ios/src/screens/SettingsScreen.tsx:262-270, 1516-1525`; `~/Projects/kalsa-ios/src/engine/remote/remoteSettings.ts:80-82`). An empty setting produces empty door and desk URLs (`~/Projects/kalsa-ios/src/pairing/pairingUrls.ts:16-34`).

In `run`, lines 245-250 reject an invalid/empty door URL, log `validate`, set the validation failure, and return. They run before the desk URL guard, before session construction, and before the code/nonce MAC checks (`~/Projects/kalsa-ios/src/screens/PairingScreen.tsx:230-257`). The collapsed-screen message uses `!doorReady` to render “Set your computer's address on this phone before pairing.” (`~/Projects/kalsa-ios/src/screens/PairingScreen.tsx:119-123, 395-405`; English string at `~/Projects/kalsa-ios/src/i18n/en.ts:472-485`). This matches both the displayed message and `KALSA_PAIRING_FAIL {"stage":"validate","status":null}`. The one-shot code was not claimed.

The check the question calls out at `~/Projects/kalsa-ios/src/pairing/pairingTransport.ts:181-200` is a *different* possible `validate` source: it decodes the code and nonce and calls `phoneMacHex`, catches any failure, logs `validate`, and returns before the claim. It was not reached in this attempt because the screen returned at lines 245-250.

## What `deliveryToken` and `doorReady` mean

- `deliveryToken` is a fresh, random 16-byte (32 lowercase hex character) per-ceremony delivery identity. The `PairingSession` constructor calls `secureRandomBytes(16)` and stores its hex (`~/Projects/kalsa-ios/src/pairing/pairingTransport.ts:11-13, 71-80, 143-157`). The implementation obtains bytes from `expo-crypto.getRandomBytes`, documented in source as the platform CSPRNG. `phoneMacHex` checks its format and includes it in the signed phone payload (`~/Projects/kalsa-ios/src/pairing/pairingWire.ts:90-110`); after claim, it is sent as `delivery_token` during completion (`~/Projects/kalsa-ios/src/pairing/pairingTransport.ts:240-253`). It is **not** the computer's address, an APNs token, or an `expo-notifications` token. It does not come from a push module.
- `doorReady` is simply `isAllowedPairingUrl(fields.doorUrl)` (`~/Projects/kalsa-ios/src/screens/PairingScreen.tsx:119-123`). `fields.doorUrl` is initialized from the configured `getRemoteBrainUrl()` prefill or from a parsed invite's optional tailnet URL. The UI also disables Start when this value is false (`~/Projects/kalsa-ios/src/screens/PairingManualForm.tsx:20-22, 94-109`). It has no relationship to a push token or an Android-only setting.

## iOS versus Android

This failure is not inherently iOS-specific. The parser, URL prefill, screen guard, and pairing transport are shared React Native TypeScript. With the same build logic and an empty configured Brain URL, Android takes the same `run` branch and rejects before claim. An iOS build without the `aps-environment` entitlement is not implicated: this transport makes its own CSPRNG delivery token using `expo-crypto`; it does not request or consume an APNs token. A platform-specific difference would matter only if one platform has a different `getRemoteBrainUrl()` value or native iroh-module availability; neither would make this missing-door guard an APNs issue.

## What Brain v3 promises

Brain's v3 payload explicitly defines `reachable` as the pairing desk's loopback bind, says the phone never dials it because pairing traffic arrives through the tunnel, and says it remains MAC-bound (`~/Projects/kalsa-brain/crates/kalsa-pairing/src/payload.rs:30-37`). The node is present when the iroh road is open. The optional `tailnet` field is the door's Tailscale base URL only when both serve rules are detected, and the source calls it “a convenience ... never a fact the ceremony depends on” (`~/Projects/kalsa-brain/crates/kalsa-pairing/src/payload.rs:44-61`). Brain requires a node to mint an invite (`~/Projects/kalsa-brain/crates/kalsa-pairing/src/invite.rs:145-168`).

So an **iroh pairing ceremony** (claim and completion) is intended not to depend on a door/tailnet URL: the phone's node-bearing invite selects the iroh desk fetch (`~/Projects/kalsa-ios/src/screens/PairingScreen.tsx:279-303`; tunnel fetch uses the node at `~/Projects/kalsa-ios/src/pairing/pairingDeskFetch.ts:62-79`). The missing `tailnet` key is valid, not a malformed v3 invite. However, this app currently makes a configured door URL a prerequisite anyway. The URL is also saved with the credential and used for the subsequent `/props` confirmation probe (`~/Projects/kalsa-ios/src/screens/PairingScreen.tsx:311-342`; `~/Projects/kalsa-ios/src/pairing/pairingConfirmation.ts:138-165`). Thus “can execute the pairing protocol without a door URL” and “the current app can finish and confirm a usable pairing with no door URL” are not the same claim. Removing the guard alone would leave that later address-dependent flow unresolved.

## Smallest correct fix and tomorrow's test

**For the current app, the smallest safe action is configuration, not a code edit:** before opening the invite, set the phone's **Settings → Remote Brain → Your computer's address** to the owner's actual phone-reachable Brain door base URL (for example, the owner's working Tailscale/Serve URL, or a working same-LAN URL). Do not enter the invite's loopback `reachable` value as the phone's address; it names the desk's loopback bind. Settings persists this URL via `setRemoteBrainUrl` (`~/Projects/kalsa-ios/src/screens/RemoteBrainSettings.tsx:332-347`; `~/Projects/kalsa-ios/src/engine/remote/remoteSettings.ts:184-196`). Reopen the fresh invite after saving. With no tailnet field, the app will prefill from this configured address; its generated HTTPS desk URL is checked by the UI, but the node-bearing invite selects the iroh lane for the actual claim/completion.

For the owner-present run: (1) while the owner is present, obtain the Brain door base URL that the owner's Mac currently serves and enter/save it on the phone under Remote Brain settings; (2) verify the Pairing screen shows the configured address rather than the “set your computer's address” message; (3) open the still-unclaimed, fresh `kalsa://pair#…` invite; (4) have the owner watch Brain for the claim and approve/Allow it when prompted; (5) verify the phone receives completion and reaches its confirmation/paired state. If the Mac has no phone-reachable door URL yet, establish that separately before expecting post-pair confirmation or remote use.

**Source-level product fix, if address-free link pairing is the intended UX:** change `~/Projects/kalsa-ios/src/screens/PairingScreen.tsx` and its pairing state flow, not the token code and not Brain's valid v3 payload. Let a node-bearing iroh invite reach claim/completion without `doorReady`, then collect/require the phone-reachable Brain door URL before saving a usable credential and starting `/props` confirmation (or otherwise represent the pending-address state explicitly). Merely changing `doorReady` to accept any node is incomplete because the current save/confirmation code uses `doorUrl`. Brain should add `tailnet` only when it has actually verified its serve rules; its source says an absent field is expected and optional.
