## 2. The 14 app-side fixes — do any change runtime behaviour?

Runtime-affecting: **two, and neither is disclosed as such.**

**2.1 `StatusBar backgroundColor` removal — Android runtime change, CONFIRMED.**
`App.tsx:167` `<StatusBar barStyle={palette.statusBar} />`. Confirmed against the changelog
(`sdk58.md:195`): `the deprecated StatusBar backgroundColor, translucent, and
networkActivityIndicatorVisible props are removed`. Android-only in practice. The report does
flag this — to its credit — but sizes it as "one visual check".
Note the accompanying `const { colors, palette }` → `const { palette }` destructure edit is a
second, undocumented edit in the same file.

**2.2 `PdfToImages.tsx` `ComponentType<any>` — no runtime change, but it silently widens.**
`PdfToImages.tsx:12` `const PdfHostWebView = WebView as unknown as React.ComponentType<any>;`.
Same object at runtime, so zero behaviour change — **CONFIRMED benign**.
But the companion edit is a genuine narrowing of *checking*:
`onShouldStartLoadWithRequest={(request: { url: string }) => ...}`. That hand-written param
type replaces webview's real prop type, so any future change to that callback's contract is
now invisible to `tsc`. Low severity, but it is exactly the "silently widened type" pattern the
brief asked about.

**2.3 The `CodegenTypes` ambient shim — faithful, but shadows a real RN file. CONFIRMED benign, PLAUSIBLE latent.**
I checked the shim against RN 0.88's real definition because I suspected a wrong `WithDefault`.
**It is correct.** `types_generated/Libraries/Types/CodegenTypes.d.ts`:
`export type WithDefault<Type extends DefaultTypes, Value extends (null | undefined | Type) | string> = null | undefined | Type;`
shim `reactNativeCodegenTypes.d.ts:20-21`: `Value extends Type | string | undefined | null` → `= Type | undefined | null`. Same union, reordered constraint. `DirectEventHandler`, `Double`, `Int32`, `DefaultTypes` also match. **The report's "the four codegen aliases" claim is accurate.**
Latent risk: it is a hand-maintained copy of a `@generated SignedSource<<aaf3626222282b843a4477788d8e6f92>>`
file that drops `Float`, `UnsafeObject`, `UnsafeMixed`, `BubblingEventHandler`, `EventEmitter`,
and an ambient `declare module` wins over node_modules resolution for the whole project. When
webview/view-shot catch up, this file becomes a *shadow*, not dead code. The report calls it
"drop this file when webview ships RN 0.88 types" — correct, but the shadowing hazard is
unstated.

**2.4 `tsconfig.json` `customConditions` — CONFIRMED as documented, and the changelog backs it.**
`tsconfig.json:12` `"customConditions": ["react-native", "react-native-legacy-deep-imports"]`.

**2.5 `typography.ts` mutable-view cast — CONFIRMED type-level only.**
`typography.ts:119` `const mutable = live as { fontSize?: number; lineHeight?: number };`.
Identical mutation, identical objects. No runtime change. Claim accurate.

**2.6 `useShareIn.ts` `?? null` — CONFIRMED behaviour-identical.**
`useShareIn.ts:110` `.then((url) => consume(url ?? null))`; `useShareIn.ts:100`

## 6. whisper.rn patch and the kalsa.rn "selectors no longer declared" claim

**6.1 `RCTCxxBridge` really is gone — CONFIRMED.**
`find node_modules/react-native -name "RCTCxxBridge*.h"` returns only `RCTCxxBridgeDelegate.h`.
`React/CxxBridge/RCTCxxBridge.h` does not exist. The report's claim is correct.

**6.2 BINDING-PATCHES.md's stated reason is FALSE — REFUTED.**
`BINDING-PATCHES.md` (SDK 58, item 2) asserts:
> `RN 0.88's public RCTBridge header exposes no runtime/jsCallInvoker/batchedBridge at all.`

All three are wrong. `RCTBridge+Private.h:49` declares
`@property (atomic, strong) RCTBridge *batchedBridge;`, and
`RCTTurboModule.h:204-205` declares `@interface RCTBridge (RCTTurboModule)` with
`- (std::shared_ptr<facebook::react::CallInvoker>)jsCallInvoker;`. Both ship in the prebuilt
`React.framework/Headers` (verified under
`/tmp/kalsa-ios-dd58/.../React-Core-prebuilt/React.framework/Headers/`). The actual failure is
narrower and more interesting: `runtime` is not on `RCTBridge` at all (the run-2 error
`property 'runtime' not found on object of type 'RCTBridge *'` proves it), and `RCTCxxBridge.h`
is gone so the old `RCTCxxBridge *` declaration dies with it.

**6.3 How the patched code actually survives — the report's mechanism is wrong, the conclusion survives.**
`RCTBridgeProxy.mm:259-263`:
```objc
- (RCTBridge *)batchedBridge
{
  [self logWarning:@"This method is not supported. Returning bridge proxy." cmd:_cmd];
  return (RCTBridge *)self;
}
```
`RCTBridgeProxy.mm:99-109` implements `- (void *)runtime` (returns `_runtime`) and
`- (std::shared_ptr<...>)jsCallInvoker`, each preceded by
`[self logWarning:@"Please migrate to C++ TurboModule or RuntimeExecutor." cmd:_cmd];`.
`RCTBridgeProxy` is an `NSProxy` (`RCTBridgeProxy.h:19`), not an `RCTBridge` subclass.

So in bridgeless mode `self.bridge` is an `RCTBridgeProxy`; `bridge.batchedBridge` returns
`(RCTBridge *)self` — non-nil — and `cxxBridge.runtime` resolves against the proxy. The
`if (!cxxBridge) cxxBridge = (id<...>)bridge;` fallback (`RNWhisper.mm:323-325`) is therefore
**dead code**, not a safety net. That is why kalsa.rn's identical pattern at `RNLlama.mm:104-114`
worked, and the report is right that the JSI install ran.

The report's phrasing — `relies on selectors the public RN 0.88 header no longer declares` —
is wrong in the part that matters. The selectors are declared *and implemented*; the code works
by obtaining the object through a **type lie**: `(RCTBridge *)self` on an `NSProxy`. RN is
logging an explicit "Please migrate to C++ TurboModule or RuntimeExecutor" every call. "Deprecation-shaped"
is the right conclusion; the mechanism is type-laundering through an NSProxy, not missing
declarations.

**6.4 Real release risk — PLAUSIBLE, and the report understates it.**
Not a bridged/bridgeless difference (same code path in both configs), but three live hazards:
1. The pattern only works because `RCTBridgeProxy.batchedBridge` returns `self`. That method is
   itself annotated `"This method is not supported."` A single RN refactor deleting it turns a
   working JSI install into an `unrecognized selector` crash at first `install()`.
2. `RCTBridgeProxy` is an `NSProxy`. There is no compile-time guarantee the selectors exist; the
   only signal is a runtime string.
3. If `self.bridge` is ever nil and `[RCTBridge currentBridge]` returns a real `RCTBridge`,
   `bridge.batchedBridge` has **no implementation** (`grep -rn batchedBridge React/` → only
   `RCTBridgeProxy.mm:259` and the header), so the first message send throws before the nil check.

The report's own caveat (`runtime path untested (no voice flow in this trial)`) is honest, and
`BINDING-PATCHES.md` item 4's follow-ups are correct. But `SDK58-TRIAL.md` reasons #2 calls this
"a binding that survives on a deprecation-shaped runtime path" without noting that the whisper
patch **converts a loud build-time failure into a silent runtime hazard** — strictly worse failure
mode than not building.

**6.5 The patch is not re-appliable. CONFIRMED.**
`scripts/` contains no patcher for either binding (`ls scripts/ | grep -i patch` →
`assert-native-patch.sh`, which asserts, it does not patch). `BINDING-PATCHES.md` says patch 1
was `Re-applied by sed`. The trial's run 1 already proved the failure mode
(`/tmp/ios-build58.log` — patch 1 missing after fresh `node_modules`). So on merge, the iOS build
breaks on the first clean `npm ci` unless the patches are forked upstream. The report lists this
under "node_modules only" but never states that **nothing in the repo reproduces them**.

## 7. Is the recommendation justified?

**The verdict (no-go now) is correct. The stated reasons are incomplete, and the report's own
framing understates the blocker.** Reasons 1 (RN 0.88-rc) and 3 ("everything else was routine")
hold. Reason 2 (unsupported surface) is directionally right but rests on a factually wrong
mechanism (F6.3) and omits the whisper fallback hazard (F6.4).

**Blocking items the report missed, in severity order:**

1. **CI-breaking peer set (§4.3).** Three genuine peer conflicts, zero at baseline, all masked by
   a flag that was never persisted. This is the concrete reason not to merge, and it is a *merge*
   risk, not an rc-philosophy risk. Nothing in the report addresses it.
2. **Fingerprint `balanced` × node_modules patching (§5.2a).** SDK 58's new default makes the
   trial's entire binding strategy unsafe under EAS Build caching. Unmentioned. This alone
   justifies no-go regardless of RN 0.88 stable timing.
3. **No reproducible patch pipeline (§6.5).** Neither binding patch survives `npm ci`, no CI
   workflow applies either, and no iOS workflow exists to catch it.
4. **`expo-notifications` foreground-default behaviour change (§5.2b).** Shipped silently.
5. **20 undocumented package.json changes (§3.2), incl. a reverted deliberate jest 30→29
   downgrade** (`git log -S'"jest": "^30'` → `69a7662b`, a deliberate bump; the report's
   `(expo --fix aligned it back)` mischaracterises a regression as a correction).
6. **Baseline is now stale (§1.4):** `origin/main` is `de52fdf1`, 3 commits past `cbddc1f2`.
7. **Simulator-only.** The report says so; the on-device pass is correctly listed as a
   precondition. One addition: `recommendedMaxWorkingSetSize 0.00 MB` and `offloaded 0/31`
   mean **zero Metal offload was exercised** — the entire `ggml-metal-ops.cpp` patch sits in
   kernel code that never ran. The report says "CPU backend, numbers are not device datapoints"
