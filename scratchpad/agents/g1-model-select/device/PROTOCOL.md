telefoni" (here: S23 + Jelly; the Xiaomi 192.168.1.193 is out of scope and must
never be addressed) with the §7 time-spending rules (paired comparisons,

## Per-case structure (what the runner does)

thermal gate → force-stop → (kalsa.model.id via SQL iff changed) → NEW
conversation appended to `kalsa.conversations.v1` + empty `kalsa.messages.<id>`
via WAL-safe SQL (app stopped) → launch → wait engine-idle → per user turn:
clear logcat, deliver via `kalsa://share?text=` (share-send proves submission),
poll the message store until the assistant text is stable ×2 AND no new
KALSA telemetry/toolcall/session line for 20 s AND last telemetry not
interrupted → capture reply (text + raw modelEmittedText), telemetry
(promptMs, predictedPerSecond, tokensCached, tool names), RSS, thermal,
battery. Timeouts/send failures are rows (`reply_timeout`, `send_failed`,
`not_run`) — never dropped. Model proof per case: `llama_model_loader` line
(names the GGUF) + `KALSA_NATIVE_VARIANT` in `row.engine`.

## Timeouts (task: 240 s S23 / 600 s Jelly — model-adjusted)

| phone | model | reply cap | ready cap | why |
|---|---|---|---|---|
| S23 | lfm2.5-2.6b | 240 s | 240 s | measured turns settle 70–130 s |
| S23 | dev-minicpm5-2b | 480 s | 360 s | MiniCPM prewarm never logs `done` (see limits) and re-prefills ~2.5 min after each share reload |
| Jelly | either | 600 s | 600 s | per task; raise REPLY_TIMEOUT only if the log shows clipped turns with evidence of progress |

## Thermal / battery rules (never disables protections)

- Read before every case: `dumpsys thermalservice` status + battery
  temperature (deci-°C) + level; pause condition status ≥ 3 (SEVERE) or
  battery > 41.0 °C; resume only when status ≤ 1 AND battery < 38.0 °C;
  30 s polls; 1200 s cap then the run dies naming the thermal state.
- Runs are unplugged (measured discipline). Charge to 100 % between model
  arms and let the phone cool below ~36 °C before starting the next arm.
- Keep-awake (screen timeout 24 h + Doze whitelist + Termux wakelock, all
  restored on exit) is armed by the runner for the whole invocation — never
  split a phone/model run across invocations without keep-awake.
- S23 runs over wireless ADB; Jelly over USB. Every adb call uses
  `-s <serial> … </dev/null`.

## Declared limits (measured, not assumptions)

1. **Share deep link backgrounds RN** (AppState → disposeEngine) on every
   delivery; share-send recovers via the model-bar reload, and each case's
   first turn pays the engine reload + idle prewarm again. Cold-start loss is
   real on this APK and is part of the measurement (bootstrap is never
   counted in turn telemetry; promptMs comes from KALSA_TELEMETRY).
2. **Fresh conversation per case requires the app stopped** (SQL writes are
   refused while it runs) → every case is a cold launch; that is why the
   ready wait is part of each case.
3. **MiniCPM prewarm quirk**: its `n_predict=0` prewarm completion returns no
   timings (`promptMs:0`) → `KALSA_PREWARM done` never logs; the engine logs
   `skip eval-failed` after the prefill (~2.5 min on the S23) and is idle
   then. The runner treats that marker as ready. The prefix KV is populated
   anyway (first-turn tokensCached ≈ 2180–2255 measured).
4. **Tool arguments are not verifiable on-device**: KALSA_TOOLCALL is
   privacy-safe by design (names + counters only). Tool cases (T09→device_calc,
   T11→write_note) PASS on name + `executed ≥ 1`; corpus argument checks do
   not apply on-device (recorded in the cases file `adaptation`).
5. **Only two corpus tool ids are offline-capable** on this APK; the subset's
   7/7/6/4 quota is therefore 7 conv / 11 instr / 2 tools / 4 memory (see
   SUBSET-24.md). No EN offline tool case exists in the corpus (the dry run's
   EN device_calc case T09-en is a declared synthetic twin).
6. **S23 uiautomator dumps are flaky**; UI text is a last-resort ready signal
   (fresh dump each poll), logcat markers are primary.
7. **Rubric cases C07/I14** get status RUBRIC and need the blind judge;
   holdout is untouched.
8. Interrupted replies persist with `interrupted:true` and no telemetry —
   recorded as `reply_timeout` rows with the partial text (never dropped).
9. LFM answered the IT C01 turn with a **device_calc tool call**; MiniCPM
   answered directly and echoed a textual `<function>` block in the answer
   prose while still emitting the structured call — both PASS the corpus
   check; both behaviors are model signal, not harness error.
