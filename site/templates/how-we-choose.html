How we choose what is listed

Kalsa is a database of local inference engines and forks. This page says what gets listed, what counts as an improvement, and what a review does and does not cover. Zero risk is impossible: an engine is someone else’s code running with your permissions.

The rules an engine must pass

All seven, before it appears. A person checks the evidence and the install source; a weekly job rechecks stars, licence, archived status and the last commit.

An improvement anyone can check

An improvement can be many things, not only speed. The author must show at least one, with a source anyone can open, on a named machine. A fork has to improve on its upstream on that same machine, or on itself with the feature switched off. Reference engines such as llama.cpp and mlx-lm are the baseline, so they are exempt. Projects that other listed forks build on are listed as references even when they publish no comparison of their own.

ImprovementWhat countsEvidence we need
Faster decodeTokens per second while generating, at least 5% above the baseline.A benchmark row: the machine, the model, the quantisation and both numbers, measured on the same machine. The baseline is the upstream, or the engine with the feature switched off.
Faster prefillTokens per second while reading the prompt, at least 5% above the baseline.The same benchmark row, with the prefill figures.
Bigger modelsA model that does not fit, or does not run, in the baseline on the same machine.The model and its size, the machine and its memory in GB, and the tokens per second measured there.
Multiple machinesOne model run across more than one machine.The machines and the link between them. A speed only if the author published one.
Longer contextA longer context window on the same machine.The context length before and after, in tokens, on a named machine.
New hardwareRuns on hardware the baseline does not support.The hardware, and the model that was run on it.
New modelRuns a model the baseline does not.The model, and the machine it was run on.
Faster startA shorter time before the first token, or to load a model.The time before and after, in seconds, at least 5% apart, on a named machine.
Less memoryLess memory for the same model.The memory before and after, in the same unit, at least 5% apart, with the model and the machine.
Parallel throughputMore tokens per second across many requests at once.The total before and after, and how many requests ran together, at least 5% apart. It is a total, not the speed of one stream.
QualityA better result from the same model.A named measure, before and after, at least 5% apart, with the model and the machine.
EnergyLess energy for the same work.The energy before and after, in one unit, at least 5% apart, on a named machine.
  • Under 5% is noise. Where an improvement is a number before and after, a difference under 5% either way does not count.
  • Trade-offs must be declared. When the source states a cost, such as lower quality or a slower speed, the entry says so beside the improvement.
  • What does not count. Features that cannot be measured, such as tool calling, vision or a user interface. A change that is only different, not better. A number without the machine it was measured on.

At least 5 GitHub stars

A low bar on purpose: it only filters out projects nobody has looked at yet.

A real open-source licence

Apache, MIT, BSD, GPL and the like (OSI-approved). No licence, non-commercial or research-only licences are excluded.

Signs of life

Not archived, not marked deprecated in its own README, and at least one commit in the last six months.

A declared upstream

A fork has to say what it forks, through GitHub’s fork flag or its README, so we can show “fork of X” and credit the original.

Install from official sources only

The repository’s releases, PyPI or Homebrew, pinned to one version or commit and checked against a checksum. No curl | sh from arbitrary domains and no binaries hosted somewhere else.

No sudo, no tampering

The install must not need sudo, must not ask you to turn off Gatekeeper or SIP, and must not add system services.

What “claimed by the author” means

Every number on this site comes from the author’s own README, run on the author’s own machine, and links back to it. Kalsa has not re-run it.

What the badge means

Two separate things. Listing says where an engine sits in the catalogue. The badge says whether Kalsa has checked its code.

ListedListing

The verified catalogue. It came in by pull request, the rules were checked, and Kalsa can recommend it.

CommunityListing

Self-listed by its author, in a separate section. Kalsa never recommends it.

ReviewedBadge

Kalsa checked the code at a specific commit for suspicious changes. Both listing tiers can earn it. The badge shows the commit and the date.

No badgeBadge

Not reviewed. No pill is shown, in either tier.

What a review looks at

  • new network calls
  • install or build scripts that download things
  • new dependencies
  • binary blobs
  • obfuscated code
  • secrets or telemetry endpoints

For a fork the review reads the diff against its upstream; for any other engine it reads the whole repository. The result is worded plainly: Reviewed: no suspicious changes found in the diff against <upstream> at <commit>. When a newer commit lands, the badge shows “re-check pending” until it is looked at again. A review lowers the risk, it cannot remove it.

Reference projects such as llama.cpp and mlx-lm are the baseline others are compared against. They are not diff-reviewed. That is a note, not a badge.

How the order is decided

Same chip first

A number measured on your own chip leads, with a solid label and a larger figure.

Other chips are weaker

A number from a different chip is shown smaller, dashed, with the chip’s name next to it. A chip that is faster or slower than yours says little about how an engine behaves on it. Lists are otherwise A to Z, not ranked.

A note on risk.
An engine runs as you, with access to your files, and macOS offers no real sandbox for it. The rules above lower the chance of a bad engine; they cannot remove it. Read the “How to install” section on every engine page, follow the project’s own instructions, and install only what you trust.

Listing and removal

Kalsa is not affiliated with the authors of the listed projects.

We list public projects without asking

An engine is listed when it is a public open-source project that passes the rules. The author does not have to apply, though they can submit one.

The summaries are our own

We write the one-line descriptions ourselves and do not copy README text. Numbers are always attributed to the author and linked to the page they came from.

Avatars and usernames are public

They come from public GitHub profiles. Kalsa holds no private data about the people behind a project.

Anyone can ask to be removed

An author, or anyone else, can ask for an entry to be taken down. Requests are handled within a few days. Write to {{help}}, or open an issue on GitHub; every engine and developer page links here from the line at its bottom.

When an entry is removed

It falls below the bar

The weekly check opens an issue when an entry has too few stars, a changed licence, an archived repository or no commit in six months.

Someone shows evidence

Anyone can open an issue or a pull request against the catalogue, for example when a benchmark is wrong or an install source has changed.

The author asks

If the author asks, the entry goes.

This is the proposed process. How long an entry gets to fix a problem is not decided yet.
